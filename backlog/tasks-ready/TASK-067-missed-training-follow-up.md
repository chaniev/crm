# TASK-067: Выявлять клиентов с повторными пропусками тренировок

## Status
ready

## Goal
Администратор или главный тренер видит единый список клиентов, требующих внимания, понимает все причины попадания каждого клиента в список и может связаться с клиентом после трёх и более пропусков подряд.

## Context
На `Главной` уже есть вкладка `Абонементы` со списком клиентов, требующих внимания из-за состояния абонемента. Её нужно переименовать в `Клиенты, требующие внимания` и дополнить причиной повторных пропусков. Один клиент должен отображаться в списке один раз, даже если одновременно подходит по нескольким условиям, при этом в его строке должны быть видны все актуальные причины попадания в список. После связи сотрудник отмечает причину повторных пропусков как обработанную; она появляется снова только после новой последовательности из трёх и более пропусков подряд.

## User role
Администратор / главный тренер.

## Problem
Повторные пропуски не выделяются в рабочем интерфейсе, поэтому администратор может поздно заметить клиента, которому требуется внимание.

## Scope
- Реализовать backend-owned расчёт последовательности из трёх и более явно отмеченных пропусков `Absent`.
- Считать последовательность по клиенту, а не отдельно по группе: смена группы не разрывает последовательность.
- Учитывать последовательность как в период действия абонемента, так и после окончания его срока; граница окончания абонемента последовательность не разрывает.
- Разрывать последовательность при отсутствии занятия и на период заморозки абонемента.
- Переименовать существующую вкладку `Абонементы` на `Главной` в `Клиенты, требующие внимания`, не создавая дополнительную вкладку.
- Объединить в этой вкладке существующие причины внимания, связанные с абонементом, и новую причину `Три и более пропуска подряд`.
- Возвращать и показывать каждого клиента в объединённом списке только один раз независимо от количества актуальных причин.
- Показывать у клиента все актуальные причины попадания в список, включая одновременно причину по абонементу и причину повторных пропусков.
- Показывать в списке ФИО, телефон, количество пропусков подряд при наличии соответствующей причины, статус абонемента и комментарий из карточки клиента.
- Если у клиента указан Telegram, предусмотреть переход во внешний Telegram без автоматической отправки сообщения.
- Добавить для причины повторных пропусков действие `Связались`, после которого текущая последовательность считается обработанной, а эта причина скрывается до появления новой последовательности из трёх и более пропусков подряд.
- Если после `Связались` у клиента остаются другие актуальные причины внимания, оставить клиента в списке и показывать оставшиеся причины.

## Out of scope
- Автоматическая рассылка сообщений.
- Изменение правил посещаемости и списания абонемента.
- Полноценная CRM-воронка удержания клиентов.

## Constraints
- Backend владеет attendance semantics и вычислением признака.
- Backend владеет состоянием обработки `Связались` и границей, после которой начинается подсчёт новой последовательности.
- Backend формирует единый набор причин внимания и исключает дубли клиентов; frontend не должен самостоятельно объединять клиентов или восстанавливать причины из разных наборов данных.
- Frontend не должен самостоятельно восстанавливать последовательность пропусков.
- Пропуском считается только явно сохранённый статус `Absent` (`не был`).
- `Unmarked` (`не отмечено`) не считается пропуском.
- Смена группы не должна сбрасывать последовательность пропусков клиента.
- Окончание срока действия абонемента не должно сбрасывать последовательность пропусков клиента.

## Acceptance criteria
- [ ] Клиент попадает в список после третьего подряд явно отмеченного `Absent`.
- [ ] При двух последовательных `Absent` клиент ещё не отображается; при трёх и более отображается.
- [ ] Последовательность может пересекать дату окончания абонемента, включая сценарий с пропусками до и после окончания срока.
- [ ] Три пропуска после окончания абонемента также приводят к отображению клиента.
- [ ] Отсутствие занятия и заморозка абонемента разрывают последовательность.
- [ ] Смена группы не разрывает последовательность.
- [ ] Существующая вкладка `Абонементы` переименована в `Клиенты, требующие внимания`; дополнительная вкладка для пропусков не создаётся.
- [ ] Администратор и главный тренер видят вкладку `Клиенты, требующие внимания` на `Главной`; остальные роли её не видят.
- [ ] Вкладка сохраняет существующие причины внимания, связанные с абонементом, и добавляет причину трёх и более пропусков подряд.
- [ ] Клиент, попавший в список по одной причине, отображается один раз с этой причиной.
- [ ] Клиент, одновременно попавший в список по нескольким причинам, отображается один раз, и у него видны все актуальные причины.
- [ ] В списке показаны ФИО, телефон, статус абонемента и комментарий из карточки клиента; количество последовательных пропусков показано при наличии причины повторных пропусков.
- [ ] При наличии Telegram сотрудник может открыть внешний Telegram клиента.
- [ ] После действия `Связались` причина повторных пропусков скрывается и появляется повторно только после трёх новых последовательных `Absent`.
- [ ] После действия `Связались` клиент исчезает из списка, если других причин внимания нет.
- [ ] После действия `Связались` клиент остаётся в списке, если у него есть другие актуальные причины, и эти причины продолжают отображаться.
- [ ] После исправления посещаемости или изменения заморозки признак пересчитывается корректно.

## Test checklist
- [ ] Проверить границу в два и три пропуска.
- [ ] Проверить статусы `был`, `не был` и `не отмечено`.
- [ ] Проверить последовательность, пересекающую дату окончания абонемента.
- [ ] Проверить три пропуска после окончания абонемента.
- [ ] Проверить разрыв последовательности отсутствием занятия и заморозкой.
- [ ] Проверить сохранение последовательности при смене группы.
- [ ] Проверить скрытие после `Связались` и повторное появление только после трёх новых пропусков.
- [ ] Проверить отсутствие дубля клиента при одновременной причине по абонементу и причине повторных пропусков.
- [ ] Проверить отображение всех актуальных причин у одного клиента.
- [ ] Проверить, что `Связались` закрывает только причину повторных пропусков и не скрывает актуальную причину по абонементу.
- [ ] Проверить новое название вкладки, её счётчик уникальных клиентов и объединённое пустое состояние.
- [ ] Проверить доступ к вкладке для администратора и главного тренера и отсутствие доступа у остальных ролей.
- [ ] Проверить переход во внешний Telegram и поведение при отсутствии Telegram.
- [ ] Добавить backend-тесты расчёта и frontend-тест отображения.

## Clarification questions
Не требуется. Продуктовая семантика уточнена:
- порог — три и более явно отмеченных `Absent` подряд;
- окончание абонемента и смена группы не разрывают последовательность;
- отсутствие занятия и заморозка разрывают последовательность;
- после `Связались` для повторного появления нужна новая последовательность из трёх пропусков;
- существующая вкладка `Абонементы` на `Главной` переименовывается в `Клиенты, требующие внимания` и расширяется, отдельная вкладка не создаётся;
- клиент отображается в объединённом списке один раз, а рядом показываются все актуальные причины внимания;
- действие `Связались` закрывает только причину повторных пропусков и не скрывает клиента при наличии других причин;
- отображаются ФИО, телефон, количество пропусков подряд, статус абонемента и комментарий из карточки;
- при наличии Telegram открывается внешний Telegram.
