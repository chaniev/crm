# Backlog

`backlog/` хранит входящие запросы и задачи на доработку.

Каждая активная карточка содержит `## Requirements`:

- `REQ-... — implements|changes|constrains|verifies` для связи с реестром;
- `none — <причина>` только если поведение продукта не меняется;
- `pending — <что нужно решить>` только в `needs-clarification`.

Статус `предложено` не разрешает реализацию; для перехода в `tasks-ready` или
`implementation` связанное продуктовое решение должно быть `принято`.

## Каталоги и статусы

- `inbox/` — новые входящие запросы до triage.
- `processing/` — временная обработка входящих запросов.
- `processed/` — обработанные исходные заметки.
- `tasks-ready/` — актуальные задачи с достаточными требованиями для планирования/реализации.
- `risky/` — актуальные задачи, которым нужен отдельный review из-за security, domain, data или runtime-риска.
- `needs-clarification/` — актуальные задачи с блокирующими продуктовыми или архитектурными вопросами.
- `implementation/` — задачи, явно переведённые в активную реализацию.
- `implementation-plans/` — планы только для незавершённых задач; наличие плана само по себе не означает, что задача реализуется.
- `done/YYYY-MM-DD/` — завершённые задачи, планы и контракты проверок по дате завершения.
- `logs/` — журналы triage, планирования и status audit.

Статус в карточке должен совпадать с каталогом. Реализованная задача и её plan перемещаются вместе в `done/YYYY-MM-DD/`; задача с незакрытыми обязательными вопросами не должна оставаться в `tasks-ready/` или `risky/`.

## Команда `зафиксируй`

Если пользователь пишет `зафиксируй`, создай файл `backlog/inbox/YYYY-MM-DD.md` с текущей датой, если его еще нет, и впиши туда все, что написано после первого `зафиксируй`. Если файл уже существует, добавь запись в конец файла.

Опечатку `зафикчируй` считай тем же триггером.

## Дата завершения и архив

- Формат папки: `backlog/done/YYYY-MM-DD/`. Отдельные task-файлы непосредственно
  в `done/` не размещать. Статус карточки остаётся `done`.
- Для реализации использовать дату интеграции завершённой доработки в `main`:
  `delivered_on_main_at` / `merged_to_main_at` либо подтверждённый Git merge.
  Если интеграция отдельно не фиксировалась, использовать явную дату завершения
  в карточке или плане, сверенную с evidence выполнения.
- Для закрытия уточнением, объединением или признанием уже выполненной работы
  использовать подтверждённую дату завершения соответствующей задачи; это
  не означает, что в этот день был реализован новый код.
- Не использовать дату создания задачи, mtime или текущую дату triage вместо
  исторической даты завершения. При недостаточном evidence не угадывать дату:
  записать неопределённость в triage-log и оставить перенос до её разрешения.
- Исключение для первоначального разнесения старого архива 2026-09-05: если
  точная дата реализации не установлена, использована дата первого появления
  карточки в `done` по Git. Эти приближённые даты явно отмечены в
  [журнале переноса](logs/2026-09-05-done-date-migration.md).
- В карточке при закрытии записывать `completed_at: YYYY-MM-DD` и
  `completion_date_evidence` со ссылкой на merge, проверку или решение;
  дату самого переноса при необходимости хранить отдельно в `moved_to_done_at`.
- В одну папку переносить карточку, её завершённый `.plan.md`, verification
  contract, baseline и task-owned evidence. Общие assets оставлять на месте.
  Обновлять актуальные ссылки, включая относительные пути из перенесённых файлов.
- Поиск дубликатов, следующий TASK-ID, подсчёты и поиск контрактов выполнять
  рекурсивно по всем датам. Исторические журналы не переписывать: добавлять
  запись о переносе с соответствием старых и новых путей.
