# Backlog

`backlog/` хранит входящие запросы и задачи на доработку.

Каждая активная карточка содержит `## Requirements`:

- `REQ-... — implements|changes|constrains|verifies` для связи с реестром;
- `none — <причина>` только если поведение продукта не меняется;
- `pending — <что нужно решить>` только в `needs-clarification`.

Статус `предложено` не разрешает реализацию; для перехода в `tasks-ready` или
`implementation` связанное продуктовое решение должно быть `принято`.

## Каталоги и статусы

- `inbox/` — новые входящие запросы до triage.
- `processing/` — временная обработка входящих запросов.
- `processed/` — обработанные исходные заметки.
- `tasks-ready/` — актуальные задачи с достаточными требованиями для планирования/реализации.
- `risky/` — актуальные задачи, которым нужен отдельный review из-за security, domain, data или runtime-риска.
- `needs-clarification/` — актуальные задачи с блокирующими продуктовыми или архитектурными вопросами.
- `implementation/` — задачи, явно переведённые в активную реализацию.
- `implementation-plans/` — планы только для незавершённых задач; наличие плана само по себе не означает, что задача реализуется.
- `done/` — реализованные задачи и завершённые implementation plans.
- `logs/` — журналы triage, планирования и status audit.

Статус в карточке должен совпадать с каталогом. Реализованная задача и её plan перемещаются в `done/`; задача с незакрытыми обязательными вопросами не должна оставаться в `tasks-ready/` или `risky/`.

## Команда `зафиксируй`

Если пользователь пишет `зафиксируй`, создай файл `backlog/inbox/YYYY-MM-DD.md` с текущей датой, если его еще нет, и впиши туда все, что написано после первого `зафиксируй`. Если файл уже существует, добавь запись в конец файла.

Опечатку `зафикчируй` считай тем же триггером.
