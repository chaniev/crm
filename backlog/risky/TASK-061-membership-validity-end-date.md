# TASK-061: Исправить дату окончания абонемента при оформлении

## Status
risky

## Goal
При оформлении абонемента пользователь видит и сохраняет корректный период действия: если абонемент начинается 10 июня и действует один месяц, последним днем действия должно быть 9 июля, а не 10 июля.

## Context
В inbox зафиксирована заметка: `При оформлении абонемента дата его действия автоматически стоит например с 10 июня по 10 июля, а должно быть с 10 по 9`.

Требование касается автоматического расчета периода абонемента в момент оформления. Так как это membership semantics, задача относится к risky: ошибка может повлиять на истечение абонементов, списание посещений, отчеты и отображение статусов.

## User role
администратор / главный тренер

## Problem
Сейчас автоматически рассчитанный период абонемента выглядит на один день длиннее ожидаемого пользовательского правила. Для включительного отображения периода пользователь ожидает диапазон `10 июня - 9 июля`, потому что 10 июля уже относится к следующему периоду.

## Scope
- Найти, где рассчитывается дата окончания абонемента при оформлении: backend contract/use case, frontend form default или оба слоя.
- Зафиксировать backend-owned правило периода действия абонемента: дата начала включается в период, а видимая дата окончания для месячного периода должна быть днем перед тем же числом следующего периода.
- Исправить автоматический расчет даты окончания для нового абонемента.
- Убедиться, что frontend не дублирует доменную логику, если backend уже возвращает или валидирует рассчитанный период.
- Обновить тексты/форматирование даты только там, где это нужно для корректного отображения периода.
- Добавить regression coverage на пример `10 июня - 9 июля`.

## Out of scope
- Изменение цен, типов абонементов, оплат, возвратов или заморозок.
- Изменение правил списания посещений, кроме случаев, напрямую зависящих от исправленной даты окончания.
- Массовая миграция существующих абонементов без отдельного решения.
- Переработка всего membership UI.
- Изменение доступа ролей к оформлению абонементов.

## Constraints
- Backend owns membership validation semantics and ProblemDetails contracts.
- Нельзя исправлять только визуальный текст, если сохраняемое значение остается неверным.
- Если backend contract меняется, нужно обновить все consumers.
- Существующие сценарии истекающих, истекших и неоплаченных абонементов не должны сломаться.
- Нужно внимательно проверить граничные даты месяцев, чтобы не ввести off-by-one ошибку для конца месяца.

## Acceptance criteria
- [ ] При старте абонемента 10 июня и месячном сроке действия автоматическая дата окончания показывается как 9 июля.
- [ ] Сохраняемое значение даты окончания соответствует отображаемому правилу, а не только тексту в форме.
- [ ] Backend validation не принимает противоречивый период, если такой guard уже предусмотрен архитектурой.
- [ ] Frontend использует backend-owned contract или единый helper, а не отдельную несогласованную формулу.
- [ ] Существующие статусы абонемента и сценарии списка/карточки клиента продолжают работать.
- [ ] Regression tests покрывают off-by-one пример из inbox.

## Test checklist
- [ ] Запустить backend tests.
- [ ] Запустить `cd frontend && npm run lint`.
- [ ] Запустить `cd frontend && npm run build`.
- [ ] Добавить или обновить backend tests на расчет/валидацию периода абонемента.
- [ ] Добавить или обновить frontend tests на default-дату в форме оформления абонемента, если расчет виден на frontend.
- [ ] Вручную проверить оформление абонемента со стартом 10 июня.
- [ ] Вручную проверить дату около конца месяца, если UI позволяет выбирать такую дату.
