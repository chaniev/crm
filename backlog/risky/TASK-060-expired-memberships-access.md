# TASK-060: Расширить блок абонементов на главной истекшими абонементами

## Status
risky

## Goal
Администратор и главный тренер могут быстро увидеть клиентов с истекшими и скоро истекающими абонементами в существующей области главной страницы, не нарушая backend-owned правила ролей, memberships и доступа.

## Context
В inbox зафиксировано требование: `добавить для администратора и главного тренера возможность просмотра истекших абонементов`.

В текущей реализации на главной уже есть блок `Истекающие абонементы` для ролей `Administrator` и `HeadCoach`. Он использует backend endpoint текущего home-сценария и показывает клиентов, у которых абонемент истекает в ближайшее окно, но не показывает уже истекшие абонементы. В проекте также уже есть backend-семантика состояния `Expired` для абонементов в списке клиентов.

Выбранный продуктовый путь: не создавать отдельную область только для истекших абонементов. Нужно развить существующий блок на главной в общую область внимания по абонементам, например `Абонементы требуют внимания`, где истекшие и истекающие абонементы показаны вместе, но явно различаются в UI и в backend-контракте.

## User role
администратор / главный тренер

## Problem
Администратору и главному тренеру нужна явная видимость клиентов, у которых текущий абонемент уже истек, чтобы вовремя продлевать абонементы и управлять клиентской базой. Текущий блок на главной помогает с будущими истечениями, но создает слепую зону для уже просроченных абонементов. При этом отдельный новый экран или отдельная область увеличили бы сложность интерфейса, хотя сценарий логически относится к той же зоне внимания на главной.

## Scope
- Проверить текущий backend endpoint главной для истекающих абонементов и существующую backend-семантику `Expired`.
- Расширить backend-контракт home-сценария так, чтобы он возвращал элементы внимания по абонементам с явным состоянием, например `Expired` / `ExpiringSoon`.
- Считать состояние истекшего и истекающего абонемента только на backend; frontend должен использовать готовое состояние из ответа, а не вычислять его эвристикой по дате.
- Обеспечить доступ к просмотру для ролей `Administrator` и `HeadCoach` согласно существующей модели permissions/access scope.
- Обновить существующий блок главной `Истекающие абонементы` в единую область внимания по абонементам, например `Абонементы требуют внимания`.
- Показать понятные поля: клиент, тип абонемента, дата окончания, состояние абонемента, сколько дней просрочено или осталось, статус оплаты и действие перехода в карточку клиента, если оно доступно.
- Отсортировать элементы так, чтобы истекшие абонементы не терялись среди будущих истечений; предпочтительно показывать истекшие первыми, затем истекающие по ближайшей дате.
- Добавить backend/frontend regression coverage для доступа и отображения.

## Out of scope
- Изменение правил расчета истечения абонемента.
- Изменение правил покупки, продления, оплаты или списания посещений.
- Изменение ролей и общей модели permissions вне доступа к просмотру истекших абонементов.
- Создание отдельной новой области, отдельного экрана или отдельного раздела только для истекших абонементов.
- Переработка списка клиентов и его quick filters, если она не требуется для корректной работы главной.
- Массовые изменения данных или миграции без отдельного решения.
- Telegram-bot сценарии, если текущий продуктовый scope относится к CRM frontend.

## Constraints
- Backend owns CRM business logic: roles, permissions, memberships, attendance, validation semantics and ProblemDetails contracts.
- Frontend не должен вычислять истекший абонемент независимо от backend.
- Frontend должен явно отличать `Expired` от `ExpiringSoon` по состоянию из backend-контракта, а не только по отрицательному `daysUntilExpiration`.
- Не расширять доступ ролей, кроме явно указанных `Administrator` и `HeadCoach`, без отдельного решения.
- Существующие сценарии истекающих и неоплаченных абонементов не должны сломаться.
- Если меняется backend contract, обновить все затронутые consumers.
- Если сохраняется старый URL endpoint для совместимости, название UI и форма ответа должны отражать расширенную семантику области внимания, а не только `expiring`.

## Acceptance criteria
- [ ] Administrator видит на главной единую область внимания по абонементам, включающую истекшие и скоро истекающие абонементы.
- [ ] HeadCoach видит на главной единую область внимания по абонементам, включающую истекшие и скоро истекающие абонементы.
- [ ] Роли без соответствующего доступа не получают новую видимость истекших абонементов.
- [ ] Состояние истекшего абонемента определяется backend-логикой, а не frontend-эвристикой.
- [ ] Backend item для области внимания содержит явное состояние абонемента, например `Expired` / `ExpiringSoon`.
- [ ] UI явно отличает истекшие абонементы от истекающих и неоплаченных.
- [ ] Для истекших абонементов UI показывает понятный текст просрочки, например `Истек 3 дня назад`, а не только отрицательное количество дней.
- [ ] Для истекающих абонементов UI сохраняет понятный текст ближайшего окончания, например `Сегодня` или `Осталось 3 дня`.
- [ ] Пользователь может перейти из элемента области внимания в карточку клиента, если это разрешено доступом.
- [ ] Regression tests покрывают права доступа и отображение данных.

## Test checklist
- [ ] Запустить backend tests.
- [ ] Запустить `cd frontend && npm run lint`.
- [ ] Запустить `cd frontend && npm run build`.
- [ ] Добавить или обновить backend tests на доступ `Administrator`, `HeadCoach` и отрицательные роли для расширенного home endpoint.
- [ ] Добавить или обновить backend tests, что home endpoint возвращает и `Expired`, и `ExpiringSoon`, но не возвращает абонементы вне окна внимания.
- [ ] Добавить или обновить frontend tests/e2e на отображение истекших и истекающих абонементов в одной области главной.
- [ ] Проверить, что неоплаченный статус отображается отдельно от состояния истечения.
- [ ] Проверить, что существующие сценарии истекающих абонементов продолжают работать в обновленной области главной.
