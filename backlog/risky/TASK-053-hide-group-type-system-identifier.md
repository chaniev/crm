# TASK-053: Убрать системный идентификатор из создания типа группы

## Status
risky

## Goal
Пользователь создает тип группы без ручного ввода технического системного идентификатора.

## Context
В inbox есть заметка: "удалить системный идентификатор при создании типа группы". Сейчас типы групп появились как часть настроек CRM, и ранее для них был зафиксирован набор полей: название, описание и системный идентификатор.

## User role
главный тренер / администратор

## Problem
Техническое поле системного идентификатора попадает в пользовательский сценарий создания типа группы и усложняет форму.

## Scope
- Проверить текущий backend/frontend контракт типов групп.
- Убрать ручной ввод системного идентификатора из create-flow типа группы.
- Определить backend-owned поведение для системного идентификатора: автогенерация, nullable/optional поле или сохранение только для внутренних/system-seed записей.
- Обновить frontend форму создания типа группы под новый контракт.
- Обновить validation/error handling так, чтобы frontend не дублировал backend validation semantics.
- Сохранить корректное поведение редактирования существующих типов групп.

## Out of scope
- Перепроектирование всего раздела `Настройки`.
- Изменение справочников филиалов, залов или групп.
- Массовая миграция/переименование существующих типов групп без отдельного решения.
- Изменение расписания, посещаемости или membership logic.

## Constraints
- Backend остается источником истины для group type validation semantics и ProblemDetails.
- Frontend не должен самостоятельно придумывать доменные правила уникальности системного идентификатора.
- Если изменение требует database contract/schema change, оно должно быть выделено и проверено как backend contract change.
- Не ломать существующие группы, которые уже ссылаются на типы групп.

## Acceptance criteria
- [ ] В форме создания типа группы нет поля системного идентификатора.
- [ ] Создание типа группы работает без ручного ввода системного идентификатора.
- [ ] Backend явно владеет правилом генерации или отсутствия системного идентификатора.
- [ ] Validation errors по типам групп остаются backend-owned и отображаются во frontend без доменного дублирования.
- [ ] Существующие типы групп и группы с выбранным типом продолжают открываться и редактироваться корректно.

## Test checklist
- [ ] Backend tests: создать тип группы без системного идентификатора.
- [ ] Backend tests: проверить уникальность/валидацию нового правила, если идентификатор сохраняется.
- [ ] Frontend lint + build.
- [ ] Frontend test или ручная проверка settings group type create/edit flow.
- [ ] Проверить, что создание/редактирование группы с выбранным типом не сломано.
