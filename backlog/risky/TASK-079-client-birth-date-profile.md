# TASK-079: Добавить дату рождения и возраст в профиль клиента

## Status
risky

## Goal
Пользователь с доступом к карточке клиента может указать дату рождения при создании клиента, изменить её в профиле и увидеть дату рождения и вычисленный возраст в карточке клиента.

## Context
В текущей модели `Client`, create/update request и details response отдельного поля даты рождения нет. Для реализации необходимо согласованно изменить хранение, backend API и frontend-формы клиента.

## User role
Все пользователи, которым существующие backend permissions разрешают создавать, просматривать или редактировать карточку клиента.

## Problem
В профиле клиента нельзя сохранить и увидеть дату рождения, а возраст клиента не вычисляется.

## Scope
- Добавить nullable date-only поле даты рождения в domain/persistence и backend API-контракты создания, редактирования и получения карточки клиента.
- Добавить необязательный ввод даты рождения в форму создания клиента.
- Добавить возможность указать, изменить и очистить дату рождения при редактировании профиля.
- Показывать дату рождения и вычисленный возраст в карточке клиента.
- Вычислять возраст в полных годах на текущую календарную дату; возраст не хранить отдельным изменяемым значением.
- Если дата рождения не задана, показывать пустое поле и не вычислять возраст.
- Использовать существующие permissions карточки клиента: поле доступно для просмотра всем, кто может просматривать карточку, и для изменения всем, кто может её редактировать.
- Оставить дату рождения пустой у существующих клиентов; backfill не выполнять.

## Out of scope
- Автоматический расчёт возрастной категории или изменение правил групп.
- Поздравления, уведомления и отдельные birthday-отчёты.
- Фильтры и поиск по дате рождения или возрасту.
- Сбор иных персональных данных.

## Constraints
- Дата рождения является персональными данными; доступ и аудит изменений должны соответствовать backend-owned ролям и permissions.
- Дата должна иметь однозначную date-only семантику без зависимости от часового пояса.
- Специальные бизнес-ограничения по минимальной, максимальной или будущей дате не требуются. Backend должен отклонять только значение, которое невозможно разобрать как дату согласно API-контракту.
- Возраст является производным значением и не должен независимо сохраняться или редактироваться.
- Возраст вычисляется по бизнес-дате клуба из существующего backend business date provider, а не по локальной дате браузера.
- Для будущей даты рождения карточка показывает дату, а вместо отрицательного возраста — `Не вычисляется`; значение при этом принимается и сохраняется без range validation.
- Для даты рождения 29 февраля возраст в невисокосный год увеличивается 1 марта.
- API и форма используют `YYYY-MM-DD`, а карточка отображает дату рождения в русском календарном формате.
- Изменение схемы БД, API-контрактов и consumers требует отдельного implementation plan и полной cross-layer проверки.
- Существующие клиенты без даты рождения остаются валидными.

## Acceptance criteria
- [ ] При создании клиента дату рождения можно указать или оставить пустой.
- [ ] При редактировании клиента дату рождения можно указать, изменить или очистить.
- [ ] Backend сохраняет nullable date-only значение и возвращает его в details response без преобразования часового пояса.
- [ ] Карточка клиента показывает сохранённую дату рождения и возраст в полных годах на текущую дату.
- [ ] Текущая дата для расчёта возраста определяется бизнес-днём клуба; часовой пояс браузера не влияет на результат.
- [ ] Будущая дата сохраняется и показывается без отклонения, а значение возраста отображается как `Не вычисляется`.
- [ ] Для 29 февраля в невисокосный год возраст увеличивается 1 марта.
- [ ] Карточка показывает дату рождения в русском календарном формате, сохраняя wire/form contract `YYYY-MM-DD`.
- [ ] Для клиента без даты рождения поле в карточке остаётся пустым, возраст не показывается.
- [ ] Просмотр и изменение даты рождения используют те же backend permissions, что просмотр и изменение карточки клиента.
- [ ] Для существующих клиентов дата остаётся пустой; обязательный backfill не требуется.
- [ ] Значения даты не ограничиваются специальным продуктовым диапазоном; невалидный формат обрабатывается стандартной validation-семантикой API.
- [ ] Изменение даты рождения попадает под существующую audit-семантику изменений клиента.
