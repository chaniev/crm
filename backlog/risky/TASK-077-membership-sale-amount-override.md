# TASK-077: Поддержать индивидуальную сумму продажи абонемента

## Status
risky

## Goal
Администратор может оформить клиенту абонемент по каталожной цене, по индивидуальной сумме либо зафиксировать продажу только суммой без выбора варианта каталога; все финансовые расчёты используют фактически сохранённую сумму продажи.

## Context
Сейчас вариант абонемента служит шаблоном с неизменяемой ценой, а при оформлении клиенту сумма продажи берётся из каталога. Требуется разрешить индивидуальную сумму для конкретного клиента и сценарий продажи без выбора варианта абонемента.

Ранее реализованная TASK-070 закрепила каталог, неизменяемую цену варианта и историческую сумму продажи. Эта задача расширяет контракт оформления и должна явно согласовать новую семантику с действующими ограничениями каталога, возвратов, коррекций и финансовых отчётов.

## User role
Администратор / главный тренер.

## Problem
Каталожная цена не позволяет отразить индивидуальную договорённость с конкретным клиентом. Пользователю нужен явный выбор между ценой шаблона, индивидуальной суммой при выбранном шаблоне и продажей только по сумме без шаблона, при этом отчёты не должны продолжать использовать каталожную цену вместо фактической суммы.

## Scope
- Поддержать оформление с выбранным вариантом каталога без ручной суммы: фактическая сумма равна цене варианта.
- Поддержать оформление с выбранным вариантом каталога и вручную указанной индивидуальной суммой: фактическая сумма равна введённому значению.
- Поддержать оформление только с вручную указанной суммой без выбора варианта каталога.
- Сделать сохранённую фактическую сумму продажи единственным источником денежных расчётов по конкретной продаже.
- Согласовать backend-контракт, валидацию, аудит и frontend-формы для трёх сценариев.
- Сохранить корректность возвратов, коррекций и финансовых отчётов при индивидуальной сумме.
- Зафиксировать понятное отображение происхождения суммы: каталожная или введённая вручную.

## Out of scope
- Изменение цены уже созданного варианта каталога.
- Массовое изменение сумм существующих продаж.
- Перерасчёт исторических продаж без отдельного решения по данным.
- Изменение правил доступа к абонементам, филиалам и финансовым отчётам.
- Изменение сроков действия и правил списания посещений.

## Constraints
- Backend остаётся единственным владельцем финансовой семантики, валидации, ролей, филиального scope и аудита.
- Цена варианта каталога остаётся неизменяемой и используется как значение по умолчанию, а не как динамический источник для уже оформленной продажи.
- Фактическая сумма должна храниться как исторический snapshot и не зависеть от последующих изменений каталога.
- Нельзя допустить неоднозначное состояние, в котором отсутствуют и вариант каталога, и ручная сумма.
- Продажа без варианта каталога должна получить явную backend-owned семантику типа/поведения абонемента; frontend не должен выводить её самостоятельно.
- Сумма должна проходить денежную валидацию и использовать согласованные правила округления и валюты.
- Существующий инвариант возвратов не должен нарушаться: сумма неотменённых возвратов не превышает фактическую валовую сумму продажи.
- Изменение контракта требует обновить и проверить все backend, frontend и bot-потребители.

## Acceptance criteria
- [ ] Backend принимает и различает три сценария: вариант без override, вариант с override и ручная сумма без варианта.
- [ ] Если выбран вариант и ручная сумма отсутствует, в продажу копируется каталожная цена.
- [ ] Если передана ручная сумма, она сохраняется как фактическая валовая сумма продажи и используется во всех денежных расчётах.
- [ ] Нельзя оформить продажу без варианта и без ручной суммы.
- [ ] Для продажи без варианта backend однозначно определяет и сохраняет поведенческий тип абонемента; контракт не позволяет frontend подменять бизнес-правила.
- [ ] Некорректные суммы отклоняются единым ProblemDetails-контрактом.
- [ ] Финансовые отчёты, возвраты, оплаты и коррекции используют сохранённую фактическую сумму, а не цену каталога.
- [ ] Аудит фиксирует выбранный вариант, фактическую сумму и факт ручного переопределения либо отсутствия варианта.
- [ ] Интерфейс явно показывает применяемую сумму и не маскирует ручное значение каталожной ценой.
- [ ] Существующие продажи и отчёты сохраняют прежнюю историческую сумму без автоматического перерасчёта.
- [ ] Обновлены все потребители изменённого backend-контракта, включая bot при наличии соответствующего сценария.

## Test checklist

- [ ] Добавить backend integration-тесты сохранения продажи, валидации ProblemDetails, авторизации и аудита.
- [ ] Проверить нулевую, отрицательную, чрезмерно точную и отсутствующую ручную сумму согласно утверждённым денежным правилам.
- [ ] Проверить возврат и correction для продажи с override и без каталожного варианта.
- [ ] Проверить финансовые итоги и разбивки по продажам с каталожной и индивидуальной суммой.
- [ ] Добавить frontend-тесты переключения трёх сценариев, payload и отображения фактической суммы.
