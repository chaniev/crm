## Goal

## Executable evidence
- Web учитывает materialized overrides, отмену, перенос и one-off; перенесённое занятие не остаётся на прежней дате.
- Bot строит recurring список, для Coach добавляет exact substitution occurrences с ещё не выданным ID. Обычные one-off и overrides не обрабатываются одинаково с web.
- Bot DTO содержит status и canEditAttendance, но текущий selector выдаёт кнопки всем возвращённым строкам. Поэтому единое поведение требует проверки Python consumer, а не только C# extraction.
- Web calendar и web today worklist — разные представления: календарь показывает Cancelled; REQ-ATT-006 скрывает Cancelled и полностью отмеченные занятия только на landing /attendance. Это не основание автоматически переносить весь action-only фильтр в бота.

## Принятый продуктовый контракт — 17.11.2026
1. Для одного сотрудника и выбранной даты календарь и бот опираются на одни актуальные занятия с одинаковыми датой, временем, залом и действующими тренерами. Их представление может отличаться.
2. Разовые занятия показываются наравне с занятиями серии в пределах доступа.
3. Перенос сохраняет идентичность занятия, убирает старую дату и показывает новую; дубля на прежней дате нет. Уже сохранённый snapshot посещений не переписывается.
4. Отмена запрещает новые отметки; восстановление возвращает обычную возможность отметки в рамках прав и дат.
5. Старая кнопка после отмены или переноса на другую дату не позволяет сохранить отметки; пользователь выбирает актуальное занятие заново. Автоматического переноса черновика на другое занятие нет.
6. Назначения и замещения учитываются в данных занятия; права и допустимые даты не расширяются.
7. Отменённое занятие в боте остаётся строкой «Отменено» без кнопки отметок.

На отдельный вопрос о представлении отменённых занятий ответил: «Показывать „Отменено“ без кнопки». Оба решения приняты владельцем проекта в текущем чате. Продуктовые вопросы закрыты; нормативная редакция REQ-BOT-003 обновлена до production code.

## Technical decision evidence — 17.11.2026
Исходный запрос разрешает выполнить предложенный общий серверный read model. После рассмотрения сохранения различий пользователь явно принял единые фактические занятия, переносы/отмены/one-off и строки без кнопки. В совокупности это выбирает общую проекцию фактического календаря для двух consumers. Независимый refactoring review подтвердил отсутствие дополнительных material choices: typed facts, reader/projector и DI являются деталями реализации. Новые блокировки, схема, транспортные форматы и гарантии сериализации не вводятся.

## Implementation boundary
Application: единая проекция фактических занятий с materialized precedence, действующими тренерами и attendance flags. Infrastructure: scoped чтение через существующий IAccessScopeService. Staff API и Bot сохраняют transport maps, сортировку и фильтры; Bot resolver проверяет точный ID и фактическую дату общей проекции. Cancelled write отклоняется существующим контрактом ошибки, чтение roster сохраняется. AttendanceService сохраняет проверку даты/статуса внутри своей транзакции. Python показывает строки и создаёт кнопки по backend canEditAttendance. См. ADR-0008.

## Existing limitation outside scope
Review обнаружил, что AttendanceService проверяет право Coach save через постоянный GroupTrainers, хотя чтение допускает exact substitution. TASK-199 не расширяет права и не обещает substitute-only save success; сохраняет существующий финальный authorization guard.
