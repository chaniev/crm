## Goal

Если группа обычно тренируется в зале А, но хотя бы один её слот или отдельное занятие ссылается на зал Б, попытка архивировать или удалить Б возвращает сотруднику причину отказа. Зал и история расписания сохраняются.

## Decisions and contracts

- Проверять сохранённые `TrainingGroups.HallId`, `LessonScheduleSlots.HallId` и `LessonOccurrences.HallId` по ID целевого зала. Учитывать все даты, статусы занятий и версии правил. Для серии достаточно ссылки из слота до появления экземпляра занятия. Проекция календаря и счётчик групп в справочнике отвечают на другие вопросы.
- Для `PUT /halls/{id}/archive` и `DELETE /halls/{id}` сохранить существующий ответ `400 ValidationProblemDetails` с ключом `errors.hall`. При ссылке из группы сохранить действующую причину. При ссылке только из расписания локализованное сообщение указывает действие и использование зала в расписании. Порядок авторизации и филиальной проверки задан [ADR-0003](/docs/architecture/adr/0003-administrator-client-branch-scope.md).
- Граница гарантии — момент выполнения команды над залом. Если расписание первым закрепило ссылку, операция над залом ждёт результата его транзакции. Если первым завершилось действие над свободным залом, последующая запись расписания подчиняется своим действующим правилам. Проверка восстановления зала, выбор зала при создании расписания и служебное восстановление посещений находятся вне задачи.

Зафиксировать исходный результат до правки обработчиков.
2. **Согласовать проверку и запись.** В двух командах `backend/src/GymCrm.Api/Auth/BranchEndpoints.cs` после допуска к действию и филиалу использовать одну транзакцию PostgreSQL с `Read Committed`. В Infrastructure сосредоточить локальную операцию чтения и блокировки зала: параметризованный `SELECT … FOR UPDATE` по его ID, затем отдельный запрос наличия привязок. После ожидания использовать актуальное состояние строки, при конкурентном удалении вернуть существующий ответ для отсутствующего зала. Обычный снимок до блокировки для принятия решения непригоден. Отдельный запрос нужен для видимости ссылки, которую другая транзакция успела зафиксировать за время ожидания. В InMemory использовать ту же проверку привязок. Успешное изменение и его аудит фиксируются вместе. Сохранить существующую семантику повторной архивации. [Пример блокировки строк в проекте](/backend/src/GymCrm.Infrastructure/Clients/ClientMembershipQueryStore.cs) · [Блокировки PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS) · [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)
3. **Довести причину отказа до сотрудника.** Добавить причины для двух действий в `BranchResources.cs` и `Resources/BranchResources.resx` рядом с сообщениями о группах. В `frontend/src/features/settings/BranchSettingsScreen.tsx` в обработчиках ошибок архивации и удаления брать сообщение поля `hall` из `ApiError.fieldErrors`, с текущим резервным сообщением. Транспорт и фасад уже передают поле. Переиспользовать существующую область ошибки и текущий порядок закрытия подтверждения удаления.
4. **Подтвердить результат.** Выполнить регрессии ниже. При закрытии задачи приложить результаты к REQ-BRN-001 и обновить журнал требований с учётом доказанного объёма.

## Regression specification

| Сценарий | Наблюдаемый результат |
|---|---|
| Единственная ссылка на Б — слот серии. Отдельно проверить слот завершённой версии без экземпляров занятий. | Обе операции возвращают 400 с причиной в `errors.hall`. Статус зала, слот и версия сохраняются. |
| Единственная ссылка на Б — разовое занятие. Варианты включают будущее, прошедшее и отменённое занятие. | Обе операции возвращают 400. Занятие сохраняет ID, статус, дату и зал. После отказов отсутствуют события успешной архивации и удаления. |
| Основной зал группы, свободный зал, зал чужого филиала, отсутствующий зал. | Для занятого группой зала сохраняется прежняя ошибка. Для свободного проверить архивацию/повтор/восстановление и удаление, число событий аудита. Для администратора чужого филиала — существующий отказ до выдачи сведений о привязках. Для разрешённой роли и отсутствующего ID — 404. |
| PostgreSQL, два соединения. Транзакция A записала первую ссылку на Б, но ещё открыта. В B вызвать каждый из двух HTTP-методов. | Синхронизировать фактическое ожидание блокировки с ограниченным тайм-аутом. После commit A — 400 и исходный зал. После rollback A — успешное действие над свободным залом и одно событие. Проверить состояние новым контекстом. Не использовать задержки как доказательство порядка. |
| В настройках зал с нулём групп. Главный тренер архивирует его или подтверждает удаление, сервер отвечает 400 с общей формулировкой в заголовке и конкретной причиной в `errors.hall`. | В области ошибки видна причина про расписание, зал остаётся в списке с прежним статусом. Сохранить проверки доступных действий ограниченной роли. |

**Ожидаемое исходное падение.** При единственной ссылке из расписания архивация сейчас может вернуть 200. InMemory допускает удаление, на PostgreSQL удаление доходит до ограничения FK вместо контролируемого ответа 400. UI берёт общий `error.message`. Реальные блокировки и FK подтверждать на PostgreSQL через существующую Testcontainers-фикстуру.

## Risks and stop conditions

- При 500, потере записи, ложном событии аудита или пропущенной конкурентной ссылке остановить интеграцию. Сохранить порядок операций и состояние БД для воспроизведения. Обработка любого `DbUpdateException` как «зал используется» скроет независимые ошибки записи.
- Схема и существующие данные совместимы. Откат кода возвращает прежнюю проверку. Если обнаружится необходимость исправлять уже архивные залы массово, менять FK или поведение назначения зала, вернуть это решение в планирование.
