## Goal
При одинаковой роли, данных и фильтрах доступный «Алексеев Алексей Дмитриевич»
находится по фамилии, фамилии с именем и полному ФИО после завершения загрузки.
Результат подтверждён реальным API на PostgreSQL и пользовательским сценарием.

## Decisions and contracts
- Восстановить принятый поиск в существующем списке. Введённое ФИО передаётся
  через `getClients` на сервер; фильтрация, ограничения доступа, подсчёт и
  пагинация остаются серверными. Форматы запросов, ответов и ошибок сохраняются.
- Сохранить действующие `query`, fallback `search` и отдельный `fullName`:
  при непустом `query` он приоритетнее `search`. Сейчас слова разделяются обычными
  пробелами, каждый непустой фрагмент должен совпасть с одной из частей имени;
  регистр и внешние/повторные обычные пробелы не должны мешать поиску.
  Это защита текущей семантики, а не новый алгоритм сопоставления.
- Телефон участвует в поиске только для HeadCoach, SuperAdministrator и
  Administrator в их текущей области доступа. Coach не находит клиента по
  номеру через `query`/`search`, а явный `phone` получает действующий `403`.
  Совпадение ФИО не раскрывает чужого клиента, его телефон или счётчики.
- Существующие поиск, debounce, очистка, фильтры, переход в карточку и возврат
  сохраняются. Смена запроса начинает выдачу с первой страницы; устаревший ответ
  не заменяет результат актуального запроса. Новый экран, состав данных и
  визуальный выбор отсутствуют. Для этой функциональной правки достаточно
  сравнения текущего интерфейса до/после по `docs/DESIGN_PROCESS.md`;
  гипотеза каркаса из аудита не является утверждённым редизайном.
- Миграции и преобразования данных не нужны в согласованных границах.
  Откат локального исправления возвращает прежний код без изменения данных.

## Implementation slices
1. **Воспроизводимый пример.** На одной версии и одном наборе данных выполнить
   три целевых запроса под HeadCoach с одинаковыми фильтрами. Зафиксировать
   введённую строку, декодированный URL, роль/область, страницу, завершённый
   HTTP-ответ с ID и счётчиками, DOM и отдельные поля имени. Проверить ту же
   строку прямым API-запросом. При необходимости сравнить кодовые точки пробелов,
   хранимое ФИО, версию/локаль PostgreSQL и выполняемый SQL. Не объявлять
   токенизацию причиной на основании одного скриншота. Сохранить обезличенное
   evidence рядом с задачей в новом `TASK-204-evidence/`.
2. **Регрессия и локальное исправление.** Добавить нижеописанные тесты; получить
   исходное падение на реально воспроизведённом дефекте. Исправить выявленное
   расхождение в серверном запросе, передаче параметров или состоянии загрузки,
   сохранив контракты выше. Не менять остальные слои только ради симметрии.
   Исходно проходящие сценарии оставить контрольными. Изменения вне этих
   контрактов подчиняются условиям остановки, а не выбору нового поведения.
3. **Подтверждение результата.** Повторить исходные запросы через UI и реальный
   PostgreSQL API, выполнить браузерные проверки и отдельный проход приёмки
   затронутого поиска через `crm-interface-audit`. Сравнить desktop/mobile
   до/после с существующим представлением; при UI-правке применить
   `crm-react-implementation` и визуальную приёмку `crm-interface-design`.
   Обновить карточку, REQ-CLI-008 и историю подтверждённого ограничения
   REQ-USR-001 вместе с CHANGELOG. Не объявлять широкие требования полностью
   реализованными на основании одной поисковой регрессии.

## Regression specification
### Automated tests to add or update
1. **PostgreSQL API, основной барьер.** На синтетических данных создать
   «Алексеев Алексей Дмитриевич», «Алексеев Алексей Александрович»,
   «Алексеев Андрей Дмитриевич», клиента с длинной фамилией и тёзку вне доступа.
   Для `query`, `search` и `fullName` проверить фамилию, два/три слова,
   смешанный регистр, внешние и повторные обычные пробелы. Сравнивать ID:
   два слова находят обоих Алексеев, полное ФИО отделяет нужного;
   фамилия плюс несовпадающее имя дают пустую выдачу. Проверить приоритет
   `query` над `search`, сочетание с фиксированными status/group-фильтрами,
   общий `totalCount`, отсутствие чужих агрегатов и поиск до пагинации
   на наборе больше размера страницы.
2. **Роли.** HeadCoach и SuperAdministrator находят разрешённых клиентов
   глобально, Administrator — в текущем филиале, Coach — в текущем разрешённом
   охвате. Для тёзки вне доступа проверять отсутствие ID/контактов и вклада
   в счётчики. Для Coach проверить запрет явного `phone`, пустой поиск номера
   через `query`/`search`; для трёх разрешённых ролей — успешный поиск телефона
   без расширения области. Существующие scope-тесты остаются контрольными.
3. **Frontend transport/state.** Проверять декодированный `query` из URL:
   кириллица и все слова сохраняются. При вводе со второй страницы запрос
   использует первую, очистка сохраняет остальные фильтры. Управляемыми
   отложенными ответами воспроизвести A → B и A → очистка; поздний ответ A
   не заменяет актуальные items/count/loading/error. При ошибке нового запроса
   доступен существующий повтор; повтор отправляет текущую строку.
4. **Playwright.** В новом spec: последовательный ввод трёх целевых строк,
   ожидание ответа с нужным `query`, сверка результатов, пустая выдача,
   очистка, ошибка/повтор, смена строки во время загрузки; открытие найденного
   клиента и возврат с сохранённым запросом/фильтрами. Проверить HeadCoach и
   ограниченный ответ Coach. При заглушках фиксировать ожидаемые ответы
   явно, не реализовывать поисковый алгоритм внутри mock; эти проверки
   доказывают transport/UI, серверное сопоставление доказывает пункт 1.

### Expected red evidence
- До исправления должен падать тест в найденном владельце дефекта:
  PostgreSQL API не возвращает ожидаемый ID либо UI отправляет другую строку /
  отображает результат неактуального ответа. Сохранить запрос, ожидаемые и
  фактические ID, вывод теста и версию в evidence без токенов и чужих данных.
- Если синтетические API-тесты уже зелёные, это не опровергает CLI-01.
  Сопоставить аудит и текущий runtime по данным, версии, фильтрам и завершению
  загрузки. Без воспроизведения и установленного различия не менять поисковый
  алгоритм и не заявлять исправление; искусственно падающий тест не нужен.

### Manual evidence
- Один сопоставимый проход исходного CLI-01 через настоящий backend: роль,
  версия, фильтры, три запроса/ответа и desktop/mobile снимки после загрузки;
  источник использует HeadCoach. Проверка mock-выдачи его не заменяет.
- Отдельный проход приёмки: фокус ввода/очистки/возврата, доступные имена,
  длинное ФИО, состояние ошибки и отсутствие визуального изменения композиции.
  Мобильные размеры и ограничения устройств — по единой mobile-acceptance
  матрице проекта; Safari, клавиатуру и физические устройства отмечать только
  при фактической проверке.

### Regression barrier
`ClientFullNameSearchPostgreSqlTests`: реальный список через API возвращает
точные доступные ID для трёх вариантов имени и исключает тёзку вне доступа;
браузерный spec закрепляет передачу этой строки и показ актуального ответа.

## Risks and stop conditions
- Если пример не воспроизводится и различие с аудитом не установлено,
  остановить функциональную правку, сохранить результаты диагностики и
  отметить нерешённое расхождение в задаче. Не подменять evidence предположением.
- Если необходимы изменение правил сопоставления, разрешений, UX, схемы,
  локали БД или исправление сохранённых данных, это выходит за локальное
  восстановление контракта: сделать план non-ready, вернуть задачу в
  планирование и закрыть новое решение в REQ/ADR до зависимых изменений.
- Не заменять PostgreSQL зелёным InMemory-тестом при недоступном Docker;
  явно оставить SQL-путь неподтверждённым. Не использовать миграции,
  пересоздание общей базы или правку персональных данных как диагностический шаг.
