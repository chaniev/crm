## Goal

Главный тренер открывает «Настройки → Администраторы → Группы посещений» и видит один и тот же назначенный филиал в строке сотрудника и в загруженном диалоге. Список правильно показывает филиал сразу после разрешённого сохранения сотрудника и после обновления страницы.

## Decisions and contracts

- Воспроизведение 21.11.2026 на `main` (`bf14d61`), в изолированном тестовом API с EF InMemory. Под ролью HeadCoach для одного Administrator три GET вернули 200. В списке и деталях `branchId` совпал с назначением, а `branchName` был `null`. В `attendance-groups` совпали и идентификатор, и имя. Оба первых запроса материализуют пользователя без связанного филиала, затем читают `user.Branch?.Name`. Диалог получает имя из явно загруженного филиала.
- Источник для списка и деталей — филиал сотрудника, включая сохранённую привязку к архивному филиалу. POST и PUT также возвращают `UserResponse`: панель сразу вставляет этот результат в список. Поля ответа должны описывать сохранённую запись на всех четырёх путях. Состав разрешённых действий, область посещений и счётчик назначений определяются действующим серверным контрактом.
- В обычной строке название отображается при достоверной паре ID и имени. Явное отсутствие назначения в полном ответе допускает «Филиал: не назначен». Пропущенные поля, пустое имя при наличии ID или противоречивая пара означают, что сведений недостаточно. В этой же строке показать, что данные филиала недоступны. Для SuperAdministrator сохранить «Доступ: все филиалы».
- В диалоге после успешного чтения использовать сведения `branch` ответа для открытого сотрудника. Явный `branch: null` означает отсутствие назначения, пропущенный или неполный `branch` — недоступные сведения. При загрузке и ошибке использовать существующие состояния диалога, не выводя неподтверждённое назначение. Сохранить место строки в существующей композиции. Это локальное исправление данных и текста в уже работающем сценарии.

## Implementation slices

1. В `AdministratorEndpoints.cs` загрузить связанный филиал вместе с пользователями в GET списка и GET по ID. Использовать существующий `ToResponse`. Для ответов создания и изменения получить актуальные данные филиала сохранённой записи перед формированием ответа. Не добавлять запрос на каждого сотрудника списка. Контроль этих путей описан ниже.
2. В клиенте Staff API сохранить различие между явным отсутствием назначения и неполными данными до точки отображения. Учесть поддерживаемое написание полей camelCase/PascalCase. В списке и диалоге убрать подстановку «не назначен» только по отсутствию имени. Сохранить штатное обновление строки из POST/PUT и существующие состояния загрузки и ошибки.
3. Зафиксировать регрессионные проверки, результаты сравнения и отдельного аудита изменённого сценария. Обновить затронутые записи REQ и `docs/requirements/CHANGELOG.md` со ссылкой на доказательства именно для TASK-206.

## Regression specification

### Automated tests to add or update

1. **API.** В xUnit на данных с двумя разными филиалами найти строку по ID сотрудника. Сопоставить ID и имя с назначенным филиалом в списке, деталях и ответе `attendance-groups`. Проверить SuperAdministrator без назначения, значение имени для сохранённого архивного филиала и существующие ограничения на чтение. Для разрешённых создания и редактирования проверить ответ сохранения и последующий GET. Проверки мутаций проводить только на изолированных тестовых данных.
2. **Клиентский контракт.** В Vitest проверить полную пару, явные `null`, отсутствующие ключи, пустое имя при наличии ID и неполный объект `branch` в ответе диалога. Различия должны переживать преобразование API-ответа.
3. **Интерфейс.** В Playwright сравнить имя в строке и диалоге одной записи. Удержать ответ диалога, затем вернуть ошибку и проверить текст во время ожидания и после ошибки. Проверить неполный успешный ответ, явное отсутствие назначения и строку глобальной роли. После штатного сохранения проверить название в списке до ручного обновления и после него. Для строки без разрешения `ManageAttendanceScope` проверить отсутствие действия.

### Expected red evidence

На исходной версии сравнение имён в GET списка и деталей падает на `null` при корректном `branchId`. Тест строки с ID без имени обнаруживает «не назначен». При задержке или ошибке диалога тот же текст появляется, если у исходной строки отсутствует имя. Сначала зафиксировать эти падения на публичных путях, затем вносить исправления. Сценарии действующих разрешений служат контролем сохранения поведения.

### Required validation

В проверочном контракте задачи перечислить затронутые сценарии Playwright для Chromium, `iphone-air-webkit` и `iphone-17-pro-max-webkit`. Сейчас фильтры двух WebKit-проектов не выбирают указанные файлы. Подключить затронутые тесты, проверить их обнаружение и фактический запуск на целевых размерах. Выполнить проверки задачи через harness.

### Manual evidence

Сравнить список и открытый диалог на одной учётной записи до и после исправления на настольном и узком экране. Отдельным проходом `crm-interface-audit` проверить читаемость длинного названия, сообщение об ошибке и возврат фокуса к вызвавшей кнопке.

### Regression barrier

Проверка трёх реальных HTTP-ответов на одной тестовой записи обнаруживает потерю имени на сервере. Браузерный сценарий с заведомо неполным ответом обнаруживает ложное «не назначен» на клиенте.
