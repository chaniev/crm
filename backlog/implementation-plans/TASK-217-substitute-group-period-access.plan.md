## Goal

Сотрудник назначает тренера на период. Заместитель в CRM и боте работает с группой в пределах своих прав. Отмена или окончание периода прекращает доступ по этому основанию уже при следующем обращении.

## Decisions and contracts

| Основание | Наблюдаемый результат |
|---|---|
| Постоянное назначение | Действуют обычные права тренера. Окончание периода сохраняет доступ, если он по-прежнему положен по постоянному назначению. Основной тренер продолжает работать с группой. |
| Новое периодное замещение | В обе граничные даты доступны группа, её клиенты, разрешённые данные и фотографии, расписание и посещения. Для записи должны одновременно выполняться три условия: период действует сейчас, фактическая дата занятия входит в него, дата разрешена обычным окном тренера. |
| Разовая замена | Доступ к выбранному занятию по действующему контракту, в том числе когда у группы два занятия за день. Назначение на одно занятие не открывает весь список клиентов и фото группы. |
| Прежняя запись о периоде | Остаётся доступной для просмотра сотрудникам с правом управления. Сама по себе не даёт полномочий даже при совпадении дат с сегодняшним днём. |

Вариант хранения, предлагаемые маршруты и выдача фото описаны в [ADR-0010](../../docs/architecture/adr/0010-substitute-group-period-access.md). Общая проекция фактических занятий и повторная проверка полномочий при сохранении следуют [ADR-0008](../../docs/architecture/adr/0008-shared-schedule-projection.md). Привязка права к группе сама по себе не меняет список тренеров, ведущих конкретное занятие.

## Decision evidence

- product: [Решения 21 и 22 ноября в карточке TASK-217](/backlog/risky/TASK-217-substitute-group-period-access.md) — owner: владелец CRM; decision: групповое замещение действует включительно, разовая замена остаётся отдельной, историческая запись не даёт прав, обе даты ограничивают запись посещений, переход для прежних разовых замен вне задачи.
- Независимое ревью прав, хранения и потребителей 22.11.2026 выявило, что один список ID групп потеряет основание права на запись, действующая команда перехода читает историческую таблицу, а Python-карточка не показывает снимок из метаданных. По результатам уточнены этапы и тесты ниже.
- Владелец 22.11.2026 исключил возврат к предыдущему выпуску из границ задачи и согласовал проверенный прототип управления периодами. [Запись решения](/backlog/risky/TASK-217-substitute-group-period-access.md)

## UX contract

В согласованном прототипе сотрудник управляет периодами в существующем разделе замещений карточки группы. Сотрудник выбирает тренера и обе даты, видит созданный период, может отменить его с подтверждением. Прежние записи явно обозначены как исторические. При ошибке пользователь может исправить форму с сохранённым вводом. Разовая замена остаётся в расписании у конкретного занятия. Для тренера действуют его обычные рабочие разделы. [Прототип](../mockups/TASK-217/index.html) · [Состояния и проверка](../mockups/TASK-217/README.md).

## Scope

- **Входит:** выдача и отмена нового периода, аудит, Staff API и обе клиентские поверхности, миграция с сохранением данных, проверка отзыва прав в открытой сессии.
- **За пределами:** перевод ранее оформленных разовых замен, правка исторических записей, начисления тренерам, изменение ролевых разрешений и загрузка или замена фотографий через Telegram.

## Implementation slices

1. **Выдача и отзыв периода.** Ввести EF-модель и добавочную миграцию по ADR. Реализовать Staff-операции получения списка, создания и отмены, используя существующие проверки группы, филиала, тренера, дат, CSRF и транзакционного аудита. Исторические строки и новые назначения адресуются раздельно. Проверить новую запись на чистой и сохранённой БД до подключения к правам.
2. **Текущий доступ к группе и клиенту.** Расширить обе операции `IEffectiveGroupAssignmentService` (список групп и проверка одной группы). Вычислять активный период по серверной деловой дате. Проверить сессию, рабочие списки групп, поиск/карточку клиента, разрешённые группы клиента и фотографии. Проверять права при каждом запросе даже с ранее выданной сессией. Управленческий раздел `/groups` сохраняет требование `ManageGroups`.
3. **Расписание и посещения.** Сохранить идентичность фактического занятия для recurring, разового и перенесённого занятия. Согласовать серверные `allowedActions` в Staff API и `canEditAttendance` в боте с датой занятия, основанием доступа и обычной политикой посещений. Проверять открытие состава по идентификатору и сохранение. В действующей транзакции записи использовать актуальные статус, дату и полномочия, включая случай отмены после открытия состава. Запрет правки не должен скрывать разрешённое чтение. Не распространять узкое основание отдельного занятия на соседние строки.
4. **Клиентские сценарии.** В веб-клиенте подключить новые типы и методы через фасад, использовать ответы о доступных действиях и сверить результат с выбранным прототипом. В боте подключить получение и показ фотографии с повторной авторизацией, включая устаревшую кнопку. Для недоступного или отсутствующего снимка сохранить возможность работы с разрешённой карточкой. Списки занятий, состав и сохранение продолжают использовать серверные решения.
5. **Сквозная приёмка.** На одном наборе данных пройти путь от назначения до отзыва в CRM и боте. Сравнить интерфейс с согласованным прототипом и провести отдельный аудит изменённого сценария. При завершении связать подтверждённые результаты с пятью требованиями и журналом требований.

## Regression specification

### Automated tests to add or update

| Проверка | Данные и ожидаемый результат |
|---|---|
| Выдача и аудит | Уполномоченный сотрудник создаёт и отменяет период в своём охвате. Тренер, сотрудник чужого филиала и запрос с историческим ID не меняют данные. Проверить однодневный период, неверный диапазон, пересечение новых назначений одной пары и атомарность операции: при сбое записи аудита изменение назначения не фиксируется. |
| Матрица доступа Staff + Bot | Ввести **отдельное новое назначение** в `GroupTrainerSubstitutionAccessMatrixTests`. Для 10–15 декабря проверить 9, 10, 15, 16 декабря и досрочную отмену из открытой сессии. Проверить ФИО, разрешённые поля, фактические байты фото, отсутствие телефона, контактов и сумм. Клиент в двух группах раскрывает только разрешённые группы. Основной тренер и другое независимое назначение сохраняют положительные проверки. |
| Запись и корректировка | При замещении 10–15 декабря: 10-го за 9-е отказ, 12-го за 10-е успех, 15-го за 12-е отказ по окну, 15-го за 13-е успех, 16-го за 15-е отказ. Проверить будущую дату и перенос через границу периода. Для Staff и Bot сравнить возможность действия с фактическим результатом сохранения. |
| Отзыв после открытия состава | Открыть состав, завершить отмену периода, затем сохранить из старого веб-экрана и диалога бота. Проверить отказ и отсутствие новых отметок, списания абонемента, аудита успешной записи и незавершённого резерва идемпотентности. Покрыть повтор команды бота по старой кнопке. |
| Разовая замена и история | Оставить действующие отрицательные тесты `GroupTrainerSubstitutionsApiTests` и `ScheduleLessonsApiTests`. В одной группе в один день назначить только вечернее занятие. Утреннее занятие и общий доступ к клиентам закрыты. Историческая запись и запуск команды перехода не должны выдавать периодные права. |
| PostgreSQL | Расширить `GroupTrainerSubstitutionPostgreSqlTests` и проверки `AttendanceTransitionServiceTests` для обновления БД с прежними записями: новый период на те же даты допустим, историческая строка не открывает группу, команда перехода обрабатывает только исторические строки. Прогнать реальные конкурирующие операции отмены/сохранения и создания пересекающихся периодов. |
| Потребители | Расширить `group-trainer-substitutions.spec.ts` и тест секции: создание, ошибка с сохранением ввода, отмена, прежняя история без действий, ограниченная роль. Для бота проверить фактическую доставку фото в личном чате обоими адаптерами, отсутствие фото, потерю доступа и отсутствие отправки после отказа. Проверить выбор занятий и устаревшие кнопки в `test_attendance_flow.py`. |

### Expected red evidence

Сначала ввести контрактные тесты нового периода и воспроизвести исходное расхождение. В текущей версии отсутствуют маршрут создания нового периода и путь чтения содержимого фото ботом. При отдельной фикстуре активного нового назначения групповой сервис читает только постоянные связи. Проверки исторических и разовых записей уже выражают полезные гарантии и должны проходить до и после изменения.

### Required validation

При подготовке проверки реализации включить `frontend/e2e/group-trainer-substitutions.spec.ts` и затронутые сценарии расписания/посещаемости в контракт для Chromium и двух целевых проектов iPhone WebKit. Для PostgreSQL получить результаты создания чистой БД и обновления БД с историческими записями. Для бота проверить внутренний HTTP-контракт и отображение результата независимо от доступности живого Telegram.

### Regression barrier

Одна сквозная фикстура с постоянным, периодным и разовым назначениями и исторической строкой должна различать все четыре основания в Staff API и боте, включая фактическое сохранение отметки и запрос фото после отзыва.

## Risks and stop conditions

Остановить затронутый этап при выявлении расширения прав по старым данным, потери данных при обновлении, различия между серверным запретом и успешной записью или необходимости менять согласованный способ выдачи фото. Вернуть существенное изменение контракта в ADR и план. Развёртывание не входит в этот план.
