## Goal
Корректная группа с начальным расписанием создаётся за одно нажатие;
ошибки исправляются в той же заполненной форме, с понятной причиной и фокусом.

## Decisions and contracts
- Принятое продуктовое направление: «Создать группу» сразу запускает проверку
  и создание; постоянного действия «Получить предпросмотр» или
  «Проверить и продолжить» нет. Серверные проверки, права и аудит сохраняются.
- Существующие POST preview/create и confirmation token позволяют реализовать
  одно действие без объединения endpoint и изменения транзакции.
- В текущем backend preview возвращает `warnings: []`. Новый поиск пересечений
  не включён; наличие типа warnings само по себе не доказывает его реализацию.
- Приведённые ниже UX/технические детали — конкретное предложение для завершения
  планирования, не запись об их утверждении владельцем.

## Proposed technical contract
1. **Варианты создания.** Добавить `GET /api/groups/options/create`, защищённый
   существующим правом управления группами. Ответ:
   `{ branches: [{ id, name, address }], halls: [{ id, branchId, name }] }`.
   Возвращать только активные филиалы в `GroupManagementScope` и активные залы
   этих филиалов. Администратор без области получает существующий 403
   `branch_scope_forbidden`; глобальная роль при отсутствии настроек — пустые массивы.
   Списки упорядочены по имени и ID. Общие `/api/branches` и `/api/halls` не меняются.
   Это узкое дополнение рядом с существующим `options/trainers`, без нового
   универсального механизма capabilities и без клиентского вычисления прав.
2. **Начальные значения.** Создание использует новый lookup; существующие
   group types/trainers остаются. Подставлять первый разрешённый филиал и его
   первый зал; при смене филиала очищать несовместимый зал по нынешнему правилу.
   При отсутствии вариантов объяснять предпосылку и запрещать отправку.
   Загрузка справочников имеет повтор; late response не перезаписывает ввод.
3. **Валидация.** При отсутствии slots вернуть ошибку расписания; не выводить
   из отсутствующего firstSlot ложное отсутствие hall/duration/startTime.
   Независимые name/branch/type/trainers проверяются обычными серверными правилами.
   При непустых slots сохраняются авторитет slot-данных, диапазоны, принадлежность
   зала, даты и mapping индексных ошибок на соответствующий день. Не принимать
   пустое расписание и не заменять backend-валидацию клиентскими доменными правилами.
4. **Отправка.** Зафиксировать один payload и одну попытку; блокировать повторный
   submit и изменение полей до завершения. Выполнить preview, затем create с тем
   же payload и полученным токеном. Не читать изменившиеся form values между запросами.
   Ошибка preview не запускает create; окончательный success только после create.
5. **Ошибки и повторы.** Привязанные ошибки рядом с полями; фокус/прокрутка на первое
   действительное невалидное поле, иначе на alert. 403 показывает серверную причину.
   Известные expired/stale/invalid token завершают попытку с сохранением ввода;
   новая явная попытка получает новый preview. Не добавлять автоматические retries.
   Сетевой/неопределённый отказ ПОСЛЕ отправки create не трактуется как доказанное
   отсутствие записи: состояние «Результат создания не подтверждён», без новой
   отправки, с переходом к проверке списка. Новая серверная idempotency/reconciliation
   система в scope не входит; нельзя обещать exactly-once между новыми token.
6. **Совместимость/откат.** Контракты preview/create, общий lookup и БД сохраняются;
   новый GET добавляется совместимо. Поставлять backend до frontend или совместно;
   новый frontend не работает со старым backend без нового GET и показывает recovery.
   Откат frontend возвращает прежний UX; откат backend выполняется после frontend.
   Созданные данные/аудит сохраняются, миграция и удаление данных не нужны.

## Proposed UX contract
Одна страница на существующих компонентах, без мастера и нового визуального направления.
Роль, устройство и начало/конец сценария совпадают с исходным проходом.

| Состояние | Видимое действие и результат | Ввод/фокус |
|---|---|---|
| Загрузка / сбой справочников | Индикатор / «Повторить» | Форма не отправляется до готовности |
| Готова | «Отменить» и основная «Создать группу» | Обычный ввод, отдельные времена дней |
| Проверка и запись | Одна кнопка «Создаём…», без второй стадии для пользователя | Поля и повторный submit заблокированы |
| Ошибка данных / доступа | Конкретная ошибка; «Создать группу» после исправления | Значения сохранены, фокус у причины |
| Непустые server warnings | Показать реальные сообщения; «Вернуться к форме» / «Создать всё равно» | Перед записью явный выбор; изменение полей сбрасывает token |
| Результат записи неизвестен | «Результат создания не подтверждён» и «Проверить список групп» | Не показывать ложный отказ/успех; не повторять create |
| Успех | Именное уведомление, возврат в существующий список | Dirty guard снят, прежний контекст списка сохраняется |
| Уход с изменённой формой | «Остаться» / «Выйти без сохранения» | Escape остаётся, закрытие возвращает фокус инициатору |

Предложение по уходу: защищать «К списку групп», «Отменить», смену раздела,
пароля и выход из аккаунта через существующий managedNavigation-подход импорта;
сохранить guard импорта. При pending уход не отменяет уже принятую сервером запись,
о чём сообщает диалог. Forced redirect при потере доступа не блокировать.
`beforeunload` подключать только для изменённой/ожидающей/неподтверждённой формы;
он не гарантирует защиту на iOS. Browser Back/Forward не покрыт этим механизмом
и остаётся решением до readiness, а не скрытым ограничением реализации.

Автоматические значения после загрузки — чистая база, не dirty. Не обещать
автосохранение, localStorage, восстановление после закрытия или между устройствами.
Сохранить текущие поля и live-сводку; убрать только отдельный preview-блок,
таймер подтверждения и технический текст об атомарности. Добавить понятные
пометки необязательного окончания и тренеров, диапазон длительности 1–180 минут.
Перегруппировка в новые секции и новая обзорная карточка не требуются для цели.

Сопоставление до/после: обычная отправка 2 нажатия → 1; время выполнения не измерено.
На mobile основное действие остаётся над навигацией; на desktop сохраняется
текущая форма. Проверять длинные ошибки и имена, focus/scroll и малую высоту.

## Implementation slices
1. **Регрессионный контракт.** После готовности плана добавить тесты ниже,

2. **Backend и typed client.** Реализовать scoped create-options и валидацию пустых
   slots; синхронно добавить types/endpoints/facade/client tests. Проверить старые
   lookup-потребители и неизменность server authorization/token/transaction.
3. **Одна отправка и recovery.** Реализовать последовательную цепочку, блокировки,
   field errors/403/unknown и утверждённое предупреждение; убрать обязательный preview UI.
4. **Защита формы.** Подключить согласованный guard, чистую базу после lookups,
   корректное снятие после success и cleanup при unmount. Изменения общего механизма
   ограничены подключением формы; настройки/импорт не теряют прежнюю защиту.
5. **Приёмка.** Пройти contract, сравнить с выбранным прототипом и отдельно проверить
   интерфейс. После проверенной интеграции обновить статусы требований и архивировать evidence.

## Regression specification
### Automated tests to add or update
- Backend options: глобальные роли/свой филиал администратора/нет филиала/Coach;
  активные и архивные филиалы/залы, пустые настройки. Общие lookup остаются общими.
- Backend validation: valid identity + empty slots даёт ошибку дней без ложных
  hall/duration/time; непустые slots сохраняют ошибки дат, зала, времени и диапазонов.
- Backend regression: foreign branch отказ; missing/stale/expired/used token;
  PostgreSQL concurrent execute одного token сохраняет ровно одну группу,
  начальную серию и аудит; ошибка записи не оставляет частичного результата.
- Frontend: одно нажатие отправляет preview→create с идентичным payload; pending
  не допускает edit/double-submit; preview failure не вызывает create; retry сохраняет ввод.
- Frontend: field aliases независимых дней; 403 с точной причиной; lookup error/retry
  и empty state; неизвестный результат create не отправляет новый create.
- Frontend: warnings требуют выбранного исключительного действия; отмена и изменение
  данных аннулируют подготовленное подтверждение; stale token возвращает к форме.
- Guard: заполнение→уход→остаться сохраняет поля; разрешённый уход вызывается один раз;
  untouched initial values/success не спрашивают; import guard и доступ не регрессируют.
- Browser: создание за одно нажатие, восстановление ошибок, роли/lookup, уход, клавиатура,
  длинные данные, mobile sticky action/no overflow и сохранение контекста списка.

### Expected red evidence
На исходной реализации нет create-options, нужен второй submit, wrong-branch выбран
по общему lookup, empty slots дают ложные hall/duration ошибки, «К списку» теряет ввод.
Эти новые проверки должны падать по указанным причинам. Существующие token/concurrency
и transaction проверки должны оставаться зелёными; искусственный red им не нужен.

### Required validation
При исполнении task contract включает backend и frontend плюс существующие suites:
`e2e/groups-registry.spec.ts`, `e2e/group-schedule-workflow.spec.ts` на `chromium`,
`iphone-air-webkit`, `iphone-17-pro-max-webkit`; `e2e/settings-client-import.spec.ts`
на `chromium` для потребителя общего guard. Проверки запускать корневым harness.
Обновить mocks старого двойного submit во всех затронутых unit/e2e сценариях,
не удаляя проверки самостоятельного редактора серий и назначений тренеров.

### Manual evidence
Сравнение с выбранным прототипом и отдельный аудит сценария; 390×844,
420×912, 440×956, 768/1440 и малая высота 912×420/956×440 соразмерно диалогу.
Физические Safari-панели, клавиатура и beforeunload на iPhone требуют отдельного
Simulator/device evidence; обычный resize не считается их приёмкой.
В contract не отмечать manual checks выполненными до фактического прохода.

### Regression barrier
Browser один click → один preview → один create → именное подтверждение и список,
вместе с backend тестами разрешённого филиала и отсутствия ложных ошибок пустых slots.

## Risks and stop conditions
- Не фильтровать общий справочник и не выводить правила доступа из роли на frontend.
- Не превращать token для одной попытки в обещание идемпотентности между новыми попытками.
- Если нужны автоматические повторы, новый mutation API, хранение черновика,
  history blocker или новый генератор предупреждений — вернуть план в подготовку.
- При пересечении файлов с отдельной TASK-201 API response boundaries согласовать
  владение/базу; её worktree обнаружен, но чужие изменения и статус не изменялись.
- Согласование прототипа и разрешение реализации нельзя подменить успешным линтером плана.
