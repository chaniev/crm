# TASK-192: Уточнить филиальный охват клиентов тренера

## Status
needs-clarification

## Requirements
- pending — определить, сохраняется ли доступ только к своим группам или требуется доступ ко всем клиентам филиала; определить смысл филиала тренера.

## Requirement context
- [REQ-CLI-009](../../docs/requirements/01-клиенты.md) — constrains
- [REQ-BRN-001](../../docs/requirements/09-филиалы-и-настройки.md) — constrains
- [REQ-USR-001](../../docs/requirements/05-пользователи-и-роли.md) — constrains

## Goal
Однозначно определить, каких клиентов видит тренер, не расширяя его доступ
на основании неоднозначного выражения «свой филиал».

## Context
REQ-CLI-009 допускает только клиентов назначенных групп и активных замещений,
а REQ-BRN-001 не предусматривает прямого филиала тренера: филиалы определяются
через группы. Это уже более узкое ограничение, чем «все клиенты филиала»;
назначения могут относиться к нескольким филиалам.

На main `8773321` Staff API, Bot API и photo service проверяют назначения
Coach. `ClientsApiTests`, `InternalBotApiTests` и
`GroupTrainerSubstitutionAccessMatrixTests` содержат соответствующие сценарии,
включая ограничения данных и замещения. В triage прочитан код тестов;
новый запуск и runtime-проверка не выполнялись.

## Scope
- Получить решение владельца: оставить текущие группы/замещения, расширить
  доступ до клиентов филиалов этих групп или вводить отдельный филиал тренера.
- Если выбран новый охват, до planning согласовать несколько филиалов,
  отсутствие групп, начало/окончание замещения и потерю последнего назначения.
- При изменении поведения обновить соответствующие REQ и CHANGELOG, определить
  матрицу Staff API/Internal Bot API и провести authorization review.
- Если текущий охват подтверждён, зафиксировать подтверждение без выдуманной
  реализации; отдельную регрессию заводить только при наличии evidence нарушения.

## Constraints
- До решения действуют принятые REQ-CLI-009 и REQ-BRN-001. Фраза из inbox
  сама по себе не разрешает всем тренерам видеть всех клиентов филиала.
- Скрытие телефонов, контактов и финансов тренеру сохраняется; чтение клиентов
  не предоставляет управление ими или посещениями чужих групп.
- [TASK-191](../risky/TASK-191-administrator-client-branch-access.md) исправляет
  администратора независимо от этого продуктового вопроса.

## Acceptance criteria
- [ ] Записано явное решение о группах/филиалах и его источник.
- [ ] Для нового охвата согласованы несколько филиалов, отсутствие назначений
  и активные замещения; требования приняты до подготовки реализации.
- [ ] После решения карточка закрыта подтверждением текущего поведения либо
  переведена в соответствующий статус с проверяемыми критериями новой модели.

## Test checklist
- [ ] После решения: свои/чужие группы одного филиала, группы в разных
  филиалах, клиент без группы, тренер без назначений, границы замещения.
- [ ] Список, карточка, фото и Bot API соблюдают выбранный охват и ролевой срез.

## AI safety
- Safe for autonomous implementation: no
- Risk level: high
- Reason: трактовка «филиала» как разрешения на всех его клиентов расширяет
  доступ к персональным данным; привязка к одному филиалу меняет модель назначений.
- Required review: при изменении охвата — продуктовая матрица и authorization
  review обоих API; для новой модели данных — применимый ADR workflow.
- Stop conditions: нет решения владельца либо предлагается заменить группы
  филиалом или раскрыть дополнительные поля без принятой редакции REQ.

## Clarification questions
- [ ] «Свой филиал» означает только клиентов назначенных групп и активных
  замещений, всех клиентов филиалов этих групп или отдельный назначенный филиал?
- [ ] Если охват расширяется: как работают несколько филиалов, отсутствие
  назначений и временное замещение? Этот вопрос не блокирует сохранение текущего правила.
