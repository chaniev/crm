## Goal
Из «Настройки → Импорт» выбрать XLSX, указать название существующей группы
и создать всех клиентов файла либо не создать ни одного при любой ошибке.

## Context
Последний запрос владельца заменяет отдельную CLI веб-интерфейсом CRM.
Название группы вводится отдельно, файл переименовывать не требуется.
REQ-CLI-010, REQ-BRN-002 и REQ-USR-001 отражают принятую целевую редакцию. Прочие правила
переноса сохранены; новый ADR и визуальный/интерактивный контракт ещё требуют
согласования. Реализация не начата. Анализ исходников от 15.11.2026 ниже
сохраняет силу для состава данных, но не для старой точки входа.

Оба файла содержат один лист `Клиенты` с одинаковыми заголовками A1:J1:
`Имя`, `Телефон`, `Комментарий к телефону`, `Email`, `Дата рождения`, `Пол`,
`Адрес`, `Статус`, `Баланс`, `Комментарий`.

## User role
Только Супер-администратор и Администратор. Супер-администратор предварительно
выбирает филиал; Администратор работает в своём текущем филиале без выбора.
Главный тренер и Тренер импортировать не могут; без филиала Администратору отказ.
Используется текущая сессия CRM, отдельный вход или пароль для импорта не нужны.

## Problem
Сотруднику нужен запуск переноса в CRM без отдельной консольной программы
и без соглашения об имени файла. В источнике нет филиала и группы, поэтому
группа задаётся в форме; формат клиентских данных и их ограничения сохранены.

## Scope
- Добавить вкладку «Импорт» в существующие настройки, выбор одного XLSX,
  обязательное поле «Название группы», запуск и отображение результата.
- Группа создана заранее. Все строки направляются в группу с указанным
  названием внутри целевого филиала. Супер-администратор предварительно
  выбирает филиал; для Администратора backend определяет его текущий филиал.
  Без филиала/при отсутствии группы/нескольких совпадениях в филиале — отказ.
- Имя файла произвольное и не участвует в поиске группы. Группа не создаётся.
- Backend проверяет файл и актуальные права, создаёт новые карточки и аудит
  атомарно. При ошибках интерфейс показывает причины и Excel-строки.
- Повторный осознанный импорт создаёт новые карточки; совпадения с прежними
  клиентами не обновляются, не объединяются и не подавляются.
- Mapping всех десяти столбцов нормативен ниже. V/Д остаются в исходном ФИО,
  дополнительные сведения и баланс идут в заметку; финансовых операций нет.
- UI не повторяет запрос автоматически при сетевом обрыве; неопределённый
  исход сверяется по итоговому аудиту. Доступ к аудиту не расширяется.
- CLI, бот-команда, schema changes, фоновые задания, deployment и реальный
  импорт предоставленных персональных данных вне scope этой подготовки.

## Field mapping
Основание: прямые решения пользователя от 15.11.2026 о телефонах,
сохранении сведений без поля карточки в заметке и обработке ФИО.

| Столбец XLSX | Результат переноса |
| --- | --- |
| Имя | Фамилия, имя, отчество; `V` и `Д`, включая `(Д)`, остаются в ФИО как в источнике, без переноса в заметку. Остальные пометки удаляются. Неоднозначные строки исправляются в источнике до импорта; до исправления — ошибка файла |
| Телефон | Первый номер — основной телефон, остальные — заметка; нормализация к `+7` применяется к обоим назначениям. Перед 10-значным номером с начальной `8` добавляется `+7` с сохранением всех десяти цифр; у 11-значного номера начальная `8` заменяется на `+7` |
| Комментарий к телефону | Заметка, с подписью источника |
| Email | Заметка, если заполнен |
| Дата рождения | Поле даты рождения; отсутствие значения допустимо |
| Пол | Заметка |
| Адрес | Заметка, если заполнен |
| Статус | Поле статуса; в обоих примерах все клиенты активны |
| Баланс | Заметка «Баланс из исходного файла» с исходным значением, включая ноль; без трактовки как долг, оплата или абонемент |
| Комментарий | Заметка, с подписью источника |

Итого в заметке: дополнительные телефоны, комментарий к телефону, Email,
пол, адрес, исходный баланс и общий комментарий. Пустые значения не добавляют
сведений. Пометки `V` и `Д`, включая `(Д)`, сохраняются в ФИО и не включаются
в заметку; остальные пометки удаляются по прежнему правилу.
Фрагменты `год` и отдельная цифра `8` в неоднозначных ФИО требуют исправления
исходных строк до импорта; автоматический перенос этих фрагментов в заметку
не выполняется.
Контактные лица не создаются из дополнительных номеров или свободного текста.
Принятое правило ошибки файла применяется и к превышению действующего лимита
заметки в 2000 символов; обрезка с потерей данных не разрешена.

## Constraints
- [REQ-CLI-001/003/005/006](../../docs/requirements/01-клиенты.md): данные клиента,
  контактные лица, заметка и дата рождения. [Текущий запрос](../../backend/src/GymCrm.Api/Auth/UpsertClientRequest.cs)
  содержит отдельные части ФИО, один телефон, филиал, дату рождения, заметку,
  контакты и группы; отдельных полей Email, пола, адреса и баланса в
  [Client](../../backend/src/GymCrm.Domain/Clients/Client.cs) нет.
- [Backend-валидация](../../backend/src/GymCrm.Api/Auth/ClientLifecycleRequestValidation.cs)
  требует телефон длиной не более 32 символов, хотя бы одну часть ФИО,
  существующий активный филиал и хотя бы одну группу этого филиала.
  Контактных лиц не более двух; для каждого нужны тип, имя и телефон.
  Заметка ограничена 2000 символами. Телефон сейчас только обрезается по краям;
  правила нормализации до `+7` или слияния клиентов не следует выдавать за существующие.
- [ClientsApiTests](../../backend/tests/GymCrm.Tests/ClientsApiTests.cs), сценарии
  `Client_create_validates_required_fields_contact_limit_and_groups` и
  `Client_create_requires_branch_and_rejects_group_from_another_branch`,
  подтверждают обязательность полей, групп и филиального соответствия.
- [ClientConfiguration](../../backend/src/GymCrm.Infrastructure/Persistence/Configurations/ClientConfiguration.cs)
  задаёт неуникальный индекс телефона. Один телефон не является установленным
  уникальным ключом клиента.
- [REQ-BRN-001](../../docs/requirements/09-филиалы-и-настройки.md),
  [REQ-USR-001](../../docs/requirements/05-пользователи-и-роли.md) и
  [REQ-AUD-001](../../docs/requirements/06-аудит.md) сохраняют филиальный охват,
  права и аудит. [Создание клиента](../../backend/src/GymCrm.Api/Auth/ClientLifecycleEndpoints.cs)
  выполняет проверки доступа и транзакционное сохранение данных с аудитом.
  Импорт не должен обходить эти backend-правила.
- [REQ-SUB-002/003/004/010](../../docs/requirements/03-абонементы-и-оплаты.md)
  описывают продажи, оплаты, возвраты и отчёты. Перенос `Баланс` в финансовые
  операции требует отдельного продуктового решения; его нельзя вывести из числа.
- Материальное решение о записи и восстановлении данных проходит
  архитектурный workflow до реализации. Разовая утилита сохраняет владение
  CRM-правилами на backend.

## AI safety
- Safe for autonomous implementation: no — требуется ready plan с принятыми
  ADR-0005 и визуальным/интерактивным контрактом новой вкладки.
- Risk level: high — массовая запись клиентов, назначения, права и аудит.
- Required review: предыдущая проверка backend atomicity/scope остаётся evidence;
  browser multipart/error/recovery и новый выбор группы требуют новой сверки.
- Stop conditions: неоднозначность вне принятого mapping; обход backend guards;
  частичная запись файла; автоматический replay mutation; новый материальный
  выбор вне согласованного ADR/UX. Реальные XLSX не исправлять автоматически.

Последующее подтверждение обработки ошибок:

> согласен в предложением по обработке ошибок

Принято предложенное правило: проверять весь файл до записи; при ошибках
показывать строки и причины и ничего не добавлять; после исправления
импортировать файл целиком. Результат записи файла — «всё или ничего»;
частичный импорт при сбое не допускается. Это не вводит сопоставления
с предыдущими импортами и не утверждает предложения по полям или выбору
между одноимёнными группами.
