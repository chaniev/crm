# TASK-079: Уточнить дату рождения в профиле клиента

## Status
needs-clarification

## Goal
Зафиксировать продуктовый и технический контракт даты рождения клиента, чтобы поле можно было безопасно добавить в профиль без выдумывания требований.

## Context
В inbox указано, что в профиле клиента нет даты рождения. В текущей модели `Client`, create/update request и details response отдельного поля даты рождения нет, поэтому это не только локальное отображение: реализация, вероятно, затронет хранение, API и формы клиента.

## User role
Администратор / главный тренер / тренер — доступ к полю не уточнён.

## Problem
Неясно, нужно ли только показывать уже существующие данные, добавить ввод и редактирование нового поля или использовать дату рождения в других сценариях. Не определены обязательность, правила валидации, доступ ролей и поведение существующих клиентов без даты.

## Scope
- Определить, где дата рождения вводится, редактируется и отображается.
- Определить, является ли поле обязательным или необязательным.
- Определить допустимые значения и backend validation semantics.
- Определить, какие роли могут видеть и изменять дату рождения.
- Определить поведение существующих клиентов, для которых дата неизвестна.
- После уточнения оценить изменение domain/persistence/API/frontend contracts и перевести задачу в `risky`.

## Out of scope
- Реализация поля до закрытия вопросов.
- Автоматический расчёт возрастной категории или изменение правил групп.
- Поздравления, уведомления и отдельные birthday-отчёты.
- Сбор иных персональных данных.

## Constraints
- Дата рождения является персональными данными; доступ и аудит изменений должны соответствовать backend-owned ролям и permissions.
- Дата должна иметь однозначную date-only семантику без зависимости от часового пояса.
- Изменение схемы БД, API-контрактов и consumers требует отдельного implementation plan и полной cross-layer проверки.
- Существующие клиенты без даты рождения не должны стать невалидными без явного решения о backfill.

## Acceptance criteria
- [ ] Зафиксированы экраны создания, редактирования и отображения даты рождения.
- [ ] Зафиксированы обязательность и поведение пустого значения.
- [ ] Зафиксированы допустимый диапазон, формат и backend validation errors.
- [ ] Зафиксированы права ролей на просмотр и изменение.
- [ ] Зафиксировано поведение существующих записей и необходимость миграции/backfill.
- [ ] После уточнения задача может быть переведена в `risky` с проверяемыми критериями реализации.

## Test checklist
- [ ] После уточнения определить backend tests для persistence, API validation, roles и audit.
- [ ] После уточнения определить frontend tests для create/edit/details и пустого значения.
- [ ] Отдельно проверить date-only сериализацию на границах часовых поясов.
