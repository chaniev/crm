# TASK-115: Определить адресность и одновременное действие абонементов

## Status
needs-clarification

## Goal
Определить модель, в которой один абонемент клиента может быть привязан к
нескольким группам, и однозначно зафиксировать охват занятий, пересечения,
attendance, списания, переносы и отчётность для такой связи.

## Context
В inbox связаны три симптома: при оформлении нельзя выбрать конкретное занятие, второй абонемент завершается ошибкой, а разовую тренировку нельзя добавить при действующем абонементе.

Текущий каталог принадлежит филиалу, `ClientMemberships` защищены ограничением непересекающихся периодов одного клиента, а разовый абонемент списывается через attendance. Поэтому второй активный абонемент и `SingleVisit` поверх действующего абонемента сейчас конфликтуют с backend-owned моделью, а не только с формой.

Продуктовые уточнения от 2026-08-19 разделяют обязательную адресность и фактический охват: у каждого абонемента должна быть связь с одной группой, но `Professional` предоставляет клиенту право посещать все группы всех филиалов независимо от этой связи. Группа `Professional` используется для отчётности.

Пересечение определяется по периоду действия и охвату. Для одной группы одновременно может действовать не более одного `Term` или `SingleVisit`; абонементы разных групп могут действовать параллельно. `Professional` нельзя совмещать по времени с любым другим абонементом, включая второй `Professional`, потому что он уже покрывает все группы.

Новая inbox-заметка от 2026-08-21 явно меняет базовую cardinality: один
абонемент может быть привязан к нескольким группам. Это отменяет готовность
предыдущей one-group модели к реализации и требует повторно определить все
зависимые правила.

## Superseded product decisions (до 2026-08-21)

Следующие решения сохранены как история предыдущей модели, но больше не
являются исполнимым контрактом и должны быть подтверждены или заменены после
уточнения multi-group cardinality.

- Каждый абонемент клиента, включая `Professional`, имеет ровно одну обязательную группу.
- `Term` и `SingleVisit` покрывают только свою группу; `Professional` покрывает все группы всех филиалов, а его группа является группой отчётности.
- Пересекающиеся `Term + Term`, `Term + SingleVisit` и `SingleVisit + SingleVisit` одной группы запрещены.
- Те же сочетания для разных групп разрешены.
- Пересекающиеся `Professional + Term` и `Professional + SingleVisit` запрещены независимо от группы и филиала.
- Одновременно у клиента может действовать только один `Professional`; пересечение двух `Professional` запрещено.
- При такой матрице для конкретного занятия не возникает выбора между несколькими подходящими абонементами: backend находит единственный действующий entitlement по группе занятия и дате либо действующий `Professional`.
- Продление по умолчанию наследует группу, но пользователь может выбрать другую; будущий непересекающийся абонемент той же группы разрешён.
- При переводе клиента в другую группу его действующий и все будущие абонементы прежней группы переносятся в новую группу.
- Перенос применяется с момента операции: прошлые посещения и отчёты сохраняют старую группу, новая группа используется только для событий после переноса.
- Продажа абонемента автоматически добавляет клиента в выбранную группу.
- Архивирование группы блокируется, пока все действующие абонементы не перенесены в другие группы.
- Будущие абонементы не блокируют архивирование группы и остаются без изменений привязанными к архивной группе.
- Ошибочно выбранную при продаже группу можно исправить изменением существующей записи абонемента.
- Для существующего абонемента без группы используется группа клиента. Если клиент состоит в нескольких группах, выбирается первая по алфавиту, а клиент удаляется из остальных групп.
- Если у клиента с существующим абонементом нет ни одной группы, его абонемент оставляется без изменений как legacy-исключение, но не даёт доступ и не участвует в attendance до ручного назначения группы.
- При отмене посещения списанный `SingleVisit` восстанавливается; календарного срока окончания у `SingleVisit` нет, он действует до использования.
- Возврат после перевода относится к актуальной группе абонемента на момент операции возврата.

## User role
Администратор / главный тренер; затронут также тренер при отметке посещения.

## Problem
Текущая карточка и план предполагают ровно одну группу на абонемент, а новая
заметка требует несколько групп. Без уточнений система не может однозначно
определить entitlement для занятия, overlap, списание `SingleVisit`, перенос,
архивирование группы и финансовую атрибуцию.

## Scope
- Уточнить cardinality и охват для `Term`, `SingleVisit` и `Professional`.
- Определить backend-owned правила eligibility и выбора entitlement для
  занятия, входящего в одну или несколько групп абонемента.
- Повторно определить overlap matrix для нескольких абонементов и
  пересекающихся наборов групп.
- Определить purchase/renew/correction/transfer/refund, group archive,
  historical attribution и legacy-data transition.
- После продуктового решения обновить backend contract, frontend/bot
  consumers, ProblemDetails, audit и test-first decomposition.

## Out of scope
- Выполнение существующего one-group implementation plan до закрытия новых
  clarification questions.
- Снятие overlap constraint только во frontend или без attendance allocation
  rules.
- Автоматический выбор «любого» абонемента или группы без явного backend
  contract.
- Изменение цен, скидок и возвратов, не требуемое итоговой multi-group моделью.

## Constraints
- Backend остаётся единственным источником membership, attendance, permissions, audit и validation semantics.
- Нельзя допустить двойное списание, скрытый выбор продажи или расхождение attendance и финансовой истории.
- Операции должны оставаться атомарными и идемпотентными.
- Contract/schema change требует обновить frontend, bot, tests и воспроизводимое initial DB state.
- Текущий `membership-overlap` можно менять только согласованно с новой
  multi-group overlap matrix и attendance allocation contract.

## Historical clarifications superseded by 2026-08-21

Все ответы ниже относятся к прежней модели «ровно одна группа» и сохранены
только для traceability. Они не закрывают текущие clarification questions.

- [x] К чему привязывается абонемент? Решение: к одной конкретной группе; связь обязательна также для `Professional`, но его охват распространяется на все группы.
- [x] Каков охват `Professional`? Решение: все группы всех филиалов; обязательная группа используется для отчётности; пересечение с `Term` или `SingleVisit` запрещено.
- [x] Какие пары абонементов могут действовать одновременно? Решение: пересечения одной группы запрещены, разных групп разрешены; `Professional` исключает параллельный обычный абонемент.
- [x] Разрешён ли `SingleVisit` при активном `Term`? Решение: для одной группы — нет, для разных групп — да.
- [x] Как выбирать абонемент при attendance? Решение: выбора не возникает; backend определяет единственный entitlement по группе занятия и дате либо действующий `Professional`.
- [x] Как работают продление и перевод? Решение: продление наследует группу с возможностью изменить её; будущие непересекающиеся абонементы разрешены; действующий абонемент переносится вместе с клиентом.
- [x] Как продажа и архивирование влияют на группы? Решение: продажа добавляет клиента в группу; архивирование блокируется до переноса всех действующих абонементов.
- [x] Как исправить ошибочную группу? Решение: изменить существующую запись абонемента.
- [x] Как назначить группу существующему абонементу? Решение: использовать группу клиента; при нескольких группах выбрать первую по алфавиту и удалить клиента из остальных.
- [x] Может ли один `Professional` пересекаться с другим `Professional`? Решение: нет; одновременно разрешён только один `Professional`.
- [x] Как отражать перенос между группами в истории? Решение: прошлые посещения и отчёты остаются в старой группе, новая применяется с момента переноса.
- [x] Какие абонементы переносить? Решение: действующий и все будущие абонементы прежней группы.
- [x] Что делать с существующим абонементом клиента без группы? Решение: ничего; оставить запись без изменений как legacy-исключение.
- [x] Блокируют ли будущие абонементы архивирование группы? Решение: нет.
- [x] Восстанавливать ли `SingleVisit` при отмене посещения и есть ли у него срок? Решение: восстанавливать; календарного срока окончания нет, `SingleVisit` действует до использования.
- [x] Как legacy-абонемент без группы участвует в доступе и attendance? Решение: блокируется до ручного назначения группы.
- [x] Что происходит с будущим абонементом после архивирования его группы? Решение: ничего; запись остаётся без изменений привязанной к архивной группе.
- [x] К какой группе относится возврат после перевода? Решение: к актуальной группе абонемента на момент возврата.
