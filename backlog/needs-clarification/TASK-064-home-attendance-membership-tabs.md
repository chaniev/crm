# TASK-064: Разделить главную на вкладки «Посещения» и «Абонементы»

## Status
needs-clarification

## Goal
Сделать главную компактным рабочим экраном, где сценарий отметки посещений по умолчанию не вытесняется контролем абонементов, а обе области доступны в отдельных permission-aware вкладках.

## Context
Текущая главная показывает контроль абонементов и список посещений в одной длинной области. Положительное состояние абонементов занимает значительную часть первого экрана и отодвигает основной сценарий тренера. Для новой композиции подготовлен интерактивный макет, а inbox содержит подробные desktop/mobile, accessibility, permissions и testing требования.

Задача пересекается с находящейся в реализации `TASK-059-merge-home-attendance`: та задача объединяет главную и посещения, удаляет отдельный маршрут `/attendance` и прямо исключает изменение attendance-семантики. Новая заметка меняет композиционное решение на вкладки и допускает изменение backend-контракта посещений, поэтому не может считаться простым дополнением к текущему плану без продуктового решения.

## User role
Администратор / главный тренер / тренер.

## Problem
На главной смешаны два независимых сценария. Большой блок абонементов ухудшает доступ к отметке посещений, состояния загрузки и ошибок имеют неясную область действия, а текущее boolean-представление посещения не позволяет честно показать одновременно `Не отмечено`, `Был` и `Не был`.

## Scope
- Убрать заголовок `Главная` из основной контентной области, сохранив название раздела в навигации.
- Разделить главную на вкладки `Посещения` и `Абонементы` с клавиатурной доступностью и видимым focus state.
- Показывать вкладки только по backend-provided permissions; не создавать frontend-only правила ролей и access scope.
- По умолчанию открывать `Посещения`, когда пользователю доступна отметка посещений; корректно отображать сценарий с одной доступной областью.
- Сохранять выбранные группу, дату и локальное состояние посещений при переключении, избегая ненужных повторных загрузок.
- Изолировать loading, error и empty состояния внутри соответствующей вкладки.
- На вкладке `Посещения` оставить контекст занятия, навигацию по дате, прогресс, список клиентов, явное управление отметкой, массовое действие и статус сохранения.
- На вкладке `Абонементы` показывать счётчик проблем, компактный список с причиной/сроком/оплатой либо компактное положительное состояние.
- Реализовать responsive-поведение без page-level horizontal scroll на ширинах 320, 390, 440, 768, 1440 и 1920 px.
- После продуктового решения о семантике синхронно обновить затронутые backend-модель/API/аудит и frontend-потребителей либо сохранить однозначный boolean-контракт.
- Реализовать безопасную массовую отметку через поддерживаемую backend batch-операцию без скрытого перезаписывания уже выставленных отсутствий.

## Out of scope
- Изменение правил оплаты и действия абонемента.
- Дублирование membership или attendance business rules во frontend.
- Переработка остальных экранов CRM.
- Смена Mantine или шрифта Onest.
- Несвязанный рефакторинг навигации и layout приложения.
- Офлайн-режим, требующий отдельной архитектурной проработки.

## Constraints
- Backend остаётся источником истины для permissions, access scope, membership и attendance semantics.
- До реализации визуального управления нужно выбрать целевую модель посещения: boolean либо три состояния.
- При трёхсостояний модели требуется определить начальные/существующие значения, сохранить уникальность по дате, группе и клиенту и обновить аудит и все потребители контракта.
- `Отметить всех` не должно незаметно перезаписывать уже выставленные отсутствия.
- Значение состояния не должно передаваться только цветом; touch target вкладок — не менее 44 px.
- Группа и дата на mobile остаются постоянным контекстом и не скрываются в общий drawer фильтров.
- Не смешивать эту работу с несвязанным рефакторингом.
- Реализацию выполнять в отдельной ветке от актуального `main` после прояснения вопросов.

## Acceptance criteria
- [ ] В основной области нет заголовка `Главная`, а навигационное название сохранено.
- [ ] Пользователь с обоими permissions видит вкладки `Посещения` и `Абонементы`; по умолчанию открыты `Посещения`.
- [ ] Недоступные по backend permissions вкладки не отображаются, а сценарий с одной доступной областью не имитирует вторую вкладку.
- [ ] `Посещения` содержит только выбор занятия и отметку посещений, а `Абонементы` — проблемных клиентов или компактное положительное состояние.
- [ ] Счётчик проблемных абонементов виден рядом с названием вкладки.
- [ ] Выбор группы и даты, прогресс и локальное состояние сохраняются при переключении без ненужной повторной загрузки.
- [ ] Семантика отметки однозначна: `не отмечено` не смешивается с `не был`.
- [ ] Ошибка сохранения конкретного клиента заметна и позволяет повторить действие.
- [ ] Массовая отметка имеет понятную область действия и подтверждение либо немедленную отмену и не перезаписывает отсутствия скрыто.
- [ ] На mobile группа и дата не скрыты в общий drawer, а действия остаются доступны одной рукой.
- [ ] На целевых ширинах нет page-level horizontal scroll, обрезания и перекрытия нижней навигацией.
- [ ] Вкладки и действия доступны с клавиатуры, имеют видимый focus state, а статусы различимы без опоры только на цвет.
