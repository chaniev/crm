## Goal

Если клиент утром был на занятии, а вечером его пропустил, история сначала возвращает вечернюю отметку, а серия пропусков начинается с вечернего занятия. Изменение графика группы и более позднее редактирование утренней отметки с сохранением её статуса дают тот же результат.

## Decisions and contracts

- Для отметки читать локальное время начала из `Attendance.LessonOccurrence.StartTime`. Дата — `Attendance.TrainingDate`. Время, зафиксированное у занятия, применяется независимо от возраста отметки. Отдельная обработка старых данных исключена владельцем.
- История сортируется по дате, времени занятия и ID отметки по убыванию. Сортировка выполняется после ограничения доступа и до постраничной выборки Staff API или ограничения в 20 записей у бота. В существующем поле Staff API `groupTrainingStartTime` возвращать фактическое время в формате `HH:mm`. В карточке бота строки различимы по статусу и идут в том же порядке. Форматы карточек веба и Telegram сохраняются.
- Для серии использовать тот же ключ по возрастанию. Для нового «Связались» сохранять дату, время и ID максимального события по этому ключу. При чтении подтверждения использовать записанную границу и действующее условие `MarkedAt > AcknowledgedAt`. Три новых явных пропуска после границы вновь создают причину. Форма ответа при других причинах и идемпотентность повторного действия заданы ADR-0009.
- Исправление затрагивает чтение и запись будущих подтверждений в существующие поля. Миграция не требуется. При откате вернуть предыдущую версию backend. Уже записанные отметки, подтверждения и аудит сохраняются.

В обработчике `contacted` выбрать последнюю отметку по историческому ключу и передать то же время в подтверждение и аудит. Переиспользовать действующий калькулятор и его правила для равного времени и поздних отметок.

## Regression specification

| Сценарий | Что проверить |
|---|---|
| Одна группа и дата, 10:00 «Был» и 18:00 «Не был». Одну отметку отправить через Staff API, другую через Bot API. Утреннюю изменить последней, сохранив итоговый статус «Был». Затем изменить время в расписании группы. | Полная история Staff API возвращает 18:00, затем 10:00 до и после изменения графика. Два запроса по одной строке дают те же отметки без дублей. В карточке Internal Bot API на этих данных первой идёт «Не был», следующей «Был». Для тренера соблюдается ограничение по доступным группам. |
| После утреннего посещения и вечернего пропуска добавить ещё два пропуска в следующие дни. Подобрать ID утренней и вечерней отметок так, чтобы сортировка только по ID меняла их местами. | В `GET /clients/attention` одна причина `missedTraining` со счётчиком 3. При обратной хронологии статусов («Не был» утром, «Был» вечером) остаются два новых пропуска и причина отсутствует. |
| В конце серии пропущены два занятия одной даты в 10:00 и 18:00. У утренней отметки больший ID. Нажать «Связались», сменить график, повторить команду. После контакта внести пропуски за 15:00 и 20:00 той же даты, затем ещё два за следующие дни. | В подтверждении и аудите зафиксированы вечерняя отметка и 18:00. После повтора одно подтверждение и одна запись аудита. Пропуск за 15:00 до границы, за 20:00 — первый после неё. Причина скрыта после второго нового пропуска и возвращается на третьем со счётчиком 3. |

**Ожидаемое падение на исходной версии.** Staff API отдаёт время группы для обеих строк. Staff API и бот внутри даты ставят первой последнюю отредактированную отметку. Во «Внимании» при одинаковом времени группы порядок определяет ID, а подтверждение записывает время группы. Задать в тесте отличное от 10:00 и 18:00 время группы и фиксированные ID, чтобы падение было воспроизводимым.

**Проверка исправления.** Помимо регрессий двух API выполнить существующие тесты калькулятора, частичной загрузки истории, области доступа тренера, подтверждения контакта при нескольких причинах, а также проверки потребителей истории в вебе и боте. Хотя бы один проход чтения двух занятий и записи подтверждения выполнить на PostgreSQL с реальными внешними ключами и серверной сортировкой.

## Risks and stop conditions

Если серия и команда выбирают разные последние события или чтение через связь исключает допустимую отметку из истории, приёмка не пройдена. Для ошибки фикстуры восстановить корректную связь в тесте. Если проблема воспроизводится на допустимой записи в действующей схеме и требует нового правила восстановления данных, остановить затронутую работу и вернуть её в планирование.
