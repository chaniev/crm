## Goal

Уполномоченный сотрудник задаёт временный пароль в существующей учётной записи. Получатель сохраняет логин, назначения и историю, входит с последним выданным паролем и устанавливает собственный до доступа к рабочим данным.

## Decisions and contracts

| Инициатор | Получатели | Область сброса |
|---|---|---|
| Главный тренер, Супер-администратор | Администратор, Тренер | Весь клуб |
| Администратор | Тренер | Есть хотя бы одно действующее основное назначение в группу своего филиала, включая случай с группами в двух филиалах |
| Тренер | — | Действие недоступно |

- Замещение на период, подмена на одном занятии, история назначений и разрешение администратора отмечать посещения в отдельной группе сами по себе права сброса не дают. У Администратора без филиала область пуста. Каталог тренеров по-прежнему охватывает весь клуб.
- Каждый успешный сброс отзывает сессии получателя на всех устройствах. После повторного сброса войти можно только с последним временным паролем. Ввод и личная передача временного пароля принадлежат инициатору. Ввод текущего и нового пароля получателем идёт через существующую обязательную смену.
- Контракт Staff API предусматривает отдельную команду в семействах тренеров и администраторов, признак действия `ResetPassword` в `allowedActions`, ответ об успехе без тела и серверную проверку на момент записи. Запрос, ответы, блокировки, правила временного пароля и совместимость cookie описаны в [ADR-0011](../../../docs/architecture/adr/0011-staff-password-reset.md).
- В пределах задачи находятся Staff API, веб-интерфейс, хранимое состояние восстановления и совместимость действующей блокировки Telegram. Восстановление привилегированных аккаунтов, генерация и рассылка паролей и новые требования к сложности остаются за пределами задачи.

## Implementation slices

1. **Полномочие и проекция действий.** Ввести в Application решение о сбросе для конкретной пары сотрудников. Сервер сверяет роль, филиал и основное назначение на текущую деловую дату. Проецировать это решение в списки, детали и ответы сохранения обоих семейств. Для списка тренеров получать назначения одним запросом или подзапросом. В команде заново проверить фактические права, в том числе после снятия назначения.
2. **Операция восстановления.** Расширить модель пользователя и добавить прямую EF-миграцию для сохраняемых БД. Реализовать обе команды поверх одной операции: существующая проверка CSRF, штатный хешер, обязательная смена, отзыв сессий и одна запись аудита в общей транзакции. Для типа события добавить русское название в словарь журнала и фильтров. Согласовать запись с конкурентной самостоятельной сменой пароля и сохранением карточки. Отключённая учётная запись сохраняет свой статус. Проверять версию учётных данных при выдаче и чтении cookie.
3. **Путь инициатора и получателя.** В типизированном клиенте и фасаде добавить запрос сброса. В разделе «Тренеры» и в «Настройки → Администраторы» открыть общий диалог для конкретного сотрудника по серверному действию. Сброс отправляется независимо от изменений профиля. После подтверждения удалить секрет из формы и обновить состояние сотрудника. Пока сброс не завершён, в обоих редакторах показывать обязательную смену включённой с пояснением, что снять её можно только установкой собственного пароля. При отзыве сессии защищённый запрос приводит к повторной проверке сессии и выходу из рабочего экрана. На отказ входа с неверным паролем и на потерю отдельного разрешения действует штатная обработка ошибок. Повторный вход ведёт на существующий экран обязательной смены.
4. **Сквозная приёмка.** Проверить оба входа в сброс, путь получателя и доступ связанного Telegram-пользователя на реальном backend. Сравнить интерфейс с принятым прототипом и отдельно провести аудит взаимодействия. Обновить реализацию REQ-USR-005, затронутую часть REQ-USR-002 и CHANGELOG по фактическому результату.

## Regression specification

| Проверка | Наблюдаемый результат |
|---|---|
| Матрица Staff API, параметризованные policy/API-тесты | Список, детали и ответ сохранения объявляют ровно те действия, которые разрешает команда. Проверить обе целевые роли, привилегированных получателей, попытку сброса себе, чужое семейство, отсутствие филиала и отсутствие групп. Глобальная видимость карточек тренеров сохранена. |
| Границы назначения | Основное назначение в нужном филиале даёт право в первый и последний включённые дни. Завтрашнее, истёкшее, в чужом филиале, периодное и разовое замещение по отдельности — отказ. В двух филиалах достаточно одного подходящего назначения. После снятия последнего назначения ранее загруженная карточка может показывать кнопку, но запись отклоняется. |
| Команда и аудит | Анонимный запрос, запрос без CSRF, отказ по области, неизвестный ID и ошибка поля не меняют пользователя. На успехе прежние ID, статус, привязки и история сохранены. Одна запись содержит инициатора, получателя, действие и время. Проверить отсутствие исходного секрета и хеша в HTTP-ответе, ошибках, old/new JSON и описании события. Ошибка записи аудита откатывает также хеш и отзыв сессий. |
| Два браузера получателя и браузер инициатора | После сброса обе прежние cookie отклоняются уже на первом защищённом запросе, у инициатора сессия сохраняется. При первом сбросе ответ не раскрывает совпадение с личным паролем. Повтор того же действующего временного пароля возвращает ошибку поля. Успешный повтор с другим значением аннулирует первый временный пароль. После входа со вторым разрешены штатные действия обязательной смены, прямые рабочие API блокируются. После собственной смены работает новый пароль, старые cookie остаются недействительными. |
| Состояние восстановления | Обычный PUT из карточки, открытой до сброса, не снимает обязательную смену. Конкурентная смена старого пароля не перезаписывает более новый сброс. Два сброса даже в одну миллисекунду различимы. Отдельно сохранить прежнюю семантику редактирования флага вне процедуры сброса. |
| Связанный бот | С прежней привязкой сотрудник получает существующий отказ `PasswordChangeRequired` до смены пароля, затем снова может выполнить разрешённое действие. |
| Веб-клиент | Проверить парсинг нового действия в обеих моделях. Доступ к редактированию без права сброса не показывает кнопку. Проверить поле временного пароля, запрет после открытия, неизвестный результат при потере ответа без автоматической отправки, возврат фокуса и сохранение контекста инициатора. В отозванной сессии черновик получателя не сохраняется и не появляется после нового входа. Запоздалый ответ от прежней сессии не завершает новую. |

### Точки регрессионного покрытия

- В xUnit расширить `UserRoleAuthorizationPolicyTests`, `UsersApiTests.AdministratorCoaches`, `AuthFlowTests` и `InternalBotApiTests`. Для конкурентных запросов и отката аудита использовать PostgreSQL по образцу `MutationAuditAtomicityPostgreSqlTests`.
- В Vitest расширить тесты клиентов `users` и `administrators`, `UserManagement.test.tsx`, `SettingsScreen.test.tsx` и проверку смены сессии. Сквозной Playwright проходит обе точки входа и обязательную смену получателя.

### Expected red evidence

В исходном коде оба семейства Staff API публикуют только чтение, создание и редактирование сотрудников. В выборке действий отсутствует `ResetPassword`, оба новых POST недоступны. На фронтенде исходный тест не находит действия. У обязательной смены, блокировки Bot API и проверки cookie уже есть реализация. Для них достаточно проверки после настоящего сброса без искусственного исходного падения.

### Required validation

- Включить в контракт задачи реальный PostgreSQL: чистый запуск и обновление с предыдущей схемы, прежняя активная сессия до первого сброса, обязательная смена после него, согласованная запись при конкуренции и при ошибке аудита.
- Включить Playwright для сценария восстановления на Chromium и двух целевых iPhone/WebKit. Использовать изолированные браузерные контексты. В отчётах, снимках и трассировках использовать только синтетические данные.
- Сопоставить мобильное и настольное состояния с прототипом. Отдельный проход `crm-interface-audit` охватывает клавиатуру, фокус, ошибки, отмену и повторный вход. Указать фактически проверенные условия Safari и экранной клавиатуры.

### Regression barrier

Главный сквозной тест начинается с двух открытых сессий тренера, выполняет два разрешённых сброса, проверяет отзыв обеих сессий, отказ предыдущему временному паролю и доступ к прежней учётной записи только после обязательной смены. Отдельная отрицательная ветка с замещением без основного назначения подтверждает, что попытка ничего не меняет.

## Risks and stop conditions

После первого успешного сброса запуск прежней версии backend нарушил бы отзыв сессий и защиту обязательной смены. При восстановлении сервиса сохранить обновлённую схему и совместимый обработчик по ADR-0011.

При несовпадении выданного действия с проверкой записи, восстановлении старой cookie или возможности снять обязательную смену обычным сохранением карточки выпуск заблокирован. Несовместимость схемы либо необходимость расширить согласованный охват возвращает план к владельцу до изменения зависимого кода.
