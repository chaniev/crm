## Goal
Корректный XLSX с пустыми телефонами импортируется целиком; соответствующие
новые клиенты получают `+79111111111`. Ошибка непустого номера по-прежнему
отклоняет весь файл без частичной записи.

## Decisions and contracts
- Единственная функциональная правка — `ClientImportMapping.Map`: проверять
  пустоту всей исходной ячейки `cells[1]` через `IsNullOrWhiteSpace` до
  разбиения по запятым и нормализации. Пустое поле даёт один основной номер
  `+79111111111`; непустое проходит существующий путь без изменения правил.
  Подстановка внутри `NormalizePhone` или после удаления дефисов недопустима:
  она превратила бы `-`, `,` и пустые элементы списка в допустимые номера.
- Reader уже представляет отсутствующую ячейку пустой строкой и пропускает
  целиком пустые строки. Его ошибки формул, типов ячеек и структуры XLSX
  остаются самостоятельными причинами отказа, даже при пустом результате чтения.
- Подставленный номер проходит обычную валидацию, запись и стандартный аудит
  клиента. Дополнительная запись о подстановке в заметке не вводится.
  Совпадение номера у нескольких строк не объединяет клиентов.
- Используется действующий [ADR-0005](/docs/architecture/adr/0005-settings-xlsx-client-import.md).
  Multipart, DTO, ProblemDetails, права, филиал, транзакция и recovery не меняются.
  Существующая форма показывает прежние success/error состояния; новых экранов,
  текстов, элементов управления или визуального направления нет.
- Миграция не нужна. Откат версии возвращает прежний отказ на пустое поле для
  будущих импортов; уже созданные клиенты и аудит сохраняются. Автоматическое
  удаление/исправление успешно импортированных данных не входит в задачу.

## Regression specification

### Automated tests to add or update
1. **Mapping.** Пустая строка, обычные пробелы, табуляция и неразрывный пробел
   дают точно `+79111111111`, без дополнительного телефона в заметке.
   `-`, `+`, `123`, `,`, `номер,`, `,номер` и `номер, ,номер` остаются ошибкой
   `phone`; в примерах списка использовать корректный номер для `номер`.
   Сохранить успешные случаи `8…`, `7…`, `+7…`, десяти цифр с начальной `8`
   и нескольких телефонов; не менять существующую нормализацию заполненных значений.
2. **Reader/API.** Непустая строка без XML-ячейки B получает подстановку;
   полностью пустая строка не создаёт клиента. Пустой результат ячейки с
   формулой или неподдерживаемым типом сохраняет ошибку reader и отказ всего
   файла. Пустой телефон плюс ошибочная дата сообщает только действительную
   ошибку даты. Для теста `All_errors_are_returned_with_excel_rows` заменить
   прежний пустой телефон на `123`, сохранив проверку двух ошибок в каждой строке.
3. **Старые синтетические профили.** Не переписывать их исходные пустые значения
   ради сохранения старого статуса «invalid». По текущим fixtures:
   `Rows(48, false)` теперь даёт 48 mapped / 0 invalid;
   `Rows(66, false)` — 62 mapped / 4 invalid строки (Excel 6, 32, 37, 46,
   ошибки ФИО). Телефоны в строках 7, 9, 26, 41, 62 больше не ошибки.
   `Rows(count, true)` сохраняет прежний полный успех. Это вывод чтения
   fixtures, который executor подтверждает тестом.
4. **PostgreSQL/API.** Смешанный файл с двумя пустыми телефонами и одним
   корректным создаёт три разных клиента, сохраняет точные номера, назначения
   и стандартный аудит; итоговый `createdCount` соответствует файлу. Проверять
   дельту, чтобы ранее созданные клиенты сохранялись без изменений.
   Пустой телефон плюс другая невалидная строка даёт нулевую дельту всей записи.
   В существующей матрице позднего отказа `SaveChanges`, `ClientCreated`,
   `ClientNoteChanged`, `ClientImportCompleted` использовать строки с подстановкой
   и подтвердить прежний rollback клиентов, назначений и аудита.
   Тест `Corrected_profiles_create_N_and_deliberate_repeat_creates_2N` должен
   использовать отдельный заведомо невалидный непустой номер для первого отказа:
   бывший 48-row invalid-профиль уже корректен. Повторный осознанный импорт
   по-прежнему создаёт отдельные карточки; не менять ожидания N/2N на случайные 3N.
5. **Обычное создание.** Сохранить existing
   `ClientsApiTests.Client_create_validates_required_fields_contact_limit_and_groups`,
   который проверяет наличие `errors.phone` при `POST /clients` с пустым телефоном.
   Дублирующий тест с той же защитой не нужен; общую валидацию не менять.
6. **Браузер.** Для SuperAdministrator и Administrator загрузить новый
   небольшой XLSX с пустыми/заполненным телефонами, дождаться успеха и сверить
   сохранённый номер через существующий client API в этой сессии.
   Отдельный XLSX с непустым `123` показывает ошибку строки и не создаёт клиентов.
   В существующем 66-invalid→66-corrected сценарии заменить ожидание
   «Строка 62 · Телефон» на существующую ошибку ФИО; не удалять проверку отказа.
   Остальные сценарии spec, включая запрещённые роли и recovery, сохраняются.

### Expected red evidence
Новые mapping/reader-success проверки падают из-за `phone / invalid_value`;
успешный API-сценарий возвращает 400 вместо 200, браузер показывает ошибки
вместо числа созданных клиентов. Старый 48-row профиль ещё даёт 47 mapped / 1 invalid,
66-row — 57 / 9. Существующие отказы заполненных номеров, запреты доступа и
обычного создания могут сразу быть green: искусственный red для них не требуется.

Каноническая проверка по diff плюс один task-specific browser suite через
существующий real-API/PostgreSQL host. Executor создаёт contract версии 1:

```json

  "task_id": "TASK-202",
  "expected_branch": "codex/TASK-202-import-empty-phone-default",
  "areas": ["backend", "frontend"],
  "playwright": [{
    "id": "frontend.e2e.client-import",
    "spec": "e2e/settings-client-import.spec.ts",
    "projects": ["chromium", "iphone-air-webkit", "iphone-17-pro-max-webkit"],
    "timeout_seconds": 1800

```

Для выполнения нужны Docker с PostgreSQL Testcontainers и установленные harness
browser dependencies. `import-runtime.mjs` запускает backend fixture с
`--no-build`, поэтому suite выполняется после канонической Release build;
оба слоя явно включены в contract. Не добавлять дублирующий filtered backend
suite как runtime smoke. Специальной ручной проверки нет: UI не изменяется,
новые сценарии автоматизированы. Browser projects не являются evidence
проверки физического iPhone; это ограничение указывается в итоговом отчёте.

### Regression barrier
Основной барьер — PostgreSQL import integration: корректный смешанный файл
сохраняет точный номер по умолчанию, а файл с любой оставшейся ошибкой или
поздним отказом записи/аудита не оставляет частичного результата. Browser suite
подтверждает доступность этого поведения из существующей формы.

## Risks and stop conditions
- Подстановка после нормализации расширит допустимые данные; ограничить её
  исходным пустым полем и отрицательными примерами выше.
- Старые fixtures с именем `invalid` меняют результат по принятому правилу.
  Сохранять исходные профили и разделить новый успех/действительные ошибки,
  не ослаблять assertions и не менять реальные файлы из `backlog/example`.
- Если нужны изменения API, общей обязательности телефона, уникальности,
  UI или транзакционной границы, остановить зависимую работу и вернуть план
  к согласованию; такие изменения не следуют из подстановки.
- Повторное обнаружение занятого ID/ветки либо другого владельца task-файлов
  требует разрешить конфликт до исполнения, без переиспользования чужой ветки.
