## Goal
Все frontend-экраны с фильтрами используют компактную, второстепенную по визуальному весу область фильтров, соответствующую требованиям из `docs/mockups/требования к области фильтра/filter_requirements.docx` и примеру `docs/mockups/требования к области фильтра/фильтры в журналах.png`.

## Context
В inbox зафиксировано требование модифицировать область фильтров на всех экранах по отдельному документу требований и PNG-макету фильтров в журналах. Документ задает высоту панели, расположение, состав основной строки, поведение дополнительных фильтров, авто-применение, сброс, сохранение фильтров, визуальный стиль, типографику и адаптивность.

## User role
администратор / тренер

## Problem
Фильтры на разных экранах могут занимать слишком много места, конкурировать с основным контентом и отличаться по поведению и визуальному стилю. Это снижает скорость работы с таблицами, списками, журналами, календарями и данными.

## Scope
- Найти все frontend-экраны, где есть область фильтров.
- Привести фильтры к одной горизонтальной панели над основным контентом.
- Ограничить desktop/tablet панель одной строкой, высотой 56 px и максимумом 64 px.
- Оставить в основной панели только ключевые фильтры: пользователь, действие, статус, дата, ключевой объект или их экранные аналоги.
- Перенести второстепенные фильтры в `Ещё фильтры` через popover/dropdown.
- Реализовать mobile-поведение через fullscreen bottom sheet.
- Привести размеры контролов, gap, border, radius, icon sizes, reset/save actions и text overflow к требованиям.
- Убрать служебные тексты о том, что фильтры применяются автоматически.
- Сохранить авто-применение фильтров после изменения значения без reload страницы.
- Добавить или обновить frontend regression coverage для основных экранов с фильтрами.

## Out of scope
- Изменение backend contracts.
- Изменение бизнес-правил фильтрации, ролей, permissions или validation semantics.
- Переработка таблиц, списков, журналов или календарей вне необходимой адаптации к новой области фильтров.
- Добавление новых фильтров, не описанных текущими пользовательскими сценариями.

## Constraints
- Следовать `frontend/AGENTS.md`: Mantine сохранить, CRM business logic не дублировать во frontend.
- При реализации значимого UX-изменения привлечь `ui-designer`; frontend-структуру вести через `react-specialist`.
- Если требование документа к шрифту `Inter` конфликтует с текущим frontend-правилом `Onest`, явно зафиксировать решение в implementation plan перед изменением типографики.
- Основной контент должен оставаться главным визуальным элементом экрана.
- На desktop/tablet не допускать wrap фильтров на вторую строку.
- Текст внутри фильтров должен использовать nowrap, overflow hidden и ellipsis.

## Acceptance criteria
- [ ] Все существующие frontend-экраны с фильтрами перечислены в implementation plan и либо обновлены, либо явно исключены с причиной.
- [ ] Область фильтров расположена непосредственно над основным контентом и занимает одну строку на desktop/tablet.
- [ ] Высота панели на desktop/tablet не превышает 64 px, целевое значение 56 px.
- [ ] В основной панели отображается не больше пяти ключевых фильтров.
- [ ] Второстепенные фильтры доступны через `Ещё фильтры`, popup не выше 480 px и около 320 px по ширине.
- [ ] На mobile фильтры открываются как fullscreen bottom sheet, а компактная панель не разваливает layout.
- [ ] `Сбросить` находится справа внутри панели, сохранение фильтров доступно через icon-button.
- [ ] Фильтры применяются автоматически после изменения значения, без текста `Фильтры применяются автоматически`.
- [ ] Визуальные параметры панели и контролов соответствуют требованиям: фон, border, radius, hover/active/focus states, icon size и text overflow.
- [ ] Основные пользовательские сценарии фильтрации проходят без reload страницы и без frontend-дублирования backend-правил.
