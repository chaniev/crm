## Goal
В карточке клиента видно рабочий комментарий, а также кто и когда изменил его последним.

## Context
Комментарий клиента уже реализован как рабочая заметка в TASK-023, но новая заметка требует явной атрибуции последнего изменения.

## User role
Администратор / тренер.

## Problem
Текущая заметка не даёт пользователю достаточной информации об авторе и времени последнего изменения.

## Scope
- Сохранить backend-owned идентификатор автора и время последнего изменения заметки.
- Вернуть безопасное отображаемое имя автора в контракте карточки клиента.
- Показать автора и дату/время рядом с заметкой.
- Зафиксировать audit event изменения заметки согласно существующим правилам.

## Out of scope
- История всех версий комментария.
- Несколько комментариев или обсуждение с ответами.
- Уведомления о комментарии.

## Constraints
- Не ломать существующее поле заметки из TASK-023.
- Backend владеет permissions, audit и validation semantics.
- Не раскрывать технические идентификаторы пользователя в UI.
- Метаданные заметки изменяются только при фактическом изменении нормализованного `Notes`; изменение других полей клиента продолжает фиксироваться существующим общим audit event клиента, но не меняет автора и время заметки.
- Использовать отдельные nullable-поля времени изменения заметки и идентификатора автора; не использовать общий `Client.UpdatedAt` как время изменения заметки.
- Для конкурентных изменений применяется `last-write-wins`; optimistic concurrency в этой задаче не добавляется.
- Идентификатор автора хранится только на backend. В UI-контракт возвращаются актуальное отображаемое имя пользователя и время изменения, без технического user id или login.
- Время формируется сервером и хранится как UTC `DateTimeOffset` с точностью до секунд; UI отображает локализованное время с точностью до минуты.

## Agreed semantics
- При создании клиента с непустой нормализованной заметкой автором считается создавший клиента пользователь, временем изменения — серверное время создания.
- При создании клиента без заметки метаданные заметки остаются `null`.
- Изменением заметки считаются переходы `null -> текст`, `текст -> другой текст` и `текст -> null` после существующей backend-нормализации.
- При очистке заметки метаданные автора и времени очищаются, а изменение фиксируется отдельным audit event.
- Редактирование ФИО, телефона, филиала, групп и других данных клиента не меняет метаданные заметки. Такие изменения по-прежнему фиксируются существующим общим событием изменения клиента.
- Для изменения заметки создается отдельный audit event; он возникает только при фактическом изменении нормализованного значения.
- Отображаемое имя автора читается из актуального `User.FullName`; snapshot имени на момент изменения не хранится.
- Заметку видит тренер только при наличии backend-подтвержденного доступа к клиенту через группу, в которой этот тренер назначен. Редактировать заметку могут только администратор и главный тренер.
- Legacy-записи не получают искусственную атрибуцию: существующий текст заметки сохраняется, а новые поля metadata остаются `null`. UI отображает такую заметку без автора и даты.
- Неатомарность сохранения клиента и audit осознанно принимается в этой задаче. Ошибка записи audit должна быть записана в структурированный серверный лог без текста заметки и других чувствительных данных; транзакционная связность остается вне scope.

## Acceptance criteria
- [ ] После фактического изменения нормализованной заметки сохраняются backend-owned идентификатор автора и серверное UTC-время с точностью до секунд.
- [ ] Создание клиента с заметкой сохраняет metadata создавшего пользователя; создание без заметки оставляет metadata пустой.
- [ ] Изменение любых других полей клиента не меняет metadata заметки и продолжает фиксироваться существующим общим audit event клиента.
- [ ] Очистка заметки очищает metadata и фиксируется как изменение заметки.
- [ ] Карточка показывает актуальное имя автора и локализованные дату/время с точностью до минуты, не возвращая в UI технический user id или login.
- [ ] Пустая заметка и legacy-заметка без metadata отображаются корректно; существующий текст legacy-заметки не изменяется миграцией.
- [ ] Изменение заметки фиксируется отдельным audit event только при фактическом изменении нормализованного значения.
- [ ] Тренер видит заметку только у доступного ему через назначенную группу клиента; редактирование разрешено только администратору и главному тренеру.
- [ ] Ошибка сохранения audit записывается в структурированный серверный лог без содержимого заметки и других чувствительных данных.

## Test checklist

- [ ] Проверить, что изменение ФИО, телефона, филиала и групп не меняет metadata заметки, но остается в общем audit клиента.

- [ ] Проверить, что API не раскрывает идентификатор и login автора заметки.
- [ ] Проверить UTC-значение контракта и отображение даты/времени в UI с точностью до минуты.
