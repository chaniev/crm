### REQ-SUB-001. Каталог абонементов филиала

**Статус:** реализовано

Каталог вариантов абонементов ведётся на уровне филиала: Администратор —
своего филиала, Главный тренер — всех. Вариант имеет название, цену и период
доступности. Цена неизменяема после создания; менять можно название и период
доступности; удаления нет — только вывод из обращения периодом. При продаже
видны только доступные на текущую дату варианты филиала клиента. Три
системных вида: `SingleVisit` (разовый), `Term` (на срок; длительность
задаётся индивидуально при назначении), `Professional` (профессиональный).

**Изменения:**

  о фиксированных типах разовый/месячный/годовой).

### REQ-SUB-002. Продажа абонемента

**Статус:** реализовано

Приобретение абонемента — сущность «продажа» с датой покупки и фактически
уплаченной суммой. Оформление поддерживает три сценария: по каталожной цене,
с индивидуальной суммой при выбранном варианте, только суммой без варианта.
Сохранённая сумма — единственный источник финансовых расчётов;
отображается происхождение суммы (каталог/вручную). У клиента максимум один
активный абонемент; продление — новая продажа, начинающаяся днём после
окончания текущего.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-036, TASK-070, TASK-077).

### REQ-SUB-003. Оплата

**Статус:** реализовано

Отдельный признак «оплачен/не оплачен» отсутствует: любое добавление
абонемента означает состоявшуюся оплату. Обязательна дата оплаты (по
умолчанию удобная, можно задним числом, нельзя в будущем). Сценарий
«отметить оплату позже» выведен из обращения. Предупреждения, доступ и
отчёты используют единый backend-контракт оплаченности.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-083; заменяет правило MVP-ТЗ о признаке
  оплаты и ручной отметке оплаты).

### REQ-SUB-004. Возвраты

**Статус:** реализовано

Возврат — отдельное событие с суммой и датой; допускается несколько частичных
возвратов, суммарно не больше суммы продажи; дата возврата не в будущем и не
раньше покупки; отмена возврата возможна без удаления. Сумма продажи при
возврате не уменьшается. Технические версии абонемента (исправление,
обновление оплаты, списание разового) продажами не являются.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-036).

### REQ-SUB-005. Срок действия

**Статус:** реализовано

Месячный срок: дата окончания — день перед тем же числом следующего месяца
(старт 10 июня → действует по 9 июля включительно); годовой — аналогично.
Дата окончания может корректироваться вручную ролями с правом управления
абонементом. Правила расчёта принадлежат backend; frontend формулу не
дублирует. Для разового абонемента срок не основной — действует признак
использования.

**Изменения:**

- 27.08.2026 — новая (источник: MVP-ТЗ §6.4, уточнено TASK-061).

### REQ-SUB-006. Целевые группы и пересечения

**Статус:** реализовано

Абонемент привязывается к упорядоченному набору целевых групп одного
филиала: Term и Professional — 1–5 групп, SingleVisit — ровно 1.
Professional сохраняет глобальный охват всех филиалов. Цена не зависит от
числа групп; первая группа — стабильная отчётная группа для финансовой
атрибуции. Пересекающиеся абонементы разрешены (второй абонемент, разовая
тренировка при действующем Term не блокируются); при отметке посещения
backend однозначно выбирает entitlement. SingleVisit списывается и
восстанавливается ровно один раз. Хранятся исторические snapshots групп.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-115; заменяет правило MVP-ТЗ «абонемент
  действует на все группы клиента»).

### REQ-SUB-007. Профессиональный абонемент

**Статус:** реализовано

Профессионал — клиент с действующим абонементом вида `Professional`: цена 0,
считается оплаченным, посещения безлимитны, действует пока включён. Выдать
может только Главный тренер; при назначении обязателен комментарий
(хранится в назначении абонемента). Профессионал не показывается как
должник и исключается из списков неоплаченных абонементов и из выручки
отчётов. Включение/отключение фиксируется в журнале. Отдельный признак
клиента «профессионал» не используется.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-027, TASK-070, TASK-041).

### REQ-SUB-008. Использование абонементов при посещении

**Статус:** реализовано

Term и Professional безлимитны в пределах срока. SingleVisit автоматически
списывается после одного отмеченного посещения «Был»; возврат отметки в
«Не отмечено» восстанавливает разовое посещение. Отметка посещения разрешена
независимо от актуальности абонемента; при проблеме (нет абонемента,
истёк, разовый использован) система показывает предупреждение, но не
блокирует отметку. Индикатор отсутствия оплаты отображается рядом с
клиентом и не блокирует отметку.

**Изменения:**

- 27.08.2026 — новая (источник: MVP-ТЗ §6.5, TASK-064, TASK-115).

### REQ-SUB-009. Комментарий продажи

**Статус:** реализовано

Комментарий привязан к конкретной продаже абонемента (не общий для клиента),
с автором и датой последнего изменения. Права чтения и изменения проверяет
backend; финансовые поля не затрагиваются.

### REQ-SUB-010. Финансовые отчёты

**Статус:** реализовано

Раздел «Финансы» (только Главный тренер). Показатели: валовая сумма продаж,
сумма возвратов, чистая сумма, количество проданных абонементов, количество
новых клиентов. Продажи считаются по дате покупки, возвраты — по дате
возврата (учитываются в периоде по дате возврата, даже если продажа вне
периода). Периоды: месяц/квартал/год и произвольный диапазон; фильтры по
филиалу и тренеру. Атрибуция филиала/группы/тренера — через исторические
периодные привязки на дату события; при нескольких группах/тренерах событие
дублируется в детализации, канонические итоги возвращаются отдельно
(frontend показывает предупреждение). «Нулевые» продажи Professional
учитываются количеством, но не выручкой. Все расчёты — backend.

**Изменения:**

- 27.08.2026 — новая (источник: TASK-025, TASK-026, TASK-036, TASK-037,
  TASK-038, TASK-108).

### REQ-SUB-011. История изменений абонемента

**Статус:** реализовано

Изменения абонемента сохраняются через версии записи с техническими
полями действия (`ValidFrom`/`ValidTo`, причина версии: продажа,
продление, исправление, обновление оплаты, списание разового) и
фиксируются в журнале действий. У клиента не более одной текущей версии.
