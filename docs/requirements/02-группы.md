### REQ-GRP-002. Клиенты и тренеры в группах

**Решение:** принято

**Реализация:** реализовано

Клиент может состоять в нескольких группах; группа содержит несколько
клиентов; у группы может быть несколько тренеров. Назначенный тренер
получает права отметки посещений в этой группе. Главный тренер может быть
назначен тренером любой активной группы. Архивация группы блокируется
действующими и будущими привязками абонементов к ней.


Дата окончания назначения тренера включается в период; однодневное назначение
допустимо. Календарь, посещения, бот и отчёты используют одинаковую границу.
Снятие текущего назначения обновляет текущий доступ тренера в той же транзакции.

### REQ-GRP-004. Календарь занятий

**Решение:** принято

**Реализация:** реализовано

Расписание — полноценный календарь конкретных занятий: серия занятий
(`LessonSeries`: дата старта, необязательная дата окончания, бессрочные
серии) с лениво материализуемыми занятиями (`LessonOccurrence`) со
стабильными идентификаторами. Поддерживаются несколько занятий группы в
один день, разовые занятия, перенос и изменение с тремя scope («только это»,
«это и будущие», «вся серия»), отмена и восстановление. Жизненный цикл
занятия: `Scheduled | Cancelled`. Отмена занятия с существующими отметками
посещений блокируется конфликтом. Точные пересечения занятий одной группы —
ошибка валидации; пересечения разных групп — неблокирующее предупреждение.

### REQ-GRP-007. Task-first представление расписания

**Решение:** принято

**Реализация:** частично

На экране расписания каждое занятие сохраняет отдельную идентичность, но
занятия дня группируются по точному временному интервалу. Карточка прежде всего
показывает данные для выбора занятия и разрешённую операцию посещаемости;
редкие и опасные изменения доступны через вторичную поверхность. Интерфейс
показывает нейтральное наличие или отсутствие отметок только из backend-данных
и сохраняет дату, фильтры и позицию при переходе в занятие и обратно.
В дневном представлении календарная дата видна рядом с днём недели и
обновляется вместе с ним при переключении; оба значения относятся к одной
выбранной дате, включая переходы месяца и года.

На mobile занятия внутри временной группы показываются компактными строками:
название группы, филиал, зал и тренер имеют приоритет над вторичными badges,
одновременно виден только один нейтральный attendance status. Операция
`Посещение` остаётся доступным одним нажатием, но повторяющиеся строки не
создают несколько конкурирующих filled-primary surfaces; изменение и редкие
действия доступны через `Ещё`. При `420 x 912` заполненный дневной список
показывает не менее четырёх полных строк и заголовок следующего временного
интервала без перекрытия bottom navigation.

**Границы и ограничения:**

- Представление не вводит собственные правила конфликтов, прав, просрочки,
  отмены, замещения или обязательности отметок.
- На поддерживаемых mobile и desktop размерах дата, навигация и основные
  действия остаются читаемыми без горизонтального переполнения.

**Связанные требования:** REQ-GRP-004, REQ-GRP-005, REQ-ATT-006, REQ-NFR-001

### REQ-GRP-008. Создание группы одним действием

**Решение:** принято

**Реализация:** не начато

Сотрудник с правом создания групп заполняет форму и нажимает «Создать группу».
Система проверяет данные и права в процессе выполнения операции и создаёт
группу вместе с начальным расписанием. Для корректного ввода не требуется
отдельное действие предварительной проверки или подтверждение неизменённых
данных. Неблокирующие предупреждения игнорируются: создание продолжается без
их показа и дополнительного подтверждения. Блокирующие ошибки показываются
и не позволяют создать группу. Успех показывается только после подтверждённого
сохранения.
Форма создания не содержит нижней сводки, повторяющей выбранные в полях
филиал, зал, тип, расписание, длительность и число тренеров.

При ошибках данные формы сохраняются; пользователь видит конкретную причину
и может исправить ввод. Повторное нажатие во время выполнения не запускает
ещё одну операцию создания. Серверные правила доступа, расписания и аудита
сохраняются.

Перед добровольным уходом с изменённой формы через действия приложения
пользователь получает предупреждение о потере ввода.
Выбор «Остаться» сохраняет форму, подтверждённый уход теряет введённые данные.
Уход во время создания разрешён после предупреждения, которое также объясняет:
уже отправленная операция может завершиться и создать группу после ухода.
Автоматические начальные значения сами по себе не требуют предупреждения;
после подтверждённого успеха предупреждение снимается.

Кнопки браузера, включая «Назад/Вперёд», работают без предупреждения и
блокировки со стороны формы. При таком уходе введённые данные теряются;
приложение не сохраняет и не восстанавливает черновик. Это относится и к уходу
во время создания: отправленная операция может завершиться после ухода,
но уход не запускает повторное создание.

Если после отправки создания результат невозможно подтвердить, система
не сообщает об успехе или доказанном отказе и не предлагает повторить создание
из этого состояния. Пользователь видит сообщение о неподтверждённом результате
и действие «Проверить список групп».

**Границы и ограничения:**

- Требование определяет одно пользовательское действие, а не число внутренних запросов.
- Не вводит автоматические повторы записи, автосохранение черновиков или новые права.
- Защита ограничена действиями приложения: для формы создания не добавляются
  блокировка истории браузера и предупреждение при закрытии/перезагрузке страницы.
  Принудительный выход при потере доступа не блокируется.
- Представление исключительных состояний и защиты ухода через приложение
  соответствует [согласованному прототипу A.2](../../backlog/mockups/TASK-203-group-create-single-action/README.md)
  без нижней дублирующей сводки.

**Связанные требования:** REQ-GRP-001, REQ-GRP-003, REQ-GRP-004, REQ-USR-001, REQ-AUD-001
