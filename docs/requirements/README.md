# Реестр требований Gym CRM

Этот каталог — единый источник истины о том, как система **должна** себя вести.
Требования описывают текущее и целевое поведение продукта, а не историю его
разработки. Реализованность — это отдельное поле карточки, а не способ понять
поведение системы.

Архивные снапшоты (`docs/archive/MVP-ТЗ.md`, `docs/archive/BOT-МЕССЕНДЖЕР-ТЗ.md`)
и реализованные задачи не являются источником требований. При расхождении
истинна актуальная карточка требования здесь. Первичное наполнение реестра
(27.08.2026) выполнено миграцией из этих ТЗ с уточнением по `backlog/done`.

## Формат карточки требования

Каждое требование — нумерованная карточка `### REQ-<ДОМЕН>-<NNN>` с заголовком,
статусом, текстом требования и историей изменений. Доменные коды:

`CLI` клиенты · `GRP` группы и занятия · `SUB` абонементы и финансы ·
`ATT` посещения · `USR` сотрудники и роли · `AUD` аудит · `BOT` бот ·
`BRN` филиалы и настройки · `ATTN` внимание · `CHAT` чат ·
`NFR` нефункциональные

Точные формулировки — в `_шаблон-требования.md`.

## Статусная модель

Продуктовое решение и состояние реализации хранятся раздельно:

```text
Решение: предложено → принято
                    ↘ отклонено

Реализация: не начато → частично → реализовано
```

- **Решение `предложено`** — требование сформулировано, но не одобрено и не
  разрешает переход задачи в implementation.
- **Решение `принято`** — требование одобрено. Явное решение пользователя в
  task-контексте может быть основанием сразу записать `принято`.
- **Решение `отклонено`** — требование отвергнуто; ID и история сохраняются.
- **Реализация `не начато`** — текущая принятая редакция ещё не реализована.
- **Реализация `частично`** — только часть текущей редакции подтверждена кодом
  и тестами либо task-ветка ещё не интегрирована в main.
- **Реализация `реализовано`** — текущая редакция подтверждена в main.

Оба поля меняются только вместе со ссылкой на задачу или plan, которые дали
решение или evidence. При новой редакции ранее реализованного требования его
текст становится текущей нормативной версией, решение остаётся `принято`, а
реализация временно становится `частично` или `не начато` до интеграции.

## Процесс изменения требований

1. Каждая активная задача содержит `## Requirements`. Поведенческая задача
   ссылается на существующий `REQ-*` или добавляет новую карточку. Техническая
   задача без изменения поведения использует `none` с конкретной причиной.
   Неразрешённое продуктовое решение использует `pending` только в
   `backlog/needs-clarification`.
2. В `tasks-ready` и `implementation` допустимы только требования с решением
   `принято`. Создание карточки со статусом `предложено` само по себе не делает
   задачу готовой.
3. Для отношения `changes` целевая нормативная редакция принимается и
   записывается в карточку до перехода в implementation; реализация текущей
   редакции становится `не начато` или `частично`. Для `implements` целевой
   текст уже принят и не меняется задачей.
4. Definition of done задачи включает обновление затронутых карточек и запись
   в `CHANGELOG.md`.
5. Требование обновляется **в той же задаче**, которая меняет поведение, —
   не отдельным «догоняющим» коммитом и не постфактум.
6. Нумерация не переиспользуется: отклоненная или замененная карточка
   сохраняет свой ID навсегда.

Формат task metadata:

```md
## Requirements
- REQ-BOT-006 — implements
- REQ-GRP-005 — changes
- REQ-NFR-001 — constrains
```

Допустимые отношения: `implements` — реализуется уже принятая редакция без
изменения её смысла; `changes` — меняется нормативное поведение;
`constrains` — требование ограничивает реализацию без изменения своей редакции;
`verifies` — задача только подтверждает уже требуемое поведение.

## Связь с другими артефактами

- `docs/MOBILE_UI_CONTRACT.md`, mockup-спеки, UX-контракты — уточняют
  требования для конкретных экранов и ссылаются на `REQ-*`; при конфликте
  первым является этот реестр.
- `backlog/**` — нормативная зависимость направлена от задачи к требованиям;
  audit history карточки содержит обратную ссылку на изменившую её задачу.
- Правила доступа и доменные правила, описанные здесь, реализуются только
  бекендом (см. корневой `AGENTS.md`).

## Миграционное исключение

Первичные записи от 27.08.2026 могут содержать текстовые ссылки `TASK-XXX` и
архивные ТЗ без Markdown-ссылки. Это одноразовое миграционное evidence. Все
последующие изменения решения, реализации или текста обязаны содержать рабочую
ссылку на TASK/plan и отдельную строку в `CHANGELOG.md`.

## Проверка

Из корня репозитория:

```bash
python3 scripts/validate_requirements.py
python3 scripts/validate_requirements.py --base origin/main
```

Первая команда проверяет структуру реестра и metadata активного backlog. Вторая
дополнительно требует совместное изменение `CHANGELOG.md`, если относительно
указанной базы менялись доменные requirement-файлы. Обе проверки выполняются в
GitHub Actions; diff-gate применяется к pull request.
