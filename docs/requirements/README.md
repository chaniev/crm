# Реестр требований Gym CRM

Этот каталог — единый источник истины о том, как система **должна** себя вести.
Требования описывают текущее и целевое поведение продукта, а не историю его
разработки. Реализованность — это пометка в статусе, а не способ понять
поведение системы.

Архивные снапшоты (`docs/archive/MVP-ТЗ.md`, `docs/archive/BOT-МЕССЕНДЖЕР-ТЗ.md`)
и реализованные задачи не являются источником требований. При расхождении
истинна актуальная карточка требования здесь.

## Формат карточки требования

Каждое требование — нумерованная карточка `### REQ-<ДОМЕН>-<NNN>` с заголовком,
статусом, текстом требования и историей изменений. Доменные коды:

`CLI` клиенты · `GRP` группы · `SUB` абонементы · `ATT` посещения ·
`USR` пользователи и роли · `AUD` аудит · `BOT` бот · `NFR` нефункциональные

Точные формулировки — в `_шаблон-требования.md`.

## Статусная модель

```
предложено → принято → реализовано → изменено
                ↘ отклонено
```

- **предложено** — требование сформулировано, но еще не одобрено.
- **принято** — одобрено, является обязательным для будущих задач.
- **реализовано** — принято и подтвержденно реализованным в main.
- **изменено** — реализовано, но есть более новая принятая редакция
  (в карточке хранится обе: действующая и предыдущая).
- **отклонено** — требование отвергнуто; карточка сохраняется для истории.

Статус меняется только вместе со ссылкой на задачу или план, которые его
изменили.

## Процесс изменения требований

1. Любая задача, меняющая поведение системы, ссылается на ID существующего
   требования (`REQ-*`) или добавляет новую карточку. Задача без ссылки на
   требование не готова к реализации.
2. Definition of done задачи включает обновление затронутых карточек и запись
   в `CHANGELOG.md`.
3. Требование обновляется **в той же задаче**, которая меняет поведение, —
   не отдельным «догоняющим» коммитом и не постфактум.
4. Нумерация не переиспользуется: отклоненная или замененная карточка
   сохраняет свой ID навсегда.

## Связь с другими артефактами

- `docs/MOBILE_UI_CONTRACT.md`, mockup-спеки, UX-контракты — уточняют
  требования для конкретных экранов и ссылаются на `REQ-*`; при конфликте
  первым является этот реестр.
- `backlog/**` — задачи ссылаются на требования, не наоборот.
- Правила доступа и доменные правила, описанные здесь, реализуются только
  бекендом (см. корневой `AGENTS.md`).
