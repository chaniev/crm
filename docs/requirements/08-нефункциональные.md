### REQ-NFR-001. Мобильность интерфейса

**Решение:** принято

**Реализация:** частично

Интерфейс автоматически адаптируется к мобильным устройствам; без
горизонтальной прокрутки страницы, с мобильным представлением таблиц,
доступностью основных действий без наведения, touch-friendly элементами,
одноколоночными формами на узких экранах. Экран посещений удобен для работы
одной рукой. Необязательные animations и continuous motion уменьшаются или
отключаются при `prefers-reduced-motion: reduce`; loading, pending и completion
остаются понятными без опоры только на motion. Общая типографика CRM использует
семантическую шкалу Onest; элементы формы остаются не меньше 16 CSS px на iPhone,
длинный русский текст переносится или обрезается только с восстановимым
доступом к полному значению, а сравниваемые числа используют табличные цифры
там, где выравнивание влияет на сканирование. Проверка на ширинах 390 px,
768 px, 1440 px. Детали —
`docs/MOBILE_UI_CONTRACT.md`, скилл `crm-mobile-first-ui`.
Повторяющиеся рабочие строки используют тон/границу без тени и радиус не более
16 px; focus-card сохраняет элевацию только для detail/auth и временных или
плавающих поверхностей. На мобильной границе focus/inner радиусы уменьшаются до
16/12 px без изменения плотности содержимого.

**Границы и ограничения:**

- Отдельные ограничения не зафиксированы; применяются условия из текста требования.

**Связанные требования:** нет

### REQ-NFR-005. Брендирование клуба

**Решение:** принято

**Реализация:** частично

Customer branding включает название клуба, primary/accent и
customer-specific neutral colors, auth background, logo и favicon. Primary
auth action использует customer primary color. Все цветовые роли экрана
авторизации берутся из semantic tokens дизайн-системы; локальная
несемантическая палитра экрана не поддерживается.

Исходный branding задаётся при деплое через валидируемую
runtime-конфигурацию и не требует customer-specific frontend
release. После деплоя branding можно изменить через раздел
«Настройки» в рамках его backend-owned permissions и audit-контракта.

**Границы и ограничения:**

- Functional status meaning, permissions, operation order, typography, density,
  spacing, responsive behavior and accessibility semantics do not change with
  customer branding.
- Arbitrary customer CSS and role-specific or dark themes are not supported.
- Unknown, invalid or broken configuration deterministically falls back to
  bundled defaults and must not block authentication.
- Public config does not accept arbitrary remote URLs, CSS or binary asset data.

**Связанные требования:** REQ-BRN-002, REQ-AUD-001

### REQ-NFR-007. Пользовательские тексты и ресурсы

**Решение:** принято

**Реализация:** частично

Все статические тексты, отображаемые пользователю во frontend, backend
ProblemDetails/validation surfaces и Telegram-боте, читаются из
layer-appropriate resource files или типизированных resource modules. Один
пользовательский смысл имеет явного владельца; consumers не копируют
backend-owned validation и domain semantics.

Machine-readable route paths, enum values, action/error codes, callback
payloads, telemetry-only messages и тестовые fixtures не являются
локализуемыми ресурсами. Механический перенос текста в resources сохраняет
видимый смысл и public contracts; изменение product copy требует отдельной
редакции связанного требования.

**Границы и ограничения:**

- Исторические persisted audit descriptions и production data не переписываются
  как побочный эффект resource extraction.
- Resource validation допускает документированный узкий allowlist для
  machine-readable и telemetry-only literals.
- Отсутствующий обязательный resource key обнаруживается тестом/build gate и не
  заменяется неявным пользовательским fallback-текстом из production logic.

**Связанные требования:** нет

**Изменения:**

  новая принятая карточка по явному inbox-решению; существующая частичная
  resource adoption сохраняется, полное покрытие вынесено в задачу.
