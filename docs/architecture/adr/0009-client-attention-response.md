# ADR-0009: Одна запись клиента в Staff API раздела «Внимание»

- **Статус:** Accepted (пользователь, владелец проекта, 2026-11-21)
- **Дата:** 2026-11-21
- **Автор / владелец:** владелец проекта Gym CRM

## Связанные требования

- [REQ-ATTN-001](../../requirements/10-внимание-и-чат.md) — implements

## Контекст

Список создаёт отдельную запись для каждого проблемного абонемента. Действие «Связались» адресовано клиенту и читает его состояние через `SingleOrDefault()` до и после записи. При двух продажах это нарушает ожидание единственности. Контракт прежней выдачи прямо проверяет `Attention_returns_one_stable_target_aware_item_per_membership` в [ClientsApiTests](../../../backend/tests/GymCrm.Tests/ClientsApiTests.cs).

## Критерии выбора

Один ответ должен идентифицировать клиента, сохранять принадлежность каждой причины к продаже и быть пригодным как для списка, так и для результата команды. Область доступа определяется сервером до формирования записи. Потребитель в репозитории — Staff frontend.

## Рассмотренные варианты

1. Группировать прежние записи на экране. Для чтения пришлось бы собирать сведения о клиенте и продажах повторно. Ошибку команды на сервере это сохраняет.
2. Ввести версию API для новой формы ответа и поддерживать старую выдачу по абонементам. Вариант позволяет обновлять потребителей независимо, но требует обслуживать две формы выдачи.
3. Обновить действующий Staff API вместе с интерфейсом. Одна проекция обслуживает чтение и команду. Цена — согласованное переключение и откат обеих частей.

## Решение

Принят вариант 3. `GET /clients/attention` возвращает массив записей с уникальным `clientId`. В записи остаются `fullName`, `phone`, `notes`, `telegramLink` и `reasons[]`. Единичное поле `membership` уходит. Каждая причина `expiredMembership` или `expiringMembership` содержит `membershipId`, `saleId`, `membershipName`, `behaviorKind`, `expirationDate`, `daysUntilExpiration` и упорядоченные `targetGroups` своей продажи. Серию представляет одна причина `missedTraining` с `missedCount`.

`POST /clients/{clientId}/attention/missed-training/contacted` возвращает ту же форму записи с оставшимися причинами (200) либо пустой ответ (204), если причин больше нет. Сервер по-прежнему вычисляет основания появления в списке, область доступа и порядок клиентов.

## Последствия

Две продажи с одинаковой датой или названием различимы по идентификаторам. Интерфейс получает все причины до звонка. Ранее загруженный интерфейс ожидает единственную сводку абонемента и не покажет полные сведения при несовпадении версий.

## Cross-layer impact

Обновить обе операции в backend, типы и преобразование ответов Staff API, публичные экспорты, панель «Внимание» и потребительские фикстуры в одной задаче. Бот использует Internal Bot API. Отдельный маршрут `/clients/expiring-memberships` сохраняет свой контракт. Правила доступа к клиентам заданы [ADR-0003](0003-administrator-client-branch-scope.md).

## Migration and rollback

Изменение касается проекции существующих записей. Миграция базы не нужна. Выпускать совместимые версии backend и frontend вместе, после переключения обновить открытую вкладку. Для отката вернуть предыдущую пару версий. Границы подтверждённых серий и аудит остаются в действующей схеме.

## Validation

Проверить один GET и два последовательных POST для клиента с двумя продажами и серией пропусков. Сопоставить ID, тарифы, даты и цели обеих причин в каждом ответе, единственность подтверждения и записи аудита. На клиенте проверить один набор действий и видимость обеих причин при возврате из команды. Проверки ролей, порядка и формата перечислены в [плане TASK-221](../../../backlog/implementation-plans/TASK-221-attention-one-row-per-client.plan.md).
