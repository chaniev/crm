# ADR-0010: Периодное основание доступа замещающего тренера

- **Статус:** Proposed
- **Дата:** 2026-11-22
- **Автор / владелец:** Codex / владелец проекта

## Связанные требования

- REQ-GRP-006, REQ-ATT-003 — changes
- REQ-CLI-004, REQ-CLI-009, REQ-GRP-005 — implements

## Контекст

Новое назначение должно открывать группу в пределах прав тренера. Старое периодное назначение может иметь те же группу, тренера и даты, при этом оно остаётся историческим. Третье основание, разовая замена, привязано к одному занятию. [Решения владельца в TASK-217](../../../backlog/risky/TASK-217-substitute-group-period-access.md).

Сейчас групповой сервис читает постоянные назначения. Staff API регистрирует только чтение прежних периодов. Календарь и бот используют одну проекцию фактических занятий. Команда обслуживания читает исторические периоды и может превращать их в замены на конкретных занятиях. [Сервис назначений](../../../backend/src/GymCrm.Infrastructure/Authorization/EffectiveGroupAssignmentService.cs) · [Маршруты прежних периодов](../../../backend/src/GymCrm.Api/Auth/GroupTrainerSubstitutionEndpoints.cs) · [Команда перехода](../../../backend/src/GymCrm.Infrastructure/Attendance/AttendanceTransitionService.cs) · [ADR-0008](0008-shared-schedule-projection.md).

## Критерии выбора

Сохранить данные при обновлении и откате. Исключить предоставление доступа историей, расширение разовой замены, изменение основных тренеров и финансовой атрибуции. Одно серверное решение о записи должно действовать и при показе доступных действий, и при сохранении отметок.

## Рассмотренные варианты

- **Признак вида записи в прежней таблице.** Позволяет переиспользовать модель и часть обработчиков. Потребует переделать ограничение пересечений и разделить записи в списке, в проверке прав и во всех операциях перехода. При возврате предыдущей сборки она прочитает новые строки как исторические. Запуск её команды перехода способен создать из них разовые замены.
- **Отдельная таблица новых периодов.** Требует новой модели EF, миграции и маршрутов. Источником всех новых прав становится явное назначение сотрудником. Старый код продолжает обрабатывать только знакомые ему записи. Старый и новый периоды могут совпадать по датам.

## Решение

Предлагается отдельная таблица новых периодов с группой, заместителем, включительными датами, автором и временем выдачи и отмены. Для одной пары «группа, заместитель» применить проверку диапазона и PostgreSQL exclusion constraint на пересечение неотменённых новых периодов по образцу прежнего ограничения. Правила выбора активного тренера, филиального охвата, обработки конфликтов и аудита использовать из существующих операций. Новый период не создаёт назначения основного тренера или замену на каждом занятии.

**Управление.** Предлагаемые Staff-маршруты под `/groups/{groupId}/trainer-substitution-periods` поддерживают GET списка, POST создания и POST `/{periodId}/cancel`. Создание принимает тренера и две даты. Список возвращает статус, возможности создания/отмены и причину недоступности. Идентичность сотрудника, право управления группой, филиал и CSRF проверяются сервером. Создание и отмена фиксируются вместе с аудитом. Исторический GET и операции в расписании сохраняют отдельные адреса и контракты. Отмена работает только для принадлежащего данной группе нового периода. Предлагается сохранить ранее применявшиеся правила: активная группа, допустимый активный тренер, начало не раньше текущего делового дня, конец не раньше начала. Отмена доступна для действующего или будущего периода. Проблемы валидации и пересечения возвращаются в принятом формате ProblemDetails. [Правила TASK-073](../../../backlog/done/2026-07-25/TASK-073-temporary-group-trainer-substitution.plan.md).

**Доступ.** В существующем сервисе назначений разделить две операции. Для просмотра группы и клиентов на текущую деловую дату использовать объединение постоянного назначения и действующего в этот день нового периода. Для записи по периоду проверять дополнительно фактическую дату занятия и общее окно записи. Параллельное постоянное назначение сохраняет собственные права. Разовая замена участвует только в существующей проверке конкретного занятия. Кнопки и серверная запись используют одинаковое решение. В транзакции сохранения повторно проверить полномочия с учётом актуальной даты и статуса занятия. Операцию отзыва нового периода упорядочить с записью посещений существующей блокировкой строки группы. [Транзакция посещений](../../../backend/src/GymCrm.Infrastructure/Attendance/AttendanceService.cs).

**Фото в боте.** Сейчас внутренний ответ содержит метаданные, а сценарий Python отправляет текст. Предлагается защищённый GET `/internal/bot/clients/{id}/photo` с сервисной аутентификацией, привязкой Telegram к активному сотруднику и повторной проверкой права чтения конкретного фото. В карточке клиента действие «Показать фото» запрашивает изображение и доставляет его в личный чат. Бот не использует путь хранилища как ссылку и не сохраняет файл или Telegram file ID для повторного показа. Отзыв блокирует новый запрос, в том числе из старой карточки. Уже доставленный снимок остаётся в переписке Telegram. Это последствие варианта следует учесть при согласовании.

## Последствия

В схеме остаются две таблицы периодов разного назначения. В интерфейсе новые периоды и прежние записи должны быть различимы даже при совпадении дат. Для общей пары тренер/группа совпадение с исторической строкой допустимо. Основные расходы — миграция с сохранением данных, проверка прав на всех путях к занятию и согласованная поставка backend, веб-клиента и бота.

## Cross-layer impact

- Backend владеет источником и сроком доступа, разрешёнными полями и содержимым фото. Глобальные роли и разрешения администратора филиала сохраняют свои основания.
- Frontend получает действия по периодам из нового Staff-контракта. Существующий редактор разовой замены и список прежних записей сохраняются.
- Bot получает права на конкретное занятие из общей проекции, повторно предъявляет идентичность при сохранении и при запросе фото. Оба поддерживаемых Telegram-адаптера должны отображать результат.

## Migration and rollback

Выпустить добавочную EF-миграцию и snapshot. Пустая таблица на существующей БД означает отсутствие новых выданных прав. Данные в старых периодах, занятиях, основных назначениях и аудите сохраняются. При откате вернуть согласованные версии приложений и оставить расширенную схему. Старые версии не предоставят доступ по новым периодам, записи и аудит останутся для восстановления. При повторном запуске новой версии доступ зависит от текущей даты и признака отмены. Откат приложения не требует удаления строк или применения разрушающего Down.

## Validation

Проверить чистую БД и обновление с исторической строкой на те же даты. Выполнить создание, пересекающиеся запросы, однодневный период и отмену на PostgreSQL. На тестовой сохранённой БД с новым периодом запустить прежнюю версию и команду перехода, затем вернуться на новую версию. Сверить обе истории, отсутствие добавочных разовых замен из нового периода и повторное применение правил доступа. Сценарии Staff API, бота и устаревших диалогов перечислены в [плане](../../../backlog/implementation-plans/TASK-217-substitute-group-period-access.plan.md).

## Open questions

Владельцу проекта предстоит согласовать предложенное хранение, откат и способ показа фото в Telegram. Продуктовые правила дат и совместимости подтверждены в TASK-217.
