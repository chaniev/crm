# ADR-0011: Сброс пароля сотрудника и отзыв его сессий

- **Статус:** Accepted (пользователь, владелец проекта, 2026-11-22)
- **Дата:** 2026-11-22
- **Автор / владелец:** Codex / владелец проекта

## Связанные требования

- [REQ-USR-005, REQ-USR-002, REQ-USR-001, REQ-USR-003](../../requirements/05-пользователи-и-роли.md) — восстановление доступа, управление карточкой, роли и вход.
- [REQ-BRN-001](../../requirements/09-филиалы-и-настройки.md), [REQ-AUD-001](../../requirements/06-аудит.md), [REQ-NFR-003](../../requirements/08-нефункциональные.md) — основание филиального права, журнал и защита учётных данных.

## Контекст

Карточка любого тренера доступна Администратору клуба для разрешённых правок. Сброс пароля требует отдельного разрешения на конкретного получателя. Владелец подтвердил, что филиальное право даёт только основное назначение. Периодное замещение предоставляет доступ к занятиям и клиентам, но не является основанием для сброса. [Модель ролей и восстановления доступа](../../requirements/05-пользователи-и-роли.md) · [Область замещений](0010-substitute-group-period-access.md).

Сейчас cookie содержит `UpdatedAt` с точностью до миллисекунды. При каждом аутентифицированном запросе middleware сверяет значение с БД и проверяет активность и `MustChangePassword`. В обоих семействах Staff API обычное редактирование присваивает этому флагу значение из PUT, в том числе при сохранении давно открытой формы. Обычная смена пароля проверяет текущий хеш до открытия транзакции. [Cookie](../../../backend/src/GymCrm.Api/Auth/AuthSessionSync.cs) · [Проверка запроса](../../../backend/src/GymCrm.Api/Auth/AuthenticatedUserMiddleware.cs) · [Редактирование сотрудника](../../../backend/src/GymCrm.Api/Auth/StaffManagementMutationService.cs) · [Смена пароля](../../../backend/src/GymCrm.Api/Auth/AuthEndpoints.cs).

## Критерии выбора

После фиксации сброса сервер отклоняет любой следующий защищённый запрос со старой cookie, включая запрос в ту же миллисекунду. Знание временного пароля даёт только возможность пройти штатную обязательную смену. Сбой записи в журнал должен сохранить прежний пароль и сессии. Обычные права на изменение карточки и существующие пользователи сохраняют прежнее поведение.

## Рассмотренные варианты

1. Обновлять только хеш, `MustChangePassword` и `UpdatedAt`. Это использует нынешнюю схему, но допускает совпадение версии cookie и снятие требования смены обычной правкой. Принудительная монотонность `UpdatedAt` потребовала бы одного правила для всех записей сотрудника и всё равно не различала бы причины установки флага.
2. Хранить у сотрудника версию учётных данных и отдельный признак незавершённого сброса. Middleware уже получает строку пользователя. Требуются два столбца и расширение cookie, но количество устройств не влияет на стоимость отзыва.
3. Хранить каждую сессию и отзывать строки по пользователю. Это даёт выборочный отзыв устройства, которого нет в задаче. Потребовались бы миграция действующих cookie, учёт истечения и очистка записей. Отдельную защиту обязательной смены всё равно пришлось бы добавить.

## Решение

Принят вариант 2.

**Действие на получателе.** `ResetPassword` включается в `allowedActions` при чтении списков, деталей и при формировании ответа создания/изменения по одной политике Application. На списке права рассчитываются набором. UI показывает действие только по этому значению. Команда проверяет разрешение заново. Для Главного тренера и Супер-администратора получателями служат только `Administrator` и `Coach`. Для активного Администратора нужен `Coach` с действующим основным назначением в группе его текущего филиала. Проверяется `GroupTrainerAssignments` по деловой дате и `TrainingGroup.BranchId`, с включительными `ValidFrom` и `ValidTo`. `GroupTrainers` отражает состав на день сохранения, а сервис effective assignments добавляет замещения. Каждый из них по отдельности даёт неверный ответ для этой операции. Администратор без филиала и тренер без подходящего назначения права не получают. Активность получателя сохраняется при сбросе. Для выключенной записи вход остаётся закрыт. [Периоды](0006-trainer-assignment-period-boundaries.md) · [Запись периода и проекции на день операции](../../../backend/src/GymCrm.Api/Auth/GroupTrainerAssignmentEndpoints.cs).

**Команда Staff API.** `POST /coaches/{id}/reset-password` и `POST /settings/administrators/{id}/reset-password` используют один обработчик операции со строгой проверкой семейства, аутентификацией и штатной CSRF-проверкой. В теле только `temporaryPassword`. Принимается вручную введённое значение с сохранением значащих пробелов. Отклонять отсутствующее, пустое или целиком пробельное значение. При первом сбросе допустимое значение принимается без проверки совпадения с личным паролем сотрудника: различие в ответах позволило бы проверять догадки о чужом пароле без записи сброса в журнале. Только при повторном сбросе с `PasswordResetPending = true` проверяется хеш предыдущего временного пароля под блокировкой получателя. Совпадающее значение возвращает ошибку поля, успешный повтор заменяет предыдущий временный пароль. Отказ по значению — `400` с ошибкой у `temporaryPassword` без самого значения. История паролей не нужна.

Успех — `204` с пустым телом. Анонимный запрос — `401`, невалидный CSRF — существующий `400`. Для недопустимой роли инициатора — `403 staff_management_forbidden` до поиска по ID. Для отсутствующей записи или несовпадения семейства — `404 staff_not_found`. В доступном семействе применяются `403 staff_target_forbidden` для защищённой роли и `403 branch_scope_forbidden` при отсутствии назначения в филиале. Сообщения, тела ответов, структурированные логи и аудит не содержат введённого значения или хеша. Полная сериализация запроса запрещена. [Отказы Staff API](../../../backend/src/GymCrm.Api/Auth/StaffProblemDetails.cs) · [CSRF](../../../backend/src/GymCrm.Api/Auth/AuthCsrfValidation.cs).

**Отзыв и обязательная смена.** Добавить к `Users` nullable `CredentialVersion` (UUID) и `PasswordResetPending` с начальным `false`. Ограничение CHECK требует `MustChangePassword = true` и версию при установленном `PasswordResetPending`. Это защищает также потребителей, которые читают действующий флаг напрямую. Каждый успешный сброс устанавливает новую случайную версию, хеш через `IPasswordHashService`, оба флага (`MustChangePassword` и `PasswordResetPending`) в `true` и обновляет `UpdatedAt`. В той же транзакции добавляется одна запись аудита `PasswordReset` с инициатором, ID получателя и временем. Пароль существует в открытом виде только во вводе и при обработке запроса. Не перевыпускать cookie инициатора или получателя при сбросе. Проверять `CredentialVersion` как дополнительный защищённый claim, продолжая сравнение `UpdatedAt`. Отсутствующий claim соответствует только `NULL` в БД. После первого сброса версия никогда не возвращается в `NULL`.

При `PasswordResetPending` оба PUT сохраняют разрешённые изменения карточки с эффективным `MustChangePassword = true` даже при устаревшем `false` из формы. Возвращать доступным читателям карточки `passwordResetPending` как признак только для чтения, чтобы объяснить заблокированный переключатель. Вне сброса флаг редактируется по действующему контракту. Единственный путь завершения восстановления — успешная штатная `/auth/change-password` с действующим временным паролем и отличающимся новым. Смена очищает оба флага, ротирует `CredentialVersion` для учётной записи с версией и выдаёт cookie только после фиксации. Старые сессии останутся недействительными и после этой смены. Бот уже проверяет серверный `MustChangePassword` по привязанной идентичности. [Существующая проверка Bot API](../../../backend/src/GymCrm.Infrastructure/Bot/BotApiService.cs).

**Граница фиксации.** Последовательные и пересекающиеся сбросы упорядочиваются блокировкой строки получателя в транзакции. В `/auth/change-password` перенести чтение и проверку текущего пароля под ту же блокировку и сверять версию предъявленной сессии с перечитанной записью. Это закрывает случай, когда начатая раньше смена перезаписывает уже выданный временный пароль. При входе проверять пароль и выдавать claims из одной версии прочитанной записи. Устаревшая сессия завершает следующий защищённый запрос с `401`, `/auth/session` возвращает анонимный результат. Запрос, прошедший авторизацию до фиксации, не считается новым запросом после сброса.

В команде сброса повторно проверить сессию, активность, роль и филиал инициатора и роль получателя под блокировками соответствующих строк. Для филиального разрешения удержать строку группы, дающей право, до фиксации и после захвата повторно проверить её филиал и период основного назначения по текущей деловой дате. Обе рабочие операции, способные убрать основание (изменение группы и изменение назначений), записывают ту же строку группы в своих транзакциях. При устаревшей подсказке из списка проверка завершается отказом без записи секрета и аудита. Соблюдать порядок блокировок существующих путей (пользователи в стабильном порядке, затем группа). При ошибке записи откатывается вся команда. [Изменение назначений](../../../backend/src/GymCrm.Api/Auth/GroupTrainerAssignmentEndpoints.cs) · [Изменение группы](../../../backend/src/GymCrm.Api/Auth/GroupEndpoints.cs).

## Последствия

Восстановление сохраняет ID, логин, активность, назначения, историю и привязку мессенджера. Администратор уже может назначать тренера в группу своего филиала. Как только такое основное назначение действует, оно удовлетворяет принятому условию сброса независимо от автора назначения. Наряду с записью сброса сохраняется существующий аудит назначения. Платой за точный отзыв являются миграция и согласованное изменение двух путей записи пароля и обеих форм карточки.

## Cross-layer impact

Backend владеет проверкой ролей, назначений, флагов, cookie и атомарностью. Frontend расширяет типы, общую обработку действий и оба семейства API. После `204` перечитывает данные целевой записи. После `401` защищённого запроса подтверждает потерю сессии через `/auth/session` и возвращает пользователя на вход. При потере ответа на POST автоматический повтор недопустим: результат мог уже зафиксироваться. Для получателя используется существующий экран обязательной смены. Во время восстановления прежний диалог Telegram получает существующий отказ API о необходимости сменить пароль. Изменение схемы сообщений или идентичности бота не требуется. [Типы](../../../frontend/src/lib/api/types.ts) · [Разбор действий](../../../frontend/src/lib/api/users.ts) · [Экран смены пароля](../../../frontend/src/app/AuthStages.tsx).

## Migration and rollback

Добавочная EF-миграция и snapshot, без пересоздания `Users` и изменения существующих хешей, флагов или дат. Для существующих записей и обычного создания применяются `NULL/false`, старые cookie продолжают работать по прежним правилам. Разрешить вызовы команды сброса только после обновления схемы и переключения всего трафика на совместимый backend, затем обновить UI. Старый процесс не должен обслуживать запросы после первого сброса, поскольку он игнорирует версию и позволяет снять требование смены. До использования нового состояния допустим возврат старого приложения на расширенной схеме. После первого сброса восстанавливать сервис совместимой версией с сохранением обеих проверок и выпущенных версий. Удаление столбцов, восстановление старых хешей и возврат старого обработчика обращают отзыв. Обычный bootstrap создаёт только отсутствующую запись. Отдельные CLI тестовых данных могут перезаписать хеш и снять флаг у ранее созданных демонстрационных администраторов. Для записи в ожидании смены это противоречит CHECK и должно заканчиваться откатом. Эти команды не входят в путь обновления сохранённой БД. [Запись демонстрационных администраторов](../../../backend/src/GymCrm.Api/SeedData/LeninskyAdministratorSeed.cs).

## Validation

- Интеграционные HTTP-тесты двух независимых cookie получателя, отдельной сессии инициатора и другого пользователя, совпадающей миллисекунды, повторного сброса, отказа старых паролей и возврата к обычному входу. Оба PUT во время сброса сохраняют требование смены. Защищённый Staff API и Bot API проверять напрямую.
- Сверить `ResetPassword` и реальный POST по матрице ролей и семейства, при основном назначении на первый и последний день, будущем или закончившемся назначении, нескольких филиалах и одном замещении. Отключённая запись остаётся отключённой. После отказов проверить неизменность идентификации, хеша, флагов, версии и аудита. Проверять отсутствие тестового секрета и хеша во всех полях аудита и ответов.
- На PostgreSQL проверить обе очередности фиксации для сброса и самостоятельной смены, сброса и изменения роли/филиала, снятия последнего действующего назначения. Смоделировать сбой аудита и проверить откат. Миграцию прогнать на чистой и уже используемой схеме, с пользователями в обоих состояниях старого `MustChangePassword` и старой cookie.
