# ADR-0004: Атомарный импорт XLSX через backend и разовую CLI

## Контекст

Требуется разовый перенос файла целиком с существующими правами и аудитом.
Сейчас `ClientLifecycleEndpoints.CreateClientAsync` создаёт одного клиента,
его назначения и аудит в одной `ClientAccessTransaction`. Повторение HTTP
запросов не распространяет эту транзакцию на файл. Валидация и часть создания
сейчас находятся в API; отдельный импортёр не должен копировать эти CRM-правила.
Текущее поведение и необходимые проверки разобраны в
[review](/backlog/logs/TASK-196-technical-review-2026-11-15.md).

## Критерии выбора

- Весь файл, назначения и обязательный аудит фиксируются одной транзакцией.
- Actor определяется обычной сессией; действующие роль и филиал проверяются
  в границе записи по ADR-0003, без системного пользователя или DB-доступа CLI.
- Повторный осознанный запуск — новый импорт; дедупликация не вводится.
- Сбой соединения после commit не маскируется сообщением «ничего не записано».
- Новая точка входа остаётся узкой, без очереди, нового сервиса и схемы БД.

## Рассмотренные варианты

### A: CLI вызывает существующее создание клиента для каждой строки

Минимальное изменение, готовая авторизация. Но ошибка поздней строки оставит
ранние записи. Компенсирующее удаление не возвращает атомарность, нарушает
историю и опасно при появившихся связях. Не удовлетворяет REQ-CLI-010.

### B: Backend batch endpoint и тонкая CLI — рекомендуется

Один файл передаётся backend; backend читает его и выполняет один use case.
Повторно используются cookie/CSRF, scope, клиентская валидация и аудит.
Цена: новый Staff API контракт, локальное выделение общего создания клиента,
парсер XLSX и синхронизация API/аудит consumer. Обязательные гарантии проверяемы
на реальной PostgreSQL-транзакции, без отдельной инфраструктуры.

### C: Backend console host с прямым подключением к БД

Может обеспечить одну транзакцию, но требует отдельной аутентификации
оператора, выдачи DB credentials и конфигурации всех backend policies.
Параметр `--actor-id` не доказывает полномочия. Повторная реализация входа
и доступ к БД делают этот вариант дороже и опаснее для данного сценария.

## Решение

Принят вариант B по явному решению владельца от 15.11.2026.
Ниже зафиксирован согласованный технический контракт.

### Границы и доступ

- Новая .NET CLI под `backend/tools/` только отправляет файл, поддерживает
  cookie container, получает CSRF через `/auth/session`, входит через
  `/auth/login` и передаёт актуальный `X-CSRF-TOKEN`. Пароль вводится скрыто,
  не через аргумент командной строки, cookies остаются в памяти.
- CLI принимает `--api-base-url`, `--file`, `--login`, необязательный
  `--branch-id`. Base URL включает `/api`, если используется frontend proxy;
  прямые маршруты backend начинаются с `/clients` и `/auth`.
- Авторизация `ManageClients`; Administrator только в своём филиале,
  HeadCoach/SuperAdministrator в разрешённом глобальном scope, Coach запрещён.
  Смена пароля при первом входе остаётся существующим препятствием входу.
- Backend находит точное имя группы по basename без `.xlsx`; branchId
  сужает выбор. Ноль/несколько совпадений — отказ файла без записи.
  Нельзя молча выбрать первый результат или заменить имя группы её ID.
  Явно чужой branchId Administrator отклоняется до проверки его существования;
  диагностика не раскрывает данные клиентов или подробности чужого scope.
- Общие validate/create/assignments/audit выделяются из существующего create
  в application use case и infrastructure implementation; HTTP остаётся в API.
  Обычное создание использует ту же логику без изменения ответа и правил.
  Остальные клиентские операции структурно не переписываются.

### Transport и обработка файла

- `POST /clients/import-xlsx`, multipart: `file`, необязательный `branchId`,
  обязательный UUID `operationId`, создаваемый CLI заново на каждый запуск.
  GUID служит корреляции, не idempotency key: он не подавляет повторную запись.
- Успех `200 { operationId, createdCount }` только после commit, без клиентских
  DTO. Ошибки, сформированные import handler после чтения корректного operationId,
  — существующий ProblemDetails envelope с `operationId`,
  `code` и `issues: [{ row: number|null, field: string|null, code, message }]`.
  `row` — номер в Excel, включая заголовок; сообщения без значений ячеек.
  400 — файл/данные/выбор группы/CSRF; 401/403 — существующие отказы доступа;
  409 — изменившийся выбор группы; 413 — лимит; 5xx — внутренняя ошибка.
- Штатные auth/CSRF/framework/proxy ошибки сохраняют существующий формат:
  могут не содержать operationId/issues или JSON. CLI сохраняет локальный ID
  и корректно обрабатывает такой ответ без расширения общего middleware.
- Все диагностируемые ошибки данных собираются до добавления сущностей;
  ошибки структуры, не позволяющие прочитать строки, относятся к файлу.
- Infrastructure читает XLSX через `DocumentFormat.OpenXml` в режиме read-only.
  Это новая локализованная зависимость с закреплённой версией/lockfiles и audit;
  выбор patch-версии при реализации не меняет контракт.
  SDK документирует чтение значений и shared strings:
  [Microsoft Learn](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/how-to-retrieve-the-values-of-cells-in-a-spreadsheet),
  [репозиторий и MIT license](https://github.com/dotnet/Open-XML-SDK).
- Поддерживаемый профиль: лист `Клиенты`, A1:J1 из task, текстовые значения
  shared/inline strings и числовой баланс; ДР — текст ДД.ММ.ГГГГ или пусто.
  Полностью пустые строки пропускаются с сохранением исходной нумерации.
  Формулы, непарные пометки, неизвестный статус/формат номера, ошибочные
  ячейки и другие неподдерживаемые данные дают явную ошибку без угадывания.
  Формулы не вычисляются, внешние связи не загружаются, архив не извлекается
  как набор файлов. Workbook не сохраняется как постоянный артефакт;
  штатные временные request/proxy buffers освобождаются после запроса.
- Для этого разового профиля приняты пределы: 512 KiB файла, 768 KiB HTTP
  body, 8 MiB суммарно распакованных частей, 1000 непустых строк. Проверять
  фактически прочитанные байты, а не доверять только метаданным ZIP.
  Предоставленные файлы занимают 12952/14835 байт и 48/66 строк.
  Лимиты endpoint не изменяют настройки загрузки фото и общие proxy limits.

### Транзакция, аудит и неопределённый результат

- Парсинг и чистая нормализация выполняются до locks. Затем одна
  `ClientAccessTransaction`: Branches → actor → TrainingGroups по существующему
  порядку. Повторно загрузить actor, проверить active/role/scope, группу,
  её имя/филиал и доменную валидность всех строк до первого добавления клиента.
  Изменившийся набор нужных locks/выбор группы отклоняется без записи.
  Новые глобальные locks и retry loops не вводятся.
- Все Clients, ClientGroups, branch/group assignment periods, метаданные
  заметки и `ClientCreated`/`ClientNoteChanged` каждой строки используют один
  scoped DbContext и одну транзакцию. Ошибка любой записи или аудита откатывает
  весь файл; commit по строкам и best-effort audit запрещены.
- В ту же транзакцию добавить итоговый audit `ClientImportCompleted`,
  entity `ClientImport`, EntityId = operationId, NewValueJson с operationId,
  числом созданных клиентов и их ID. Actor/time — штатные поля; source остаётся
  штатным `Web`. Сырые XLSX, телефоны и комментарии в итоговый audit не копируются;
  обязательные стандартные клиентские audit snapshots сохраняются как раньше.
- CLI печатает operationId до отправки. При сетевом обрыве/таймауте/5xx после
  отправки сообщает «результат не подтверждён» и не повторяет mutation.
  HeadCoach/SuperAdministrator сверяет actor/action/time и operationId через
  существующий журнал; Administrator не получает нового права чтения аудита.
  Отсутствие записи, пока запрос ещё выполняется, не доказывает rollback.
  Новый запуск допустим осознанно после установления исхода; он создаст новые
  карточки даже для идентичного файла. Recovery не вводит дедупликацию.

## Последствия

- Сохраняются атомарность и существующие права; схема и отдельный сервис не нужны.
- Транзакция удерживает locks до сохранения файла; размер ограничен указанным
  профилем. Импорт на десятки тысяч строк не является скрытым расширением scope.
- При неопределённом исходе требуется сверка журнала привилегированным
  сотрудником; гарантии exactly-once и автоматическое восстановление не обещаются.

## Cross-layer impact

- Backend: application/import contract, infrastructure XLSX/persistence, API,
  CLI, существующее одиночное создание, локализация ошибок/аудита.
- Frontend: mirror import request/result/problem в `src/lib/api/**`, facade,
  transport/consumer tests и подписи итогового аудита в существующем журнале.
  Новый экран или новый пользовательский workflow CRM не добавляется.
- Bot: его contracts и endpoint не меняются; он увидит обычных новых клиентов.
- Deploy/runtime: без новых сервисов/env/schema; CLI запускается отдельно,
  backend доставляется обычным релизом. Развёртывание и реальный импорт не
  входят в разрешение создать этот план.

## Migration and rollback

Миграции не нужны. При ошибке до commit транзакция откатывает весь файл.
После успешного commit откат бинарников сохраняет клиентов, назначения и
append-only audit. Автоматического удаления уже импортированных данных нет;
ошибочный успешный перенос разбирается отдельной авторизованной коррекцией.
Неопределённый commit разрешается проверкой итогового audit после завершения
запроса; повторять импорт вслепую запрещено контрактом CLI.

## Validation

Основной барьер — PostgreSQL import integration tests с отказом сохранения
и обязательного аудита на поздней строке: нулевой прирост всех связанных
таблиц. Отдельно проверить success, повтор как новую операцию, actor/scope
interleavings, все 114 структурных профилей, frontend error/audit consumer и
CLI cookie/CSRF/no-retry. Конкретные сценарии находятся в плане.
