# ADR-0006: Включительная граница назначения тренера

- **Статус:** Accepted (пользователь, владелец проекта, 2026-11-16)
- **Дата:** 2026-11-16
- **Автор / владелец:** Codex / пользователь, владелец проекта

## Связанные требования

- REQ-GRP-002 — constrains
- REQ-GRP-004 — constrains
- REQ-USR-001 — constrains
- REQ-SUB-010 — constrains (последний день исторической атрибуции тренера)
- REQ-CLI-007 — constrains (отдельное исправление business day клиента)

## Контекст

При проверке TASK-196 на неизменённой main `9edbda2` воспроизведены два дефекта.
Владелец явно разрешил включить их исправление и завершить интеграцию.

Клиентский transfer вычисляет день из UTC, тогда как seed и текущий клиентский
контракт используют IBusinessDateProvider (Europe/Moscow). После московской
полуночи вчерашнее назначение ошибочно считается созданным сегодня и удаляется
как нулевой период. Исправление использует существующий business date provider;
timestamps остаются UTC, интервалы клиента сохраняют `[from,to)`.

У тренеров конфликт шире: `GroupTrainerAssignmentEndpoints`, UI, Schedule,
Attendance и Bot используют включительный `ValidTo`. `GroupsApiTests` явно
ожидает сохранённое 2034-12-31 при замене с 2035-01-01. Но PostgreSQL CHECK
требует `ValidTo > ValidFrom`, exclusion использует `[)`, и финансовые отчёты
также исключают последний день. Закрытие назначения с предыдущего дня даёт
однодневный включительный период и HTTP 500.

## Критерии выбора

- Сохранить публичную включительную дату и однодневные назначения.
- Единое толкование истории календарём, посещениями, Bot и отчётами.
- Не удалять, не сдвигать и не угадывать существующие даты автоматически.
- Проверяемый upgrade retained database и безопасный отказ при конфликте.

## Рассмотренные варианты

### Вариант A: Включительное хранение назначений тренеров

- Сохранить значения и действующие public/Calendar/Attendance/Bot contracts.
- Forward migration меняет CHECK на `>=`, exclusion на `[]` только у
  GroupTrainerAssignments; отчёт использует включительный последний день.
- Цена: изменение DB-ограничений. Соприкасающиеся старые `[)` интервалы могут
  конфликтовать после перехода; миграция обязана выявить их и остановиться
  без изменения/удаления строк. Автоматического разрешения конфликтов нет.

### Вариант B: Исключительное хранение с преобразованием публичных дат

- Сохранить исходную структуру DB-ограничений.
- Добавить преобразование inclusive ↔ exclusive на всех write/read boundaries;
  обновить календарь, посещения, Bot и тесты сохранённых периодов.
- Цена: намного больший cross-layer delta. Смешанную старую историю нельзя
  автоматически сдвинуть на день без знания происхождения каждой строки.

## Решение

Принят A: включительный последний день уже подтверждён публичными типами,
UI и executable сценариями. Хранение приводится к нему без переписывания дат.
Владелец явно принял вариант A 2026-11-16.

## Последствия

- Однодневное назначение и закрытие вчерашнего назначения становятся допустимы.
- Финансовая атрибуция включает последний день, как календарь и посещения.
- Исторические неоднозначные пересечения не исправляются молча; deployment
  требует отдельной диагностики и решения владельца по найденным конфликтам.
- Простой откат схемы после появления однодневных записей небезопасен.

## Cross-layer impact

- Backend: trainer assignment mutations, current GroupTrainers projection,
  финансовый period lookup и доменный date predicate; client assignment day.
- Frontend: публичные даты сохраняются; выполнить staffing, transfer и import
  consumer regressions, не вводить клиентские правила интервалов.
- Bot: backend Bot period semantics сохраняются; проверить последний день
  контрактными тестами и существующий Python baseline при выборе harness.
- Deploy/runtime: только новая forward migration, исторические migrations не менять.
- Public or internal contracts: shape без изменений; исправление согласованности
  последнего дня и business day, права не расширяются.

## Migration and rollback

Новая transactional migration сначала проверяет пересечения по включительной
границе и завершает работу с диагностикой при конфликте. Затем заменяет CHECK
и exclusion без изменения строк. Проверить clean bootstrap и upgrade текущего
retained schema с одиночными/закрытыми/открытыми периодами, а также сохранность
всей истории при конфликте. Production migration этим ADR не разрешается.

Откат приложения не удаляет историю. Down migration допускается только когда
нет однодневных записей; иначе явный отказ без удаления данных. После новых
записей предпочитается forward fix. Версия приложения с прежней ошибкой может
снова ошибаться в UI/отчёте и не считается безопасным штатным rollback.

## Validation

- Детерминированные failing tests для московской даты, отличной от UTC.
- PostgreSQL: one-day assignment, закрытие вчерашнего периода, отсутствие
  пересечений, актуальный GroupTrainers после снятия, history и audit.
- Последний день согласован в Schedule/Attendance/Bot и финансовой атрибуции.
- Clean bootstrap, retained upgrade, conflict rollback и guarded Down.
- Полный harness и TASK-196 verification contract на итоговом candidate.

## Review evidence

16.11.2026 — отдельный read-only backend review подтвердил вариант A и
конфликт сохранённых периодов. Также выявлено, что текущая projection
GroupTrainers читает БД до сохранения удалений/закрытий: снятый тренер может
сохранить текущий доступ. В scope исправления входит вычисление projection
по изменённому состоянию внутри той же транзакции и regression доступа;
права и правила назначения не меняются. Review не является approval.

## Open questions

  текущая migration обязана безопасно отказать.
