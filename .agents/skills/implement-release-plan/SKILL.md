# Implement release plan

## Результат и режим

По умолчанию работать в режиме `implementation`:

1. реализовать переданный план или набор планов в task-workspace;
2. проверить итоговый candidate SHA;
3. локально интегрировать изменения в указанную основную ветку;
4. актуализировать связанные задачи;
5. очистить созданные task-ресурсы.

Включать режим `release` только когда пользователь или план явно задаёт общий
стенд для обновления. Этот режим дополнительно включает миграцию, deployment и
runtime-проверки. Не угадывать стенд и не превращать обычную реализацию в
deployment.

Считать явный вызов skill разрешением на task-ветки/worktree, локальные
коммиты, локальный merge, обновление backlog/status-файлов и безопасную очистку
созданных ресурсов. Не считать его разрешением на push, PR, production,
публикацию release или построение ветки от другой неслитой task-ветки.

## Загружать только применимые инструкции

- Для одного плана без DB/runtime/deployment изменений не читать references.
- Для двух и более планов полностью прочитать
  [references/batch-integration.md](references/batch-integration.md).
- При изменении схемы/данных, необходимости runtime-стенда или явном deployment
  полностью прочитать
  [references/runtime-release.md](references/runtime-release.md).

Не копировать содержание references, `AGENTS.md` или project skills в рабочие
заметки и планы.

## Вход и приоритет источников

Принимать путь к одному plan, список путей или manifest. Для списка проверить
все файлы, удалить точные дубликаты путей и сохранить порядок пользователя.
Если путь нельзя однозначно определить, запросить его.

Применять источники в порядке:

1. запрос пользователя;
2. ближайший `AGENTS.md`;
3. код, типы, тесты и конфигурация;
4. runtime/build-конфигурация;
5. implementation plan как описание требуемого результата;
6. документация.

Полностью читать корневой и релевантные вложенные `AGENTS.md`. Подключать только
обязательные ими skills и роли. Не дублировать эти правила внутри release
workflow.

## Короткий preflight

Для одного плана зафиксировать только:

- source task и declared branch;
- requirements metadata и product decision каждого `REQ-*`;
- подтверждённые зависимости или `none`;
- затронутые слои;
- наличие DB/runtime/deployment изменений;
- readiness/blocker.

Остановиться до изменения project code, если metadata отсутствует, содержит
`pending`, ссылается на неизвестный ID или на решение `предложено`/`отклонено`.
`none` допустимо только с конкретной причиной, что задача сохраняет поведение.
При конфликте plan с карточкой вернуть затронутый план в planning; не реализовывать
самостоятельно выбранный baseline или новый delta. Сначала согласовать точную
редакцию и обновить источники решения.

До любого изменения project code выполнить для каждого переданного плана
readiness preflight из `docs/HARNESS.md`. `readiness: no`, отсутствующее evidence,
незакрытый вопрос, непринятый ADR или отложенный выбор UX/контракта блокируют
исполнение всего затронутого плана. Не выполнять даже «независимые» slices внутри
такого плана; независимо готовые планы можно продолжать.

Не строить release-реестр или dependency graph для одного плана. Для набора
использовать компактную таблицу из batch reference.

Перед изменением project code использовать project `task-worktree` skill. Он
единолично определяет команды создания, проверки, возобновления и очистки
worktree. Не повторять его Git-инструкции здесь и не менять код в coordination
workspace.

## Реализация

Для каждого плана:

1. сверить ожидаемый результат с текущим кодом и тестами;
2. проверить соответствие кода согласованным решениям, зависимостям и stop conditions;
3. добавить конкретный regression evidence в порядке, требуемом планом и
   проектом;
4. внести минимально достаточные изменения без unrelated refactoring;
5. обновить всех потребителей изменённого контракта;
6. для изменения поведения обновить нормативный текст, поля решения/реализации,
   audit history карточки и `docs/requirements/CHANGELOG.md` в этой же задаче;
7. выполнить проверки ближайших `AGENTS.md` и requirements validator на
   финальном candidate SHA;
8. проверить diff, статус worktree и отсутствие случайных файлов.

Не создавать формальный red test, если текущий baseline уже корректен и задача
является runtime/version-skew расследованием. Сначала доказать слой проблемы,
затем менять только его.

## Проверки без повторов

Считать результат проверки привязанным к exact candidate SHA/tree.

- Перед merge выполнить полный обязательный набор проверок изменённых слоёв.
- После merge сравнить tree candidate и итоговой основной ветки.
- Если tree совпадает, конфликтов не было и runtime не изменился, использовать
  уже полученное evidence вместо повторного полного запуска.
- Если tree изменился из-за новой base, конфликтов или межплановой интеграции,
  повторить затронутые проверки.
- Для batch выполнить один совокупный regression pass после последнего merge;
  не запускать одинаковый полный suite после каждого независимого fast-forward.

Не объявлять не запускавшуюся проверку успешной. Команды и результаты хранить
кратко: command/filter, SHA, outcome.

## Интеграция и статусы

Интегрировать в подтверждённом порядке по Git-политике проекта. Функциональные
исправления выполнять в task-worktree, а межплановые — в отдельной
integration-fix ветке только когда ошибка действительно пересекает несколько
планов.

После успешной интеграции:

1. проверить достижимость task commits из основной ветки;
2. для затронутой текущей редакции требования установить реализацию
   `реализовано` только после evidence в основной ветке; иначе оставить
   `частично`/`не начато` и зафиксировать причину;
3. актуализировать только фактически завершённые task/plan status; перенести
   карточку, plan, verification contract и task-owned evidence вместе в
   `backlog/done/YYYY-MM-DD/` по правилам даты в `backlog/README.md`, записать
   `completed_at` и `completion_date_evidence`, обновить актуальные ссылки;
4. по возможности включить status-файлы в task-ветку; если завершение можно
   зафиксировать только после release, использовать один closure commit/branch
   для всего набора;
5. не повторять runtime deployment из-за status-only commit, если backlog не
   входит в build artifact;
6. вызвать project `task-worktree` skill для безопасной очистки.

## Новое решение во время исполнения

Если обнаружен пробел, требующий продуктового или существенного технического
выбора, остановить зависимую работу, поставить `readiness: no`, записать вопрос
и вернуть задачу из implementation в needs-clarification (review-only — risky).
Вернуться к planning: получить решение владельца, обновить REQ/ADR, plan и
approval evidence, затем повторить preflight. Не считать просьбу реализовать
план согласием на новые решения. Локальные обратимые детали кода, сохраняющие
согласованные контракты, остаются полномочием исполнителя.

## Блокеры

Остановиться только когда безопасное продолжение невозможно: отсутствует plan,
нельзя определить требуемый контракт/зависимость, есть необъяснимые изменения,
нужен продуктовый выбор, отсутствует обязательный доступ/секрет или миграция
несёт риск потери данных без recovery. Продолжать только независимо готовые планы,
если это не ухудшает состояние.

## Финальный отчёт

Сообщить только применимое:

- выполненные plans, порядок и итоговые SHA;
- изменённые контракты;
- проверки с привязкой к SHA;
- migration/deployment outcome, если режим `release` был включён;
- актуализированные статусы и очищенные ресурсы;
- оставшиеся блокеры или ручные действия.

Не перечислять отсутствующие миграции, конфликты, агентов или стенды и не
утверждать выполнение действия без evidence.
