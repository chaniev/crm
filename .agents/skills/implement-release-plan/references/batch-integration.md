# Порядок интеграции набора задач

Читать только для набора выпуска из двух и более планов.

## Реестр

Составить одну компактную таблицу:

| План | Ветка | Зависит от | Пересечения | БД и среда выполнения | Статус |
|---|---|---|---|---|---|

Сначала использовать явные зависимости. Выводить техническую зависимость только
из API-контрактов, общей схемы или снимка модели, конфигурации запуска или реально
пересекающихся файлов; отмечать её как вывод. Остановиться при цикле или продуктовой
неоднозначности, не разрешимой по контрактам.

## Порядок и параллельность

- Зависимые планы выполнять последовательно.
- Независимые планы можно выполнять параллельно только без пересечения файлов,
  API-контрактов, миграций и ресурсов запуска, если это разрешают инструкции репозитория.
- Одна задача получает одну ветку и рабочее дерево. Не строить ветку от
  необъединённой ветки другой задачи без явного разрешения.
- Последовательно выполнять планы, меняющие один снимок модели БД или цепочку миграций.
- Препятствие одного плана не останавливает независимые планы.

## Интеграция

1. Сначала интегрировать предшественников.
2. Синхронизировать с обновлённой базой только зависимую, пересекающуюся или
   следующую готовую к объединению ветку; не обновлять все ветки после каждого объединения.
3. После изменения базы повторять только затронутые проверки.
4. После последнего объединения выполнить один совокупный регрессионный проход
   по всем изменённым слоям.
5. Обновить статусы набора одним завершающим изменением, если их нельзя было
   включить в ветки задач.

Не использовать отдельную ветку выпуска или интеграции без требования
пользователя, плана или политики проекта.
