# Подготовка готовых задач к реализации

## Результат

Подготовить 1–3 выбранные задачи к исполнению:

1. Проверить пригодность и отсутствие дублей.
2. Переместить готовую задачу в `backlog/implementation` либо оставить рискованную
   в `backlog/risky` с планом только для планирования.
3. Обновить метаданные жизненного цикла.
4. Создать один компактный план реализации на задачу.
5. Обновить `backlog/logs/implementation-log.md`.

Не менять код, не создавать ветку или рабочее дерево и не реализовывать план.
Здесь ветка лишь объявляется для будущего исполнителя.

## Выбор задач

Если указаны TASK-файлы, работать только с ними. Иначе выбрать не более трёх
задач из `backlog/tasks-ready` по влиянию, ясности границ, риску и наличию
реалистичной автоматической защиты от регрессии.

Не готовить дубль активной или завершённой задачи либо плана. Не переводить
в реализацию задачу с незакрытыми критичными продуктовыми вопросами, полностью
неясными границами или необратимым действием в промышленной среде без восстановления.

Каждая задача содержит `## Requirements`. Для изменения поведения использовать
`REQ-*` с решением `принято` или добавить карточку по
`docs/requirements/_шаблон-требования.md`. Новое `предложено` не разрешает
реализацию: оставить задачу в `backlog/needs-clarification` до явного продуктового
согласования, затем записать `принято` со ссылкой на задачу. `none` допустимо
только с конкретной причиной сохранения поведения. `pending` — только
в `needs-clarification`. Обновление затронутых карточек и CHANGELOG входит
в критерии завершения работы исполнителя.

Для `changes` до перемещения записать принятую целевую редакцию требования,
добавить историю/CHANGELOG и сменить реализацию с `реализовано` на `частично`
или `не начато`. Для `implements` карточка уже описывает принятую цель,
не меняющую смысл в этой задаче.

Работа со всеми слоями, общий интерфейс, миграции, платежи, роли и права сами
по себе не блокируют планирование. Если изменение локализуемо, подготовить план
с конкретным риском. Рискованная задача может получить план, но остаётся
в `backlog/risky` с `readiness: no` до обязательного ревью или решения.

Без подходящей исходной задачи не создавать план из догадки и не перемещать
файлы. Записать `moved: none`, назвать проверенные и пропущенные варианты
и минимальную недостающую информацию.

## Минимальное достаточное решение

До выбора этапов рассмотреть доработку существующей политики, области запроса,
транзакции или подхода интерфейса. Новый механизм нужен, если существующий
не обеспечивает конкретный обязательный контракт. Малый объём изменений
не оправдывает пропуск затронутого API, потребителя или пути доступа.

Для нового общего механизма или широкой правки кратко обосновать в
`Decisions and contracts` либо ADR: требующий сценарий, недостаточность более
простого решения, добавленную стоимость реализации, проверок и сопровождения.
Число файлов само по себе не доказывает избыточность или безопасность.
Не создавать отдельный отчёт, числовой бюджет или дополнительное согласование.

Различать выполнение требований и дополнительное усиление гарантий. Не обещать
более строгую конкурентность, обработку повторов или внешних эффектов «на всякий
случай»; существенный выбор обосновать через `architecture-decision`.
Подтверждённый обход доступа или риск целостности в задаче не откладывать ради
скорости. Несвязанные улучшения оставить вне плана.

Если простое продуктовое изменение требует нескольких новых механизмов,
до готовности пересмотреть декомпозицию и более простой вариант. Причину
оставшейся сложности записать в существующем плане/ADR; не разделять обязательную
сквозную защиту на частично безопасные выпуски.

## Согласование до готовности плана

До `readiness: yes` закрыть все продуктовые и существенные технические решения
задачи: роли, сценарии, ошибки, UX-направление, контракт взаимодействия,
API и данные, зависимости, миграцию и откат, обязательные ревью.
Применимые процессы дизайна и архитектуры выполнить при планировании.
Для существенного выбора использовать `architecture-decision`; `Proposed`
не разрешает исполнение. Обычные детали кода внутри согласованных контрактов
не требуют отдельного согласования.

Не включать выбор варианта, согласование UX, утверждение контракта или определение
поведения в этапы реализации и ручные проверки. Это препятствия планирования,
даже с пометкой «позже» или «до UI». При реализации допустима проверка
соответствия уже согласованному решению.

Записать источник, владельца и точное содержание согласования в `Decision evidence`;
не выдумывать его и не переспрашивать уже принятое. Незакрытые вопросы оставить
в черновике с `readiness: no`; задача остаётся в `needs-clarification` или `risky`
по виду препятствия. Только после согласования проверить готовность по
`docs/HARNESS.md` и переводить задачу в реализацию. При проверке `source_task`
указывает на существующий текущий файл. После перемещения обновить ссылку
и повторить проверку.

## Жизненный цикл

Для готовой задачи:

- переместить из `backlog/tasks-ready` в `backlog/implementation`;
- установить `## Status` в `implementation`;
- добавить или обновить:

```md
## Implementation lifecycle
- moved_to_implementation_at: YYYY-MM-DD HH:mm
- moved_from: /backlog/tasks-ready
- implementation_plan: /backlog/implementation-plans/TASK-XXX-short.plan.md
- implementation_branch: feature/TASK-XXX-short
```

Для рискованной задачи только на этапе планирования не менять каталог/статус.
Добавить ссылку на план в существующий раздел жизненного цикла или обработки,
только если проект уже использует такой контракт метаданных.

## Правила компактного плана

Включать только нужное будущему исполнителю, что нельзя проще получить
из исходной задачи, `AGENTS.md`, кода или проектных навыков.

Обязательно:

- исходная задача, ветка, готовность, зависимости и конкретный риск;
- метаданные требований из задачи с `implements`, `changes`, `constrains`,
  `verifies` либо обоснованным `none`; `pending` в исполнимом плане запрещён;
- цель и решения, реально влияющие на реализацию;
- изменяемая семантика контрактов, данных и UX;
- ограниченные этапы реализации;
- вероятные файлы и слои;
- конкретные тесты, доказательства ожидаемого исходного падения и защита от регрессии;
- специфичные для задачи риски и условия остановки.

Не включать:

- команды веток/рабочих деревьев и перечень SHA/копий на момент планирования;
- пересказ `AGENTS.md`, архитектурных инвариантов и матрицы проверок;
- общие роли агентов: исполнитель выберет их по ближайшему `AGENTS.md`;
- общий порядок «сначала тесты» в каждом плане;
- общую стратегию всех слоёв, совместимости и коммитов;
- одинаковые требования одновременно в `Current understanding`, шагах,
  покрытии тестами, плане тестирования и защите от регрессии;
- длинный итоговый список и поля для неприменимых миграций или стендов.

Порядок «сначала тесты» задаётся один раз здесь: исполнитель добавляет или
обновляет перечисленные автоматические тесты, подтверждает ожидаемое падение
из-за отсутствующего поведения, затем меняет функциональный код и получает
успех. Если базовая версия уже проходит или падение неприменимо, указать
конкретное доказательство без требования искусственно падающего теста.

Обычно план укладывается примерно в 250 строк. Сложный контракт предметной
области, API или данных может быть длиннее, но каждый смысл описывается в одном месте.

## Шаблон плана

Английские имена разделов и полей ниже являются частью проверяемого формата;
сохранять их, заполняя пояснения на русском.

```md
# Implementation Plan: TASK-XXX Название

## Metadata
- source_task: /backlog/implementation/TASK-XXX-short.md
- requirements: REQ-XXX-000 (implements|changes|constrains|verifies) | none — причина
- branch: feature/TASK-XXX-short
- readiness: yes | no — краткая причина, если no
- product_decisions: accepted | none — конкретная причина
- technical_decisions: accepted | none — конкретная причина
- architecture_decisions: ADR-NNNN | none — почему ADR не требуется
- open_questions: none | конкретные препятствия для readiness: no
- dependencies: none | TASK-YYY (условие)
- risk: low | medium | high — причина, специфичная для задачи

## Goal
Измеримый пользовательский или системный результат.

## Decisions and contracts
- Только подтверждённые решения и изменяемые контракты.
- Не повторять неизменившуюся исходную задачу.

## Decision evidence
- product: [Источник согласования](/path/to/source.md) — owner: имя/роль; decision: точное принятое поведение и выбранное UX-направление.
- technical: [Источник решения](/path/to/source.md) — owner: имя/роль; decision: согласованный технический контракт.

## Scope
### In
- ...

### Out
- ...

## Implementation slices
1. Ограниченный функциональный этап с наблюдаемым результатом.
2. Следующий этап только при реальной зависимости.

## Likely files and layers
- `path` — зачем меняется; либо `to be discovered before editing`.

## Regression specification
### Automated tests to add or update
- Конкретный тест или сценарий и ожидаемое поведение.

### Expected red evidence
- Какой тест должен упасть и почему; либо почему исходное падение неприменимо.

### Required validation
- Только специфичные для задачи команды/фильтры сверх обязательных проверок ближайшего
  `AGENTS.md`.

### Manual evidence
- Только то, что невозможно надёжно автоматизировать.

### Regression barrier
- Одна основная автоматическая проверка, защищающая цель.

## Risks and stop conditions
- Только специфичные для задачи риск/условие остановки и согласованная реакция.
```

Для `accepted` соответствующая строка доказательства обязательна. Для `none`
вместо неприменимой строки сослаться на исходную задачу с обоснованием сохранения
поведения. Ссылки репозитория отсчитываются от корня; заменить `ADR-NNNN` реальными ID.

Не создавать пустые разделы. Для большого UX- или предметного контракта добавить
один `## UX contract` либо `## Domain/API contract` без пересказа в других разделах.

## Порядок работы

Для каждой задачи:

1. Прочитать исходную задачу и проверить соответствие каталога и статуса.
2. Найти дубли во всех активных каталогах и рекурсивно в `backlog/done/YYYY-MM-DD/`.
3. Проверить критичные вопросы, границы, зависимости, стратегию регрессии
   и согласование требований.
4. Выбрать уникальную ветку с префиксом `feature/`, `fix/` или `refactor/`.
5. Создать компактный план, закрыть решения и проверить готовность.
6. Переместить только готовую задачу и обновить жизненный цикл.
7. Добавить одну краткую запись в журнал реализации.

Формат записи:

```md
# YYYY-MM-DD HH:mm
- moved: TASK-XXX | none
- planned_in_place: TASK-YYY | none
- skipped: TASK-ZZZ — причина | none
- plans: /backlog/implementation-plans/TASK-XXX-short.plan.md | none
```

## Проверка результата

Проверить:

- ссылки на источники, задачи и планы, названия веток;
- метаданные требований задач/планов, наличие ID, решение `принято`, отсутствие
  `pending`; для `none` — конкретную причину сохранения поведения;
- отсутствие дублей TASK-ID и планов;
- статусы и жизненный цикл перемещённых задач;
- необходимость новых механизмов и отсутствие необоснованного расширения;
- конкретные тесты, доказательства исходного падения и защиту от регрессии;
- отсутствие повторов `AGENTS.md`, правил рабочих копий, агентов и общих проверок;
- изменения ограничены бэклогом и, только при создании/принятии требования,
  `docs/requirements/**` вместе с `CHANGELOG.md`.

В отчёте перечислить изменённые файлы задач, планов и журнала, причины пропуска.
Не печатать полное дерево бэклога и не пересказывать созданные планы.
