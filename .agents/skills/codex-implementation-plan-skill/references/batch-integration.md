# Batch integration

Читать этот файл только для release-набора из двух и более планов.

## Реестр

Составить одну компактную таблицу:

| Plan | Branch | Depends on | Overlap | DB/runtime | Status |
|---|---|---|---|---|---|

Сначала использовать явные зависимости. Выводить техническую зависимость
только из API contracts, общей схемы/snapshot, runtime config или реально
пересекающихся файлов; отмечать её как inference. Остановиться при цикле или
продуктовой неоднозначности, которую нельзя разрешить по контрактам.

## Порядок и параллельность

- Зависимые планы выполнять последовательно.
- Независимые планы можно выполнять параллельно только при непересекающихся
  файлах, API contracts, migrations и runtime resources и когда это разрешают
  repository instructions.
- Один task получает одну branch/worktree. Не строить branch от неслитой task
  branch без явного разрешения.
- Планы, меняющие один DB snapshot или migration chain, сериализовать.
- Блокер одного плана не должен останавливать независимые планы.

## Интеграция

1. Интегрировать предшественников первыми.
2. Синхронизировать с обновлённой base только зависимую, пересекающуюся или
   готовую к следующему merge ветку; не обновлять все ветки после каждого merge.
3. После изменения base повторять только затронутые проверки.
4. После последнего merge выполнить один aggregate regression pass по всем
   изменённым слоям.
5. Актуализировать статусы набора одним closure change, если их нельзя было
   включить в task-ветки.

Не использовать release/integration branch без требования пользователя, плана
или project policy.
